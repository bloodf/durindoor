title: Release process
description: Release Prepare, Release Tag, npm publish of the durindoor CLI, and rollback.
---

Releases are a three-workflow chain on `bloodf/durindoor`. A human triggers **Release Prepare**. Merging the release PR to `main` fires **Release Tag**, which tags `vX.Y.Z` and creates the GitHub Release. Publishing that Release fires **Release**, which publishes the CLI to npm.

```text
workflow_dispatch (bump, automerge)
        |
        v
Release Prepare (release-prepare.yml)
  compute version, bump package.json (root + cli), changelog, PR to main
        |
        | squash merge
        v
Release Tag (release-tag.yml)
  tag vX.Y.Z, gh release create
        |
        | release: published
        v
Release (release.yml)
  lint, check:agent-index, build, test:ci, npm run cli:publish
```

## Secrets

Two repository secrets:

- `NPM_TOKEN`: used by `release.yml` as `NODE_AUTH_TOKEN` when it runs `npm run cli:publish`.
- `RELEASE_PAT`: a fine-grained personal access token with `contents: write` and `pull-requests: write` on this repository.

Events created with `GITHUB_TOKEN` do not trigger other workflows. Both prepare and tag authenticate writes with `${{ secrets.RELEASE_PAT || secrets.GITHUB_TOKEN }}`.

Without `RELEASE_PAT`:

- Prepare still pushes the branch and opens the PR, but `ci.yml`, `test.yml`, and `commitlint.yml` never run on that PR. Required checks stay red and auto-merge stalls. The workflow prints a warning. Run the gates locally, record them in the PR, and merge with a maintainer account.
- Tag still creates the GitHub Release, but `release.yml` never fires, so npm publish does not run. See [Manual fallback](#manual-fallback).

## Cutting a release

### From the UI

1. Actions, Release Prepare, Run workflow.
2. Pick `bump` (`auto` derives it from conventional commits since the last tag; `patch` / `minor` / `major` force it) and leave `automerge` on unless you want to review the PR first.
3. The workflow opens a PR titled `chore(release): bump version to X.Y.Z`.

Checkout is pinned to `main` no matter which ref the dispatch UI selects.

### From the CLI

```bash
gh workflow run release-prepare.yml --repo bloodf/durindoor -f bump=auto -f automerge=true
```

Merging the release PR is the automation cutover: the push to `main` fires Release Tag, which tags `vX.Y.Z`, extracts that version's section from `CHANGELOG.md` (`node scripts/release-notes.mjs extract X.Y.Z`), and creates the GitHub Release. Publishing the Release fires `release.yml`, which runs lint, `check:agent-index`, build, the tests package CI script with `BASELINE_BASE_REF=HEAD^`, then `npm run cli:publish`.

The squash title is part of the contract. Release Tag runs on a main push only when the head commit subject starts with `chore(release): bump version to`. It then requires the first subject line to be exactly `chore(release): bump version to X.Y.Z`, or that string plus the repository's ` (#PR)` squash suffix, and the version in that subject must equal both `package.json` versions at the pushed commit. If a maintainer merges with a renamed title, tagging does not fire. Fallback: Actions, Release Tag, Run workflow with `version: X.Y.Z`. The manual path pins checkout to `main`, checks the requested version against both manifests, and tags that SHA.

If `main` advances while the release PR is open, the waiting PR's version and changelog were computed from the older main. Close the PR and re-dispatch Release Prepare. It recomputes from latest `main`, replaces the stale `release/vX.Y.Z` branch (`--force-with-lease` against the observed SHA), and updates or recreates the PR.

## Editing the release PR

The changelog section is generated from commit subjects and grouped into `## Features` / `## Fixes` / `## Upstream ports` / `## Maintenance`. Edit wording on the `release/vX.Y.Z` branch. Push a follow-up that touches `CHANGELOG.md` only. Do not change the version in `package.json` / `cli/package.json` or the commit/PR title format. `release-tag.yml` verifies the bump commit subject against the version.

After the bump commit, Release Prepare installs commitlint and runs `npx commitlint --from=origin/main --to=HEAD` plus a title check (`echo "<pr-title>" | npx commitlint`) before pushing.

## Versioning

- `auto` bump reads Conventional Commit subjects on `<last-tag>..main`: any breaking marker (`type!:` / `type(scope)!:`) is major; else any `feat` is minor; else patch. The repo is post-1.0, so breaking changes are major bumps.
- Tags are `vX.Y.Z`. `CHANGELOG.md` keeps one `# X.Y.Z` top-level section per version, newest first.
- Root `package.json` and `cli/package.json` are bumped together and must carry the same version.
- Prepare refuses to run when `git describe --tags --abbrev=0 --match "v*"` finds no tag, or when `git rev-list --count` from that tag to `origin/main` is 0.
- Release Tag refuses to re-tag an existing `vX.Y.Z`.

`scripts/release-notes.mjs` is the version math and changelog generator:

```bash
node scripts/release-notes.mjs next-version [--bump auto|patch|minor|major] [--from <tag>]
node scripts/release-notes.mjs notes <version> [--from <tag>]
node scripts/release-notes.mjs extract <version>
```

All three are covered in `tests/unit/release-notes.test.js`. `extract` reads `CHANGELOG.md` only. It resolves no git baseline, so it works in a checkout with no reachable `v*` tag.

## Other publish jobs

`.github/workflows/docker-publish.yml` builds GHCR images on `v*` tags (`ghcr.io/bloodf/durindoor`) and on `workflow_dispatch`. It does not build `nightly-*` tags.

`.github/workflows/nightly.yml` lists `cron: '0 2 * * *'` (02:00 UTC) and `workflow_dispatch`. After lint, `check:agent-index`, build, and `test:ci`, it publishes a GitHub pre-release `nightly-YYYY-MM-DD` (`date -u +%Y-%m-%d`) when that tag does not already exist. A comment in the workflow says the schedule can be disabled in repository settings.

## Failure and rollback

| Stage | Failure | Recovery |
| --- | --- | --- |
| Release Prepare | "No commits since tag" or no `v*` tag | Nothing to release; no state created. |
| Release Prepare | Run failed after the branch push | Re-dispatch. Retry policy replaces `release/vX.Y.Z`. |
| Release Prepare | PR open, CI red | Push fixes to `release/vX.Y.Z`, or close the PR and re-dispatch. |
| Release Prepare | PR stalled with no checks (`RELEASE_PAT` absent) | Run lint, the tests package CI script, and commitlint locally. Note them in the PR. Merge with a maintainer account. |
| Release Tag | Push ran but no tag created | Merge subject missed the contract. Run Release Tag manually with `version: X.Y.Z`. |
| Release Tag | Tag already exists | The guard refuses to re-tag. Bump the version instead. |
| After merge, before npm publish | Bad release | `gh release delete vX.Y.Z --repo bloodf/durindoor --yes`, `git push origin :refs/tags/vX.Y.Z`, then revert the bump commit on `main`. |
| After npm publish | Bad release | npm does not unpublish cleanly. Publish a fixed patch and `npm deprecate` the bad version. |

## Manual fallback

When `RELEASE_PAT` is missing, `release-tag.yml` still creates the Release with `GITHUB_TOKEN` but `release.yml` does not fire. Either:

```bash
gh release delete vX.Y.Z --repo bloodf/durindoor --yes
gh release create vX.Y.Z --repo bloodf/durindoor --title vX.Y.Z --target <bump-commit-sha> --notes-file release-notes.md
```

or publish the CLI directly after the full gate:

```bash
npm run lint && npm run build && (cd tests && npm run test:ci)
NPM_TOKEN=... npm run cli:publish
```

A maintainer can also re-run **Actions, Release Tag, Run workflow** with an explicit `version` input.
