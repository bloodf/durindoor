Two operator-configurable resilience settings live on **Dashboard → Providers → (provider)**, in the same toolbar as Round Robin, Cache Affinity, and Max Concurrent: per-provider error rules and egress-bucketed 429 cooldown. Add active connections and review their proxy-pool assignments before changing either setting.

## Provider error rules

`settings.providerErrorRules` lets an operator declare error markers for a provider alongside the built-in provider rules. A declared rule is consulted before built-in rules, so it can add a marker for a provider that has none, or override the scope and cooldown of a status code that already matches a generic rule.

Open the **Error Rules** button on a provider's connections page to add, review, and remove rules. Each rule has:

- **status**: the HTTP status code from the upstream response (100 to 599).
- **match**: a plain, case-insensitive substring of the raw upstream error text. This is never a regular expression. The settings API rejects anything that is not a plain string, so a rule can never introduce a ReDoS on the error-classification hot path.
- **scope**: `model`, `provider`, or `connection`. Matches the same scopes the built-in rules use for fallback locking.
- **cooldownMs** (optional): overrides the generic exponential backoff ladder.

Example: a provider that returns HTTP 429 with the text `daily cap hit` when its free tier resets, and the operator wants every connection on that account locked for 10 minutes:

```json
{
  "providerErrorRules": {
    "customprovider": [
      {
        "status": 429,
        "match": "daily cap hit",
        "scope": "connection",
        "cooldownMs": 600000
      }
    ]
  }
}
```

`PATCH /api/settings` with that body persists the rule; it applies immediately and again on the next server start. Up to 50 rules total are allowed across all providers.

Declaring a rule for a provider is the opt-in. There is no separate allowlist to widen.

### Built-in rules for Cline and Kilo

- **Cline daily free limit.** A 429 that says `Try again in 19h 39m` (also `19h39m`, `39m`, `45s`) benches the refused model for that stated wait, capped at seven days, instead of retrying after a few seconds. Other Cline models on the connection keep routing. A missing or malformed wait uses the normal 429 backoff, and other providers ignore the phrase.
- **Kilo paid model.** A 401, 402 or 403 whose error code is exactly `PAID_MODEL_AUTH_REQUIRED` (on `kilo-gateway` or `kilocode`) locks only the refused model for two minutes, so free models on the same connection keep routing. If the refused model id is not in the provider's catalog, no lock is written and the request moves on to the next candidate. A message about an invalid or expired key keeps the normal authentication handling.

### Built-in rules for Anthropic credit and spend limits

These apply to `anthropic`, `claude` and `anthropic-compatible-*` connections, and are checked before operator error rules.

- **Credit balance or spend limit.** An HTTP 400 whose Anthropic error message (type `invalid_request_error` or `billing_error`) begins with `Your credit balance is too low` or `You have reached your specified API usage limits` locks the whole connection, every model, and moves to the next account or combo member. The same message with no JSON envelope, with or without a leading `[400]: `, counts too. A message that only quotes either phrase later in the text is treated as a rejected request, so the key stays in rotation.
- **Stated reset.** When the spend-limit message says `You will regain access on 2026-12-01 at 00:00 UTC`, the lock lasts until that time, capped at seven days. `Z`, `UTC`, `+02:00` or `+0200` zones and a `T` separator are accepted, and a time without a zone is read as UTC. An impossible date or time, an out-of-range offset, or a time already past is ignored. Then, as for the credit message, the normal terminal billing cooldown applies, which is two minutes unless **retry delay** is set for the provider. `Retry-After` or a short `retry in 60s` hint never ends the lock early.
- Other providers, OpenRouter-style aggregators that relay Anthropic's envelope, and other status codes keep their existing handling.

A 403 whose message begins with `The free quota has been exhausted` puts the connection in a quota lockout (`quotaLockout.status: "quota_exhausted"`), also when the body was not JSON and reached DurinDoor as `[403]: The free quota has been exhausted...`. Without a stated reset, the lockout is not lifted automatically: reactivate the connection or replace its credential once the quota is restored. Permission and product-access 403s keep the normal 403 cooldown.

## Quota countdown ceiling

A 429 body can state its reset only as a countdown, such as `Resets in 76h25m43s` or `reset after 1h2m3s`. DurinDoor locks the account for that wait, but never longer than `settings.quotaProseMaxCooldownMs`. The default is `21600000` (6 hours). `PATCH /api/settings` accepts 60000 (1 minute) to 86400000 (24 hours).

The ceiling covers only the compact hour, minute and second countdown. `Retry-After`, reset headers, structured reset fields, absolute reset times, and wording such as `reset in 3 days` keep their own deadlines.

## Egress-bucketed 429 cooldown

`settings.egressBucketedProviders` opts a provider into cooling down every sibling connection that shares the same egress IP when one connection hits a 429. This matters for providers whose upstream quota is bucketed by IP address rather than by account: without it, DurinDoor keeps retrying every sibling connection one at a time until each burns its own guaranteed-to-fail call.

The bucket key is the connection's configured proxy pool in **Dashboard → Proxy Pools**. Connections routed through the same pool are assumed to share the same egress IP. Connections with no pool configured are never grouped together, since assuming every direct connection shares one host IP does not hold for most deployments.

Toggle **Egress-Bucketed 429** on a provider's page to opt it in, or set it directly:

```json
{
  "egressBucketedProviders": ["opencode"]
}
```

With that setting, if connection A (assigned to proxy pool `us-east-1`) gets a 429 for `opencode`, every other `opencode` connection also assigned to `us-east-1` is cooled down for the same window, skipping the reauth-quarantined and already-cooling ones. A sibling on a different pool, or with no pool at all, is left alone.

## Verify and recover

Save a narrow rule matching an observed upstream error. Confirm the matching status and cooldown in the provider connection view when that error occurs. Do not use a broad substring that catches unrelated failures.

For egress grouping, inspect proxy-pool assignments before enabling the option. Reusing a pool label is an assumption about shared egress, not a measured public IP. A direct connection is not grouped.

If a rule blocks healthy traffic, remove it in **Error Rules**. Turn off **Egress-Bucketed 429** if your pools do not represent shared quota buckets. Check current connection cooldowns before repeating the request.
