Antigravity (`antigravity`, alias `ag`) sends requests to Google's Cloud Code backend the way the Antigravity IDE does. It signs in with a Google account through OAuth and serves Gemini, Claude, and GPT models that Google exposes to that account, plus one image model.

The provider page shows a risk notice: this is a subscription session that was not licensed for router use, and Google can restrict the account. Use an account you can afford to lose.

## Before you connect

The Google OAuth client is not bundled. `ANTIGRAVITY_OAUTH_CLIENT_ID` and `ANTIGRAVITY_OAUTH_CLIENT_SECRET` are unset by default. Set both in the environment DurinDoor starts with, then restart. With empty values Google rejects the authorize request.

```bash
export ANTIGRAVITY_OAUTH_CLIENT_ID="CHANGE_ME"
export ANTIGRAVITY_OAUTH_CLIENT_SECRET="CHANGE_ME"
```

Keep those values available for token refresh and quota checks. Changing them later invalidates refresh for connections made with the old client. See [Environment variables](../reference/environment.mdx).

## Connect

<Steps>
<Step>
Open **Providers**, then **Antigravity**, then Connect.
</Step>
<Step>
Sign in with Google and approve the scopes. The request asks for offline access, so Google returns a refresh token.
</Step>
<Step>
Google redirects to `http://localhost:<dashboard port>/callback`. If you opened the dashboard on a loopback host, the popup finishes on its own. From any other host, the modal switches to a paste step: copy the full callback URL from the browser (`/callback?code=...`) and paste it back.
</Step>
</Steps>

DurinDoor loads the account's Cloud Code project before saving the connection. If Google has not assigned one, it waits for onboarding and saves the returned project. If onboarding fails or returns no project, the connection is not saved; retry after resolving the account's project setup.

Onboarding is a long-running Google operation, so the sign-in can wait for it. The wait is bounded: `ANTIGRAVITY_ONBOARD_MAX_ATTEMPTS` polls (default 10) with `ANTIGRAVITY_ONBOARD_RETRY_DELAY_MS` between them (default 5000). Lower them if a sign-in should fail faster, or raise them if the account needs more rounds to provision.

## The agy id

`agy` ("Antigravity CLI") uses the same executor, models, quota fetcher, and Google token refresh as `antigravity`, under a separate id. It keeps existing `agy` connections separate from dashboard IDE logins. The dashboard has no Connect flow for `agy`. A legacy DurinDoor `db.json` containing an `agy` connection can be imported by the existing database migration; this is not an import of an Antigravity CLI credential file. Catalog refresh uses the same configured Antigravity OAuth client as request refresh.

## Models

Send `ag/<model>`, for example `ag/gemini-3.8-flash`. Available models include thinking variants and image models; use discovery rather than a fixed count. Image models never stream. `GET /v1/models` shows what your connections actually expose.

The dashboard reads each account's model list from Google using that account's own Cloud Code project, so the list is the one Google reports for the signed-in account rather than a shared default. If Google refuses the credential, or answers with a list DurinDoor cannot read, the provider page keeps the built-in list and shows the failure instead of an empty list. An account whose project was never provisioned is discovered without one; finish onboarding for that account to get its own list.

## Quota

The [Quota Tracker](../features/quota-tracking.mdx) shows one row per model from Cloud Code's available-models call, plus two weekly rows: Gemini Weekly and Claude & GPT Weekly. When Google answers 429 with a reset timestamp or delay, DurinDoor uses that value for the cooldown instead of guessing.

## Errors

| Upstream says | What DurinDoor does |
| --- | --- |
| 503 `MODEL_CAPACITY_EXHAUSTED` or "No capacity available for model" | Treated as Google-side capacity, not an account problem. Falls back to the next account with no cooldown, and sweeps all accounts again up to two times. |
| 403 "has not been used in project", `SERVICE_DISABLED`, `accessNotConfigured` | Treated as a project setup problem. Falls back with no cooldown. Finish onboarding or enable the API in that project. |
| 403 saying the account is disabled, suspended, or in breach of terms | Normal two minute cooldown. Reconnecting will not help. |
| 429 whose error details give the reason `INSUFFICIENT_G1_CREDITS_BALANCE` and no reset time | The Google One AI credit balance is empty. DurinDoor locks the whole account for 24 hours and falls back to the next one. If the refreshed quota already blocks the account, it moves on without adding this lock. |
| Other 429 | Cooldown from Google's reset hint when present, otherwise exponential backoff. |

The project-403 check currently matches `antigravity` and `gemini-cli` only, so an `agy` connection gets the normal cooldown for the same error.

## MITM mode

A separate feature lets the Antigravity IDE itself route through DurinDoor. **CLI Tools** links to **MITM Proxy** (`/dashboard/mitm`), which installs a local root certificate, redirects `cloudcode-pa.googleapis.com` and `daily-cloudcode-pa.googleapis.com` to DurinDoor, and maps the IDE's model names to any DurinDoor model. It needs sudo for the certificate and DNS steps. It does not need an Antigravity connection. Recovery steps for a stuck redirect are on [Troubleshooting](../troubleshooting.mdx#mitm-root-ca-lock-or-redirect-errors).

Confirm a short request on **Usage** after connecting. For an empty-client OAuth error, set both client variables and restart. For project setup errors, finish onboarding or enable the required API. Account suspension cannot be repaired by repeating OAuth.

## Credential rotation

Token refresh for `antigravity` and `agy` shares one database lease. Browser recovery and the automatic scheduler stay off. See [Antigravity rotation](../operations/antigravity-rotation.mdx).
