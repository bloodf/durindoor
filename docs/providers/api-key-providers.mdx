title: API key providers
description: Add vendor credentials, configure Bedrock authentication, and verify provider access.
---

Most paid APIs are API-key providers: OpenAI, Anthropic, Groq, Mistral, DeepSeek, and other providers marked as API-key providers. You paste the upstream secret; DurinDoor stores it on a connection and sends it as `Authorization: Bearer` or the header that provider declares (`x-api-key` for Anthropic-style transports).

Open Dashboard, then Providers, then the provider. Add API Key (or Add Connection) opens the form.

<Steps>
<Step>
Pick the provider card. Providers that support both OAuth and API keys offer both methods on their page.
</Step>
<Step>
Give the connection a name. The dialog fills the first unused name in the `main`, `main-2`, `main-3` sequence. Reopening after a successful add clears secrets and provider-specific fields; a background refresh while the dialog is open does not.
</Step>
<Step>
Paste the key. Cloudflare Workers AI and Snowflake Cortex also require an account id (`name|apiKey|accountId` on bulk lines). Azure wants endpoint, API version, deployment, and optional organization. Google Programmable Search needs `cx`.

For Azure OpenAI (`azure`), an explicit unsupported-token-parameter response triggers one retry with the alternate token-limit spelling. A successful retry is remembered per deployment URL for the life of the process; the output limit is retained, and unrelated errors follow normal account fallback.

A deployment whose name identifies a GPT-5, GPT-6, or o-series model (`gpt-5`, `gpt-6`, `o3`, `o4`, and their versioned forms) is also normalized before the call: `max_tokens` becomes `max_completion_tokens`, a `temperature` other than `1` is dropped, and `reasoning_effort` is dropped when tools are sent. Tools and `tool_choice` are kept. Deployment names are yours to choose, so a name that does not identify one of those models (for example `prod-chat`) is sent unchanged, and the token-limit retry above still applies to it.
</Step>
<Step>
Set priority if you already have another key for this provider. Lower numbers run first under fill-first selection. Optional: default model, proxy pool, per-connection proxy URL.
</Step>
<Step>
Save, then send a request using one of the connection's models. A duplicate provider, credential, and name is rejected with HTTP 409. Validation probes stop after 10 seconds; connection tests stop after 15 seconds.
</Step>
</Steps>

`ollama-local` and other `noAuth` providers may omit the key. OpenAI-compatible nodes also allow a keyless connection when the upstream does not require authentication. See [OpenAI-compatible nodes](./openai-compatible-nodes.mdx).

Bulk add accepts one key per line (`name|sk-key`, or a bare key that gets an auto name). Bulk create is create-only: a name collision never overwrites a saved key.

## TrustedRouter

Add a TrustedRouter API key, then refresh the connection's models. Validation uses
the authenticated key endpoint because its catalog is public. Keep the vendor
prefix in model IDs, such as `trustedrouter/anthropic/claude-sonnet-4.6`.
See [TrustedRouter setup](./trustedrouter.md) for presets and embeddings.

## DemonRoute

Add a DemonRoute API key in Providers, then discover models for that connection. Its `/v1/models` catalog is account-specific; the bundled model list is only an offline starting point. Use the exact, case-sensitive model ID returned by DemonRoute, including its vendor prefix. Model availability and pricing may change. See the [DemonRoute documentation](https://demonroute.com/docs).

## Gisoo

Gisoo ([gisoo.pro](https://gisoo.pro)) is a prepaid, OpenAI-compatible relay. DurinDoor sends chat requests to `https://gisoo.pro/api/v1/chat/completions` with `Authorization: Bearer <key>`; one key covers the whole catalog.

Three details differ from most API-key providers:

- **Model discovery is keyless.** `GET https://gisoo.pro/api/v1/models` is public and answers 200 without a key, so the dashboard fetches the catalog without sending the stored key. The request always targets the built-in Gisoo host, never a per-connection base URL.
- **The connection test uses the account endpoint.** The catalog answers 200 even for a rejected key, so it cannot prove a credential. DurinDoor validates the key against `GET https://gisoo.pro/api/v1/me` instead, which answers 401 for a missing, revoked or expired key.
- **Credit and identity verification are separate failures.** A `402` means the account's credit or its spend cap is exhausted; a `403` that names identity verification means the account spent past the $2 pre-verification allowance and must be verified in the Gisoo app. Both bench the connection for a day and are reported as terminal, so no `Retry-After` is advertised. A rejected key (`401`) instead benches the connection briefly so another key can serve the request.

Gisoo publishes 60 requests per minute per key by default; DurinDoor paces connections to that rate unless you override it in the settings.

## Anthropic API-key requests

For official Anthropic API-key requests, DurinDoor removes the leading Claude Code
system identity and Claude Code beta flag. OAuth requests and third-party gateway
requests retain their existing identity behavior.

## OpenAI completion token limits

For the `openai` provider, DurinDoor sends Chat Completions output limits as
`max_completion_tokens`. Clients may still send `max_tokens`; if both fields
are present, the explicit `max_completion_tokens` value wins and the legacy
field is removed. This also applies to GPT-6-family models when using the Chat
Completions transport. Native Responses requests retain `max_output_tokens`;
this rule does not change the separate Chat-to-Responses translation. Custom
compatible nodes and other providers keep their model-specific normalization.

## Amazon Bedrock credentials

Bedrock is the one API-key provider that accepts three credential shapes. Pick the region where your models are enabled, then fill in exactly one of these in the AWS Credentials block:

| Mode | What you enter | Refresh |
| --- | --- | --- |
| Profile (SSO) | AWS Profile only, API Key left empty | Automatic, the AWS SDK re-resolves the profile |
| Static AWS keys | AWS secret access key in API Key, key id in Access Key ID, Session Token for temporary `ASIA...` keys | None, paste new keys when they expire |
| Bedrock API key | The Bedrock API key in API Key on its own | None |

A profile takes precedence over everything else, and static AWS keys are selected by the presence of an Access Key ID. A connection that only carries an API Key keeps behaving exactly as before.

Profile mode is the recommended path. Name a profile from `~/.aws/config`, save the connection with an empty API Key, then run `aws sso login --profile <name>`. DurinDoor never reads or stores the SSO token: the AWS SDK resolves it from the local token cache on each request and refreshes it on expiry, so the saved connection holds nothing secret. `source_profile` role chaining and `credential_process` profiles resolve the same way. Only the named profile is used: if it is missing or fails to resolve, the request fails with HTTP 401 and never falls back to the server's own AWS credentials (environment variables, ECS or instance role).

Saving a profile-only connection skips the usual API-key requirement, so `POST /api/providers` and the validate probe both accept an empty key. The profile is resolved as the user running DurinDoor, and a profile can run a `credential_process` command, so setting one is limited to operators (the dashboard or the CLI token). An application API key gets HTTP 403 from `POST /api/providers`, `PUT /api/providers/<id>`, and `POST /api/providers/validate` when the request names a profile. A profile name must match `^[A-Za-z0-9_.:-]{1,64}$`; anything else gets HTTP 400.

Check, Test and the health monitor verify profile and static-key connections with a SigV4-signed Converse call that carries no messages. AWS checks the signature before the body, so a `ValidationException` means the credentials work and no inference runs. An `AccessDeniedException` also counts as valid credentials: AWS accepted the key and IAM denied the model. The IAM secret access key is never sent as a bearer token. A Bedrock API key connection keeps the bearer probe.

Temporary AWS keys beginning with `ASIA` require a session token. A missing token is rejected with 401. The session token is encrypted separately and is not returned in provider responses.

When editing, leave the session-token field blank to keep the saved token. Changing or clearing the Access Key ID also clears it. Entering a new API key clears the saved profile after validation. For an expired SSO session, run `aws sso login --profile <name>` again.

## AI Studio Build and hosted Devin via CLIProxyAPI

Run an operator-controlled CLIProxyAPI instance on loopback port 8317. Configure a CLIProxyAPI client key under `access.api-keys`, then add a **CLIProxyAPI** API-key connection under **Providers** using that key. Keep Google and Cognition sign-in within your authorized upstream runtime. The saved connection gives DurinDoor access to the sidecar's OpenAI-compatible models and chat endpoints.

For AI Studio Build, use an app you are authorized to operate and follow the [CLIProxyAPI relay setup](https://github.com/router-for-me/CLIProxyAPIDocs/blob/a9f717ebab81222ad6e947b2b8a16a06aedfddf5/docs/en/configuration/provider/ai-studio.md). On the verified CLIProxyAPI version, keep `oauth.providers.aistudio.ws-auth: true` and configure the app to authenticate to `/v1/ws` with a sidecar client key. Use WSS if the app connects across a network. Keep the app private and protect the relay key and any logs containing its upgrade URL. The relay is available in standalone CLIProxyAPI mode.

Use a unique alias under the `aistudio` channel of CLIProxyAPI's `oauth.model-alias` configuration to select the relay even when another backend serves the same base model. Set `name` to a model that CLIProxyAPI lists while the app is connected and choose an `alias` unused by other upstreams.

```yaml
oauth:
  providers:
    aistudio:
      ws-auth: true
  model-alias:
    aistudio:
      - name: "<model-id>"
        alias: "office-build"
```

In DurinDoor, fetch the connection's models and call `cpa/<alias>` through Chat Completions. DurinDoor reads the sidecar's OpenAI JSON and SSE usage fields through its standard accounting path. After the app disconnects, re-fetch the models. Cached catalogs can retain the last list until refresh.

For hosted Devin, use the exact model ID discovered from CLIProxyAPI, including its `devin/` namespace when present, for example `cpa/devin/<model>`. DurinDoor's Gemini CLI, Devin cloud-agent and Devin CLI connections serve their own transports.

Scope DurinDoor client keys to the intended saved connection. CLIProxyAPI client keys on one instance share its upstream pool. For an isolated upstream account or relay, use a dedicated CLIProxyAPI instance and an independently configured OpenAI-compatible connection with its own base URL and key. Keep the instance reachable only from the clients and app that you authorize.

## DeepSeek DSML tool calls

For OpenAI-format responses from an effective DeepSeek model, DurinDoor converts complete visible DSML invoke frames into structured tool calls, including when a combo selects the model. Streaming frames can span chunks; malformed, incomplete, or oversized frames remain text. Existing structured calls are preserved. The gateway only translates response data and does not execute the calls.

Buffered responses are decoded the same way before they are projected into the format the client asked for, so a JSON reply to Chat Completions, Claude Messages, Gemini or Responses requests carries the tool call instead of the raw frame. The same reply still arrives as a single JSON body.

## DeepSeek thinking history

DeepSeek's thinking mode requires the `reasoning_content` of earlier assistant turns to be sent back with later requests that carry `tools`; omitting it makes the API answer HTTP 400. OpenAI Chat clients usually drop that field, so on the OpenAI Chat wire DurinDoor adds a single-space `reasoning_content` placeholder to every prior assistant message that has none, or has an empty one.

- A non-empty `reasoning_content` that the client already sent is never replaced, and tool calls, tool call IDs, tool results and message order are left as received. The client's own history object is not modified.
- The Anthropic-compatible DeepSeek endpoint carries thinking as `thinking` content blocks with signatures. DurinDoor forwards those blocks unchanged and sends no `reasoning_content` on that transport, including when the transport is selected as `claude-apikey`.
- Another provider that serves a model with the same ID keeps its own endpoint and credentials. On an Anthropic-format transport it never receives `reasoning_content`. On an OpenAI Chat transport, other providers with a `deepseek` model ID receive the same placeholder, as before, because gateways that front DeepSeek enforce the same rule; models with other IDs are untouched.

## Azure resource endpoint

A new Azure connection needs its resource endpoint. Without one, the request would carry your Azure key to a host that is not your resource, so `POST /api/providers` answers HTTP 400.

- `azure-openai` needs `providerSpecificData.baseUrl`. The dashboard form has no field for it yet, so create this connection through the API.
- `azure` needs `providerSpecificData.azureEndpoint`, or `AZURE_ENDPOINT` set on the server.

Saved connections and updates are not checked.

## Env fallbacks

Saved connections are the path you should use. A handful of executors still read process environment when a connection field is empty:

| Variable | Used when |
| --- | --- |
| `OPENAI_API_KEY` | Azure executor, if the connection has no `apiKey` or `accessToken`. Not a generic OpenAI connection. |
| `AZURE_ENDPOINT`, `AZURE_API_VERSION`, `AZURE_DEPLOYMENT`, `AZURE_ORGANIZATION` | Azure URL and headers when `providerSpecificData` omits them. API version default is `2024-10-01-preview`. |
| `GITLAB_DUO_BASE_URL` / `GITLAB_BASE_URL` | GitLab Duo origin; default `https://gitlab.com`. |
| `FIRECRAWL_API_KEY` | Auto-configure for the Firecrawl web-fetch connection. |
| `CLI_DEVIN_BIN` | Override Devin CLI binary discovery. |
| `WINDSURF_API_KEY` | Devin CLI executor, if the connection has no key or token. |
| `CLIPROXYAPI_HOST` / `CLIPROXYAPI_PORT` | CLIProxyAPI listen address. |

OAuth client overrides (`GEMINI_OAUTH_CLIENT_ID`, `ANTIGRAVITY_OAUTH_CLIENT_ID`, and their secrets) belong on [Connecting accounts](./connecting-accounts.mdx). The full operator list is [Environment variables](../reference/environment.mdx).

## Scoping a DurinDoor API key to accounts

A DurinDoor client key (`sk-...`) can be limited to a subset of provider connections. An empty account scope means unrestricted: the key may use every reachable account. Assigning one or more connection ids opts into the restriction. Clearing the list restores the unrestricted default.

Details, deletion guards, and the HTTP shape live in [API key scoping](../operations/api-key-scoping.mdx). Deleting a connection that is the last scoped account for a key is rejected with HTTP 409 `API_KEY_SCOPE_WOULD_BROADEN` so the key cannot silently become unrestricted.

Test a saved key from the provider page. Connection tests stop after 15 seconds. Custom URLs still go through the outbound SSRF guard. Hidden registry providers cannot be created through this form; `POST /api/providers` returns `Invalid provider`.

Priority is per provider. Drag accounts on the provider page to change their order. Fill-first selection then uses that order. See [Connecting accounts](./connecting-accounts.mdx) for how that interacts with account fallback.

Edit Connection does not display the stored secret. To rotate a vendor key, create its replacement at the vendor, update the connection, and verify a request before revoking the old credential.

Proxy fields on the add dialog are optional: `connectionProxyEnabled`, `connectionProxyUrl`, `connectionNoProxy`, and `proxyPoolId`. `__none__` means no pool. A bad pool id is rejected before the connection is written.

`google-pse` requires `cx` (Programmable Search Engine id) in provider-specific data. Without it, create returns 400.

If a probe passes but chat fails, check model entitlement and deployment names. Bedrock `AccessDeniedException` can mean the credentials are valid but IAM denies that model; a passing credential probe does not grant inference permission.

## NVIDIA assistant reasoning history

For NVIDIA NIM, assistant messages use `reasoning_content`. If a client replays
`reasoning` as an alias, DurinDoor removes that duplicate field and keeps an
existing nonblank canonical value. The alias fills a missing, null or blank
canonical value before any DeepSeek reasoning-placeholder handling. User,
system and tool messages are unchanged, as are other providers' existing rules.
This is field normalization, not validation of arbitrary reasoning value types.

## Qoder model queue

When Qoder reports code `10605` (a model queue, not a billing block), DurinDoor polls Qoder's queue-status endpoint and replays with a fresh signature as soon as the status reports that the queue cleared. If the status endpoint errors or returns an unknown response, DurinDoor falls back to the retry delay Qoder supplied (15 to 60 seconds). It stops after 6 inference attempts or `QODER_MODEL_QUEUE_MAX_WAIT_MS` milliseconds (default 180000), whichever comes first, and then returns a retryable `503` with code `qoder_model_queued` so a combo can move on. Billing signatures (`110`, `112`, `pricingUrl`) still return `403` immediately and are never replayed. A closed client connection ends the wait.

### Unverified

- No live Qoder call was made. The `10605` payload shape and queue-status contract are ported from upstream Qoder client behavior; tests use synthetic responses only.

## DeepAI

`deepai` is image-only; DeepAI has no chat endpoint. Requests to `/v1/images/generations` with model `text2img` are sent to `https://api.deepai.org/api/text2img` with the `api-key` header and return the `output_url` image link. Optional `size` (`WIDTHxHEIGHT`, 128 to 1536 in multiples of 32) and `negative_prompt` are forwarded.

API access requires your own DeepAI Pro subscription; DurinDoor does not provide one. DeepAI's asynchronous video routes are not supported yet.

### Unverified

- No live call was made. Requests are sent as multipart/form-data per the DeepAI guide (its JavaScript example sends JSON instead); response and error bodies follow `deepai.org/docs` only.
- DeepAI's resale and redistribution terms were not reviewed. Use your own key for your own requests.

## Pioneer (Fastino)

Pioneer is now Fastino: `api.pioneer.ai` is retired and the API lives at `https://api.fastino.ai/v1`. Create a key at the Fastino dashboard (keys start with `fast_sk_`; legacy `pio_sk_` keys no longer work). The provider lists the decoder models from the Fastino model catalog. GLiNER and GLiDE models need a request `schema` or `/v1/systemone` and are not exposed here.

### Unverified

- No live call was made. Whether `/v1/chat/completions` serves the listed decoder model IDs without a `schema`, and the contents of the authenticated `/v1/models`, are unconfirmed.
- Model IDs and context windows come from `docs.fastino.ai` only.

## Gemini Interactions

In **Dashboard → Providers → Gemini Interactions**, choose **Add API Key** and paste a Google AI Studio API key. Connection validation and model discovery use Google's model list. Discovery shows the supported text subset available to that key.

Send a single text turn to `POST /v1beta/interactions` with your **DurinDoor** key in `x-goog-api-key`. For example:

```json
{"model":"gemini-interactions/gemini-4-hydrogen","input":"Explain how a sundial works.","store":false,"stream":true}
```

Omit `stream` or set it to `false` for JSON. In SSE, read text from `step.delta` and token usage from `interaction.completed`. A provider failure after the stream opens arrives as an `error` event. DurinDoor chooses an eligible Gemini Interactions connection and sends its stored Google key upstream.

The same provider-qualified model works on `POST /v1/chat/completions` with one text-only user message. DurinDoor always sends `store: false`. Interaction IDs identify the current response only. This integration supports foreground creation with text input and output. The existing **Gemini** connection still serves GenerateContent and the Gemini media endpoints.

See the [Google Interactions overview](https://aistudio.google.com/docs/interactions-overview) and [streaming guide](https://aistudio.google.com/docs/streaming).

Mistral Chat requests map `seed` to `random_seed` and `max_completion_tokens` to `max_tokens`, remove unsupported OpenAI-only fields, and cap temperature at 1.5. Explicit Mistral field values take precedence. Unsupported `service_tier` values are normalized or omitted; Responses requests retain their own schema. When an HTTP 400 names `top_k`, as some Mistral models do, DurinDoor retries without it. Model discovery skips Mistral models whose `deprecation` date has passed.
