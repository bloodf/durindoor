Gemini Web (`gemini-web`, alias `gweb`) sends chat requests through your signed-in gemini.google.com session. You supply your own Google cookies once; DurinDoor opens the Gemini page in a headless Chromium with those cookies, types your prompt, and returns the answer the page itself receives. There is no API key and nothing is sent to Google except what the Gemini web app would send for you.

<Callout type="warn">
This drives the consumer Gemini web app, not the Gemini API. It depends on gemini.google.com's page and its private `StreamGenerate` endpoint, which change without notice, and it spends your account's own limits. Your Google cookies are a full login for that account. Use it for a personal gateway, keep it behind scoped DurinDoor keys, and expect Google to rate limit automated use.
</Callout>

## Requirements

- A Google account that is signed in to gemini.google.com in a normal browser.
- Playwright with its Chromium build on the host that runs DurinDoor (`npx playwright install chromium`). A missing browser answers `503` with that instruction and does not count against the connection.
- Optional: `GEMINI_WEB_RESPONSE_TIMEOUT_MS` (1000 to 600000, default 30000) sets how long a request waits for the page's answer.

## Models

| Id | Gemini UI mode |
| --- | --- |
| `gemini-3.1-pro` | The mode gemini.google.com opens to |
| `gemini-3.7-flash` | Flash |
| `gemini-3.1-flash-lite` | Flash-Lite |

The list is curated. Model discovery returns it without a request and without sending a cookie. Your account decides which modes it can actually switch to.

Before anything is typed, DurinDoor switches the page to the requested mode and reads the active-mode indicator back. A mode it cannot confirm is rejected with `400` and `unsupported_control_for_provider` instead of answering under a label that never ran. The page selectors are best-effort guesses at Gemini's markup, so a Gemini UI change can turn a non-default model into that `400` until the selectors are updated; the default `gemini-3.1-pro` needs no interaction.

## Capture the cookies

The session is two cookies on `.google.com`:

| Cookie | Required | Notes |
| --- | --- | --- |
| `__Secure-1PSID` | Yes | The session |
| `__Secure-1PSIDTS` | Yes | Session timestamp; Google rotates it |
| `__Secure-1PSIDCC` | No | Rotates too; kept if you include it |

Any other cookie in the import is rejected by the dashboard and extension contract. A pasted connection test accepts a Cookie header with extra cookies and uses only what the page needs.

### Cookie capture extension

With the [cookie capture extension](./cookie-capture-extension.mdx) paired to your gateway, open the **Gemini Web** entry while signed in to gemini.google.com and send the session. The extension reads only the two approved cookie names for `https://gemini.google.com`.

### Dashboard import

On **Providers**, choose **Gemini Web** and add a connection. Any of these can be pasted:

- the full `Cookie` request header from a gemini.google.com request, with or without the `Cookie:` prefix
- a copied cURL command for such a request
- a HAR file saved from DevTools, read locally in the browser
- a bare `__Secure-1PSID` value, or browser-export JSON such as `{"cookies":{"__Secure-1PSID":"...","__Secure-1PSIDTS":"..."}}`

To copy the header by hand: sign in at gemini.google.com, open DevTools, Network, reload, select a request to `gemini.google.com`, and copy the `Cookie` request header value. The Application tab shows the same cookies but can be stale.

### Check the session

The **Check** button makes one read-only `GET https://gemini.google.com/app` with the pasted cookies and does not follow redirects. A signed-in page carries a `SNlM0e` token, which is the only thing that counts as valid: a signed-out landing page also answers `200` to a junk cookie. A redirect to `accounts.google.com/ServiceLogin` is an expired session. `401` or `403` is a rejected credential. `429` and `5xx` are reported as unavailable, not as a bad cookie. No conversation is created.

## What it does

- **Isolation.** One Chromium process is shared, but every request gets a fresh browser context with that connection's cookies and closes it afterwards. Two connections never share a page or a cookie jar. The process closes after 60 seconds idle.
- **Conversation.** Each request is a new Gemini chat. The history in `messages[]` is flattened into one prompt (`System:`, `Previous conversation:`, `Current user message:`), so follow-ups keep context without a stored conversation id.
- **Streaming.** Gemini's `StreamGenerate` answers one body of cumulative snapshots. DurinDoor keeps the last snapshot and replays it as one content chunk, a `stop` chunk and `[DONE]`. `stream: true` therefore delivers the whole answer at once. The Anthropic Messages route translates the same chunks into Messages events.
- **Rotation.** Google rotates `__Secure-1PSID*` while a session is open. When it does, the new values are written back to the connection. Other cookies are never stored.
- **Tools.** Native function calling is not available. Tools are prompt-emulated: the model is asked to answer with a `<tool>{...}</tool>` block, which is parsed into `tool_calls`. A malformed block stays plain text.

## Errors

| Status | Cause | What to do |
| --- | --- | --- |
| `401` | No cookie, a redirect to the Google sign-in page, or a `401` from `StreamGenerate` | Capture the cookies again |
| `403` | Google rejected the session | Capture the cookies again; check the account |
| `429` | Account usage limit or Google rate limit | Wait, or route to another connection |
| `400` | A forced `tool_choice` (`required`, `any`, a named function), an unconfirmed model mode, `reasoning_effort` above `minimal` that the page cannot confirm, or no readable user message | Remove the control or change the model |
| `499` / `504` | The client cancelled, or the request timed out | Retry |
| `502` | `StreamGenerate` never answered, or answered a body that could not be read | Retry; the error body lists the endpoints the page called |
| `503` | Chromium is not installed | Run `npx playwright install chromium` |

## Limits

- Images, files, audio and other attachments are not sent. A message whose content has any non-text part is dropped from the prompt, and a request with no readable user message answers `400`.
- No token usage is reported; `usage` is zero.
- No reasoning content. `reasoning_effort` above `minimal` tries to turn on Gemini's Extended Thinking and is rejected if it cannot be confirmed.
- Per-account limits, plan features and regional availability are Google's, and DurinDoor does not verify them.
- Each request launches a browser context, so latency is higher than an API provider.
