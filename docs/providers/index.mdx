---
title: Providers
description: Provider, connection, and provider node, plus the pages that cover each credential path.
---

A provider is a registry upstream such as OpenAI, Claude Code, or Ollama Local. A connection is one saved credential for that provider; you can keep several and DurinDoor will try another account when the current one fails. A provider node is a custom OpenAI-compatible or Anthropic-compatible endpoint you add yourself, with its own prefix and base URL.

Open Dashboard, then Providers. Registry cards group OAuth, API key, cookie, free, and custom nodes. Account fallback stays on the same provider and model; combo fallback is a different chain.

| Term | Meaning |
| --- | --- |
| Provider | A registry id (`openai`, `claude`, `ollama-local`) or a node id (`openai-compatible-chat-...`). |
| Connection | One credential row: OAuth tokens, API key, or cookie. Priority decides fill-first order. |
| Provider node | A user-added OpenAI-compatible, Anthropic-compatible, or embedding endpoint. |
| Account fallback | Next connection for the same provider and model after a fallback-worthy error. |
| Combo fallback | Next model in a combo after every account for the current member has failed. |

| Credential | Typical providers | Where it is documented |
| --- | --- | --- |
| OAuth | Claude Code, Codex, Gemini CLI, GitHub | [Connecting accounts](connecting-accounts.mdx) |
| Cookie | ChatGPT Web and other `webCookie` ids | [Connecting accounts](connecting-accounts.mdx) |
| API key | OpenAI, Anthropic, Groq, Azure | [API key providers](api-key-providers.mdx) |
| Compatible node | Your own `/v1` gateway | [OpenAI-compatible nodes](openai-compatible-nodes.mdx) |
| Local / no-auth | Ollama, LM Studio, Horde | [Free and local](free-and-local.mdx) |

Cards on the Providers page are the add surface. Hidden registry ids do not appear there and `POST /api/providers` rejects them. Custom OpenAI and Anthropic nodes are the two buttons at the top of that page. Embedding-only nodes sit under Media providers.

The generated catalog is the id list for the build you are running. `GET /v1/models` is what clients should use once connections exist.

OAuth and cookie flows are on Connecting accounts. Pasting a vendor key, including Azure and Cloudflare account ids, is on API key providers. Custom base URLs are OpenAI-compatible nodes. Ollama, LM Studio, Horde, and local TTS are Free and local. Self-hosted vLLM-style ids and the metadata-only `auto` / `zed` / `codex-cloud` rows are Local router providers.

```text
Client: openai/gpt-4.1
Account A rate limited -> account B, same model
Both OpenAI accounts fail -> combo may try the next model
```

DurinDoor listens on `http://localhost:20128` in production. The Providers UI is `/dashboard/providers`. Media embeddings are under `/dashboard/media-providers`.

Hidden registry ids stay routable if a connection already exists, but they are not in the add selector. The catalog page is generated by `npm run gen:provider-catalog` from `open-sse/providers/registry/` (every module except `index.js`).

Multiple connections on one provider are the fallback unit. Priority is the fill-first order. Round-robin is optional. A DurinDoor client key can be scoped to a subset of those connections; see API key providers.
