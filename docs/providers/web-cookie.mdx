title: Web cookie providers
description: Copy the correct browser session value, check provider support, and recover expired sessions.
---

A web cookie provider reuses the session your browser already has with a chat website. There is no API key. You copy the cookie the site sets after you sign in, paste it into DurinDoor, and DurinDoor sends it the way the web app would.

On **Providers**, web-session connections have their own group. Some cards can store credentials before their request executor is available; check the supported status below before configuring a client.

<Callout type="warn">
A session cookie is a full login for that account. Anyone who can send requests through your gateway can spend that session. Keep cookie providers on a personal install, or put them behind scoped DurinDoor keys. See [API key scoping](../operations/api-key-scoping.mdx).
</Callout>

## Sign in from the dashboard

For **Grok Web** (`grok-web`), **Perplexity Web** (`perplexity-web`), **ChatGPT Web** (`chatgpt-web`), **HuggingChat** (`huggingchat`), and **Muse Spark Web** (`muse-spark-web`), the Add dialog offers **Sign in in-page** alongside manual cookie paste. Claude Web, Doubao Web, Z.ai Web, ChatGPT Web Codex and Gemini Web declare the same sign-in profile; Google single sign-on rarely completes in an embedded page, so use import or the extension for Gemini Web.

Sign in inside the embedded page, or choose **Open in popup** if embedding fails. Each popup receives a fresh, one-time bootstrap grant for the same login session; it does not reuse the iframe's grant. The dashboard polls every two seconds and displays captured cookie **names**, never their values. Once the session is ready, enter a connection name and choose **Save connection**. Cancel, closing the modal, or leaving the page discards the login session. Sessions expire after 15 minutes. Signing in does not add an executor for a provider that is not yet runnable.

Saving rechecks the exact provider/operator-bound session after readiness and immediately before the database commit. Cancellation, expiry, or a replacement login before that commit prevents an in-flight save from storing cookies.

### Isolated login origin

The operator must configure `DURINDOOR_WEB_LOGIN_ORIGIN`, for example `https://login.gateway.example`, and route that hostname to the same DurinDoor server. Use a dedicated hostname different from the dashboard's hostname: a different port alone does not isolate cookies. The flow fails closed if the origin is missing, invalid, or shares the dashboard cookie hostname; there is no same-origin fallback.

The dedicated origin keeps login cookies separate from dashboard authentication and serves only sign-in traffic. Use HTTPS. If browser cookie rules or a provider login block the embedded page, use the popup or manual paste. MiMo keeps its existing login flow.


Cloudflare Turnstile, Google SSO, third-party cookies, cross-origin redirects, or other site protections may reject reverse-proxied login, including in a popup. Use manual cookie paste in that case. The flow captures upstream HTTP cookies, not localStorage tokens; only the five providers listed above support this dashboard login. Cookie capture and readiness are not a guarantee that the provider will accept every later chat request.

## Copy the cookie

Copy from a live request, not from the cookie storage view. The storage view can show stale values, and it can miss cookies the site only sends on signed-in requests.

<Steps>
<Step>
Sign in to the site in a normal browser window and open a chat so the session is active.
</Step>
<Step>
Open developer tools, then the Network tab. Reload the page and click a request to the site's own domain.
</Step>
<Step>
Under Request Headers, copy the `Cookie` value. Some providers only want one named cookie from that header; the table below says which.
</Step>
<Step>
In DurinDoor open **Providers**, pick the cookie provider, and click Add. The field is labelled **Cookie Value**. The hint under it is the provider's `authHint`.
</Step>
<Step>
Paste and save. Model chat probes for web-cookie LLM providers are skipped and shown as "Skipped", not failed. Validate and Test Connection also skip `grok-web`, `copilot-web`, `zenmux-free`, `suno` and `udio`: their chat or music endpoints create a real conversation or generation per probe, risking account restrictions or spending credits. Saving or editing those cookies leaves connection status unknown until a real request runs; batch results count skips separately from passes. ZenMux still checks for `ctoken` locally before skipping. `perplexity-web` uses a read-only session check.
</Step>
</Steps>

You can paste the whole header or just the value. DurinDoor strips a leading `Cookie:` or `Bearer `, and pulls a single named cookie out of a full header when the provider only needs one.

The field is plain text, not a password field, so the cookie is visible on screen while you type. Once saved, the value is stored in the connection's encrypted `apiKey` column like any other secret.

### Chunked session cookies

chatgpt.com and perplexity.ai keep their session in a NextAuth cookie, `__Secure-next-auth.session-token`. When the session grows past about 4KB, NextAuth splits it into `__Secure-next-auth.session-token.0`, `.1`, and so on, each holding a different part. Copy every chunk: pasting the whole Cookie header from the Network tab is the easy way. DurinDoor sends the chunks back under their own names in index order, never joined into one value, and drops a stale unchunked cookie if the header has both. Other cookies in the paste, such as `cf_clearance`, are kept.

These cookies are `HttpOnly`, so no page script can read them. For ChatGPT Web the add dialog also offers a console snippet that prompts for each chunk value you copy from Application, Cookies, and puts the joined `name=value` string on your clipboard.

HuggingChat and Muse Spark Web dispatch only when **Allow session dispatch** is enabled on the connection serving the request; otherwise they return HTTP 501 with `type: "provider_port_pending"`. Muse Spark Web also needs the gateway's headless browser for its token flow. Suno and Udio chat requests return the same HTTP 501 error, while both run on `POST /v1/music/generations`; see [Suno and Udio](#suno-and-udio). ChatGPT Web has a working browser transport with an HTTP fallback; see its [setup guide](./chatgpt-web.mdx). Adapta Web, T3 Chat Web and Tencent Yuanbao Web have their own executors and are documented below. See [Hidden and retired providers](./retired.mdx) for unsupported entries.

## Import cookies in the dashboard

ChatGPT Web, ChatGPT Web Codex, Claude Web, Gemini Web, Doubao Web, Z.ai Web, MaxAI, Arena, ChatPlayground, PromptQL, Notion AI Web, NoTrack Web, Tencent AI Studio Web, Blackbox Web, Conol Web, Perplexity Web, Grok Web, Muse Spark Web, Tencent Yuanbao Web and Adapta Web offer **Import cookies** next to **Add Connection**. TinyCMS Web offers the same button for its local storage value, with a pasted field instead of a Cookie header. You can also paste credentials in the add dialog.

The import dialog offers three sources and one handover. Its cURL parser only reads request URL and cookie data; it never executes a command or contacts the named site. Example syntax uses synthetic credentials only:

- **Paste header or cURL.** Paste a raw `Cookie` header or a cURL command copied from the browser. For example, `curl 'https://grok.com/' -H 'Cookie: sso=synthetic-session-value'`. The input is read as data in the page: the command is never run, and the URL it names is never requested. This example is synthetic; never paste a real credential into docs or issue reports.
- **HAR file.** Choose a `.har` file from the machine. The file is parsed in the page and never uploaded. Only requests to the provider's own origin are read, and only the provider's approved cookie names are kept; requests to any other origin are ignored.
- **Browser extension.** Create a one-use pairing and hand it to the extension, which then sends the session itself. See [Import from a browser extension](#import-from-a-browser-extension).

Choose a target first: a **new connection** with a name, or an existing cookie connection whose cookies are replaced.

The dialog shows what it found before anything is sent: the request URL, the cookie **names**, and the names it ignored. A cookie value is never displayed and never appears in a message. When a HAR file holds several requests to the provider origin with different credentials, the dialog asks which one to import; requests that carry the same credentials are not ambiguous.

Chunked session cookies keep every chunk. A stale unchunked copy is dropped, and a missing chunk is refused before the import, because an incomplete session token would fail later. A pasted header names no origin, so it is imported as the provider's own origin.

The pasted text, the parsed cookies and the pairing secret are dropped from the page as soon as the operator submits or dismisses the dialog.

The import goes through the same API the browser extension uses, so the provider's origin and cookie allowlist are enforced by the server as well, and the stored value is the same encrypted cookie header as a manual paste.

## Import from a browser extension

See the dedicated [cookie capture extension guide](./cookie-capture-extension.mdx) for installation, privacy and limitations.

A browser extension can send a signed-in session to DurinDoor instead of you pasting it. It works for ChatGPT Web, ChatGPT Web Codex, Claude Web, Gemini Web, Doubao Web, Z.ai Web, MaxAI, Arena, ChatPlayground, PromptQL, Notion AI Web, NoTrack Web, Tencent AI Studio Web, Blackbox Web, Conol Web, Perplexity Web, Grok Web, Muse Spark Web and Tencent Yuanbao Web, and reads TinyCMS Web's `app-config-uuid` local storage value. DeepSeek Web stores its token in local storage too, but the extension has no profile for it, so paste it manually. Adapta Web supports dashboard import from the Clerk origin. HuggingChat uses its existing full-header sign-in or manual paste.

1. In the dashboard, an operator asks for a pairing for one provider, either for a new named connection or for one existing cookie connection. The pairing secret is shown once and expires after two minutes. The provider page's **Import cookies** dialog creates the pairing in its **Browser extension** tab and shows the secret, the import URL and the approved cookie names.
2. The extension sends the provider's approved cookies, the exact provider origin and that secret to `/api/providers/cookie-import`, in the `x-durindoor-pairing-token` header.

The secret works once, only for that provider and target, and only on that route; it is not an API key. Pair again after any failed attempt. The call must use HTTPS, except to `localhost`, `127.0.0.1` or `[::1]` for local development, and the body is limited to 32 KiB. Cookies the provider does not approve, such as `cf_clearance`, are rejected. DurinDoor checks the shape of the cookies and does not contact the provider, so use **Validate** afterwards. Replacing the cookie on an existing connection clears a pending sign-in-again state. The pairing is kept in server memory, so run a single DurinDoor process behind the address the extension uses.

### Install the extension

The extension lives in `extensions/provider-cookie-capture` and has no build step. In a Chromium browser open `chrome://extensions`, turn on Developer mode, choose **Load unpacked** and select that folder. To keep a copy, run `node scripts/package-cookie-extension.mjs`: it writes a zip and a `.sha256` file that are byte-identical for the same sources. Unpack the zip and load the folder the same way.

To use it, create a pairing as an operator, sign in to the provider in a tab, open the extension on that tab and paste the pairing. It shows the provider, the provider site and your dashboard address. Tick the confirmation and choose **Send cookies**. The browser then asks to let the extension read cookies for those two sites only, and the extension removes the temporary access when it finishes. The extension is a local unpacked MV3 extension; install it only in a Chromium profile you control. Its one-use pairing is created in the dashboard for a provider and target, expires after two minutes, and is not reusable. The extension does not capture automatically: you must open it on the signed-in provider tab, review provider and dashboard names, confirm, and send. It never runs on its own, keeps no copy of the cookies and makes one request. If a permission is denied, the pairing has expired or the dashboard rejects it, create a new pairing and try again. See the [extension README](https://github.com/bloodf/durindoor/blob/main/extensions/provider-cookie-capture/README.md) for its permissions and limits.

## Validation

**Validate** posts to `/api/providers/validate` with a 10 second limit. Grok Web, Copilot Web, ZenMux Free, Suno, Udio, Adapta Web, Doubao Web, Z.ai Web, NoTrack Web and Tencent Yuanbao Web skip network validation (so do HuggingChat and Muse Spark Web, to avoid creating a conversation) rather than creating a conversation or generation; this does not prove the cookie works. ZenMux Free still rejects a pasted cookie missing `ctoken` locally. Perplexity Web, ChatGPT Web, ChatGPT Web Codex, Claude Web (organization list), Gemini Web (signed-in page check), MaxAI (config request), Arena (a method check on its chat route, since the site has no session endpoint) and ChatPlayground (user request), Notion AI Web (workspace and model list), Tencent AI Studio Web (`GET /api/user/info`, unverified), Blackbox Web (`/api/auth/session`), Conol Web (`/api/agent-servers`) and PromptQL (project-token request) use read-only session requests; TinyCMS Web asks for a signed challenge with its device UUID; DeepSeek Web reads its `users/current` endpoint with the token; an expired or incomplete ChatGPT Web cookie (such as a missing `.1` chunk) fails with a message asking for every chunk. T3 Chat Web uses a read-only `HEAD` request against the site root: a 401 or 403 rejects the session, and a redirect or a transport failure reports the check as unavailable. Microsoft 365 Copilot Web checks locally that both fields are present, the host is allowed and the token has not expired. Copilot Web reports an expired JWT token locally; any other paste stays skipped. Kimi Web calls the site's model list endpoint with the access token. A provider with no probe answers `Provider validation not supported`.

A passing probe means the site accepted the cookie at that moment. It does not keep the session alive.

## Limits

- Tool calling is usually off. Kimi Web, for example, declares `tools: false` for every model. Use an API or OAuth provider when your client needs tools.
- The model list is whatever the registry declares for that site, and the site can change or drop models without notice.
- These providers do not report quota to the [Quota Tracker](../features/quota-tracking.mdx). For Grok Web, ChatGPT Web, ChatGPT Web Codex, Claude Web, Gemini Web, Doubao Web, Z.ai Web, MaxAI, Arena, ChatPlayground, PromptQL, Notion AI Web, NoTrack Web, Tencent AI Studio Web, Blackbox Web, Conol Web, Kimi Web, Perplexity Web, ZenMux Free, Suno, Udio, Adapta Web and T3 Chat Web and Tencent Yuanbao Web the **Usage** card shows only what DurinDoor itself recorded for that saved session in the last 30 days (requests, estimated tokens, per model). It is not your subscription's remaining allowance, which none of these sites exposes through a stable API. Music jobs show as requests with no tokens; Suno clip durations are kept in the usage ledger, not on the card. Token counts are estimates of about four characters per token.

## Revocation and expiry

A saved cookie remains usable until the provider rejects it or it is replaced; DurinDoor does not revoke a provider session when you delete a connection. To revoke it, sign out or use the provider account’s session/security controls, then remove the DurinDoor connection. If that site offers a “sign out all sessions” or session-revocation control, use it after a suspected leak. Revocation and expiry are provider-controlled and may take time to propagate. Do not assume deleting a local connection invalidates a copied cookie.

Most providers do not expose a reliable expiry time. A failed read-only check, a 401/403 on a real request, or an expired local JWT indicates that a fresh sign-in may be needed. A skipped validation or a request blocked by a provider's opt-in guard does not confirm validity. Replace an expired credential by editing that connection with a newly captured value; this preserves its name and settings and clears its cooldown. Kimi can refresh an access token only when its refresh token was included; see [Kimi Web](./kimi-web.mdx#refresh). ChatGPT Web may persist cookie rotation from its browser transport; see [its account guide](./chatgpt-web.mdx#session-lifecycle-and-recovery).

## When the session ends

Most cookie sessions have no proactive refresh or expiry tracking. ChatGPT Web can save cookies rotated by the site, but rotation does not prevent expiry or revocation. The temporary dashboard-login jar discards expired cookies before saving. Kimi Web is the exception: with a refresh token in the paste, it renews its access token on a 401 (see [Kimi Web](./kimi-web.mdx#refresh)). A 401 or 403 from upstream puts that connection on the normal two minute cooldown and the request moves to the next connection or combo member. The connection stays active, so the same rejection repeats after the cooldown.

If automatic recovery fails, sign in to the site again, copy a fresh cookie, and paste it over the old one with **Edit**. Saving a new cookie on a web-cookie connection replaces the stored value, keeps the connection's name, priority and settings, and clears the cooldown and error state recorded against the old cookie, so the next request uses the new one right away. Other connections of the same provider are not touched. Pasting the same value again changes nothing. Signing out of the site in your browser usually kills the session DurinDoor holds too.

Keep one browser profile for the account you hand to DurinDoor, and avoid signing out of it.

After saving a supported session, send one short request and check **Usage**. A skipped validation is not a successful probe. HTTP 501 `provider_port_pending` means no credential change can enable that provider in this build.

### Copilot Web sessions

Copilot Web (`copilot-web`, alias `copilot`) and Microsoft 365 Copilot Web (`copilot-m365-web`, alias `m365copilot`) are separate providers. Their credentials, accounts and transports never mix: a personal token is only sent to `copilot.microsoft.com`, a Microsoft 365 token only to the `substrate.office.com` Chathub socket, and a model such as `m365/copilot-m365` is never served from a personal connection. Neither provider can read or emulate browser attestation; DurinDoor only replays the session you paste.

#### Copilot Web (personal)

1. Sign in at `copilot.microsoft.com` and send one message.
2. In developer tools, Network, pick a request to `copilot.microsoft.com` and copy the `access_token` (from the `Authorization: Bearer` header or the cookie). A HAR export of that session also works; only requests to the exact `https://copilot.microsoft.com` origin are read.
3. Add **Copilot Web** under Providers and paste. Accepted forms: the bare token, `Bearer <token>`, a cookie string containing `access_token=`, a JSON object with `access_token` (and optionally the exact origin), or a HAR. The pasted text is saved unchanged.
4. Send one short request. Validate and Test Connection do not start a conversation and report **Skipped**. The one exception is a token that is a JWT whose `exp` has passed: that is reported as expired without any request.

Each request starts a fresh conversation. Responses stream as SSE or return as one JSON body; token counts are estimated by the gateway, not reported by Copilot. Model discovery is the static catalog (`copilot-pro`, `gpt-4-turbo`, `gpt-4`); there is no per-connection model fetch. Quota and usage are not reported by the provider.

#### Microsoft 365 Copilot Web

1. Sign in at `m365.cloud.microsoft/chat` and send one message.
2. In developer tools, Network, filter by WS and open the Chathub connection (`wss://substrate.office.com/m365Copilot/Chathub/<oid>@<tenant>?...`).
3. Paste one of: `access_token=<jwt>; chathubPath=<oid>@<tenant>` (alias `userTenant=` is accepted), the full WebSocket URL, or a HAR export. From a HAR, the newest `wss://substrate.office.com` Chathub entry is used; other hosts and redacted tokens are skipped. The credential is not a cookie. Other hosts are rejected.
4. Validate checks locally that both fields are present, the host is allowed and the JWT has not expired. It opens no socket. Set `providerSpecificData.tier` to `work` or `enterprise` for the work profile; `edu` or `included` select the education profile. Individual accounts keep the defaults.

If a Microsoft 365 stream rewrites text already sent, the stream reports an error. Retry without streaming to receive the final snapshot. Token counts are estimated by the gateway.

#### Known limits

- Neither provider refreshes. Manual tokens are short lived (Microsoft 365 tokens last roughly an hour); native work/school sign-in, refresh tokens, conversation continuation, images and tools for Microsoft 365 are not implemented here.
- Personal Copilot may send a proof-of-work `challenge` frame. DurinDoor answers only the bounded hashcash form and fails the request otherwise; it does not attempt any other attestation.
- Copilot does not report quota, so these providers have no preflight or usage gauge.
- Opaque tokens that are not JWTs are not judged locally; expiry shows up as a provider 401.

#### Recovery

A 401 or 403 (including a rejected WebSocket upgrade) puts that connection on the normal two minute cooldown and the request moves to the next account, never reusing the rejected token. A locally detected expired JWT returns 401 without contacting Microsoft. To recover, capture a fresh credential as above and paste it over the old one with **Edit** on the connection (or add a new connection). Saving a replacement credential on a web-cookie connection clears its error status, cooldown and model locks, so the next request uses the new token immediately.

## Grok Web

`grok-web` (alias `gw`) sends chat requests to `grok.com` with your signed-in `sso` session. It is separate from the `xai` API provider and the Grok CLI device flow; their credentials do not work here.

1. Sign in at grok.com. In DevTools, Application, Cookies, `https://grok.com`, copy the `sso` value. Or copy the whole `Cookie` request header from the Network tab.
2. In **Providers → Grok Web**, paste it and save. Accepted forms: the bare value, `sso=<value>`, or a full header. A full header is sent as pasted and must contain `sso=`; a header without it is rejected locally with HTTP 401 and nothing is sent to grok.com. An `sso` with no value, such as a pasted `sso=` or a header whose `sso=` entry is empty, is an empty session and is rejected the same way: HTTP 401 locally, and no request to grok.com. A raw token that merely ends in `=` padding, such as `tok==`, is kept as the `sso` value.
3. **Validate** and **Test Connection** are skipped for Grok Web. Its only chat endpoint creates a conversation per probe, so a skipped result does not prove the cookie works. Send one short request to confirm.
4. Models are the registry list (`grok-3` to `grok-4.2`); unlisted ids pass through and map to `grok-4.1-fast` when DurinDoor has no mapping for them. The same session answers Chat Completions, Messages and Responses clients, with JSON or streaming. Tools and image generation are not supported.

Recovery: HTTP 401 or 403 means the session expired (message: re-paste your `sso` cookie); 429 means grok.com is rate limiting you. With more than one Grok Web connection the request falls back to the next one. To recover a connection, paste the fresh cookie with **Edit** as above. Signing out of grok.com in that browser profile ends the session.

Known limits: no cookie rotation is written back (unlike ChatGPT Web), so a renewed `sso` must be pasted by hand. Paired `sso-rw` handling beyond forwarding it from a pasted header is untested. DurinDoor does not emulate browser attestation or work around access controls; if grok.com challenges a session, use a different session or provider.

## Suno and Udio

`suno` and `udio` are music providers, not chat providers. A chat request to either returns HTTP 501 (`provider_port_pending`). They run through the music routes with the saved session cookie.

1. Sign in at suno.ai or udio.com and copy the session `Cookie` header from a request to the site's API in the Network tab.
2. In **Providers**, pick Suno or Udio, paste it and save. Each saved connection keeps its own cookie. The dashboard credential format is unchanged.
3. **Validate** and **Test Connection** are skipped. The only generic probe would submit a generation and could spend credits, so a skipped result does not prove the cookie works.
4. Discover models with `GET /v1/models/music`. They are not listed by `GET /v1/models`. Suno ids are `chirp-fenix`, `chirp-crow`, `chirp-v4` and `chirp-v3-5`; Udio is `udio-default`.
5. Submit with `POST /v1/music/generations` (or `/v1/audio/music`) using a stored DurinDoor API key. The JSON body takes `model`, `prompt` and optional `instrumental`, `title`, `tags`, `lyrics`, `duration`. The answer is `status: "submitted"` with a `request_id` (the clip or track ids, comma separated) and an `x-9router-connection-id` header naming the account that took the job.
6. Poll with `GET /v1/music/generations/{request_id}`, the same API key, and that connection header. The status moves from `submitted` to `completed` (or `failed`). Suno clips that are `streaming` count as still pending; Udio is complete only when every track is finished. A completed job returns audio URLs, is recorded once in usage, and later polls replay the stored result without contacting the provider.

Account boundaries: a job is bound to the connection and API key that created it. Polling with another key, another connection, or an id DurinDoor never accepted answers 404, and polling never moves to a sibling account.

Recovery: a 401 or 403 on submit cools that connection down and the submit falls back to the next Suno or Udio connection. A 401 on a poll is returned to you as is, because the job exists only on the account that created it; the job stays open. Paste a fresh cookie with **Edit** and poll again with the same connection id: the poll uses the new cookie.

Known limits: no expiry time or refresh flow is known for either site, so the first sign that a session ended is a 401. DurinDoor has no timeout for a job: a poll that keeps answering `submitted` has to be abandoned by the client. Both are unofficial cookie integrations whose request shapes can change without notice. No attestation is emulated and no access control is bypassed; a session the site refuses has to be replaced.
