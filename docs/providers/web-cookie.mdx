---
title: Web cookie providers
description: Copy the correct browser session value, check provider support, and recover expired sessions.
---

A web cookie provider reuses the session your browser already has with a chat website. There is no API key. You copy the cookie the site sets after you sign in, paste it into DurinDoor, and DurinDoor sends it the way the web app would.

On **Providers**, web-session connections have their own group. Some cards can store credentials before their request executor is available; check the supported status below before configuring a client.

<Callout type="warn">
A session cookie is a full login for that account. Anyone who can send requests through your gateway can spend that session. Keep cookie providers on a personal install, or put them behind scoped DurinDoor keys. See [API key scoping](../operations/api-key-scoping.mdx).
</Callout>

## Sign in from the dashboard

For **Grok Web** (`grok-web`), **Perplexity Web** (`perplexity-web`), **ChatGPT Web** (`chatgpt-web`), **HuggingChat** (`huggingchat`), and **Muse Spark Web** (`muse-spark-web`), the Add dialog offers **Sign in in-page** alongside manual cookie paste.

Sign in inside the embedded page, or choose **Open in popup** if embedding fails. Each popup receives a fresh, one-time bootstrap grant for the same login session; it does not reuse the iframe's grant. The dashboard polls every two seconds and displays captured cookie **names**, never their values. Once the session is ready, enter a connection name and choose **Save connection**. Cancel, closing the modal, or leaving the page discards the login session. Sessions expire after 15 minutes. Signing in does not add an executor for a provider that is not yet runnable.

Saving rechecks the exact provider/operator-bound session after readiness and immediately before the database commit. Cancellation, expiry, or a replacement login before that commit prevents an in-flight save from storing cookies.

### Isolated login origin

The operator must configure `DURINDOOR_WEB_LOGIN_ORIGIN`, for example `https://login.gateway.example`, and route that hostname to the same DurinDoor server. Use a dedicated hostname different from the dashboard's hostname: a different port alone does not isolate cookies. The flow fails closed if the origin is missing, invalid, or shares the dashboard cookie hostname; there is no same-origin fallback.

The dedicated origin keeps login cookies separate from dashboard authentication and serves only sign-in traffic. Use HTTPS. If browser cookie rules or a provider login block the embedded page, use the popup or manual paste. MiMo keeps its existing login flow.


Cloudflare Turnstile, Google SSO, third-party cookies, cross-origin redirects, or other site protections may reject reverse-proxied login, including in a popup. Use manual cookie paste in that case. The flow captures upstream HTTP cookies, not localStorage tokens; only the five providers listed above support this dashboard login. Cookie capture and readiness are not a guarantee that the provider will accept every later chat request.

## Copy the cookie

Copy from a live request, not from the cookie storage view. The storage view can show stale values, and it can miss cookies the site only sends on signed-in requests.

<Steps>
<Step>
Sign in to the site in a normal browser window and open a chat so the session is active.
</Step>
<Step>
Open developer tools, then the Network tab. Reload the page and click a request to the site's own domain.
</Step>
<Step>
Under Request Headers, copy the `Cookie` value. Some providers only want one named cookie from that header; the table below says which.
</Step>
<Step>
In DurinDoor open **Providers**, pick the cookie provider, and click Add. The field is labelled **Cookie Value**. The hint under it is the provider's `authHint`.
</Step>
<Step>
Paste and save. Model chat probes for web-cookie LLM providers are skipped and shown as "Skipped", not failed. Validate and Test Connection also skip `grok-web`, `copilot-web`, `zenmux-free`, `suno` and `udio`: their chat or music endpoints create a real conversation or generation per probe, risking account restrictions or spending credits. Saving or editing those cookies leaves connection status unknown until a real request runs; batch results count skips separately from passes. ZenMux still checks for `ctoken` locally before skipping. `perplexity-web` uses a read-only session check.
</Step>
</Steps>

You can paste the whole header or just the value. DurinDoor strips a leading `Cookie:` or `Bearer `, and pulls a single named cookie out of a full header when the provider only needs one.

The field is plain text, not a password field, so the cookie is visible on screen while you type. Once saved, the value is stored in the connection's encrypted `apiKey` column like any other secret.

### Chunked session cookies

chatgpt.com and perplexity.ai keep their session in a NextAuth cookie, `__Secure-next-auth.session-token`. When the session grows past about 4KB, NextAuth splits it into `__Secure-next-auth.session-token.0`, `.1`, and so on, each holding a different part. Copy every chunk: pasting the whole Cookie header from the Network tab is the easy way. DurinDoor sends the chunks back under their own names in index order, never joined into one value, and drops a stale unchunked cookie if the header has both. Other cookies in the paste, such as `cf_clearance`, are kept.

These cookies are `HttpOnly`, so no page script can read them. For ChatGPT Web the add dialog also offers a console snippet that prompts for each chunk value you copy from Application, Cookies, and puts the joined `name=value` string on your clipboard.

Some of these ids exist in the registry before their executor does. A request to one of them returns HTTP 501 with `type: "provider_port_pending"` and names the missing piece. In this build that covers `adapta-web`, `huggingchat`, `muse-spark-web`, `suno`, `t3-web`, `udio`, and `yuanbao-web` for chat requests. `suno` and `udio` do run on `POST /v1/music/generations`; see [Suno and Udio](#suno-and-udio). ChatGPT Web has a working browser transport with an HTTP fallback; see its [setup guide](./chatgpt-web.mdx). See [Hidden and retired providers](./retired.mdx) for unsupported entries. You can save a connection for them, but no request will run until the executor ships.

## Import from a browser extension

A browser extension can send a signed-in session to DurinDoor instead of you pasting it. It works for ChatGPT Web, Perplexity Web, Grok Web and Muse Spark Web; the full-header providers such as HuggingChat are not supported.

1. In the dashboard, an operator asks for a pairing for one provider, either for a new named connection or for one existing cookie connection. The pairing secret is shown once and expires after two minutes.
2. The extension sends the provider's approved cookies, the exact provider origin and that secret to `/api/providers/cookie-import`, in the `x-durindoor-pairing-token` header.

The secret works once, only for that provider and target, and only on that route; it is not an API key. Pair again after any failed attempt. The call must use HTTPS, except to `localhost`, `127.0.0.1` or `[::1]` for local development, and the body is limited to 32 KiB. Cookies the provider does not approve, such as `cf_clearance`, are rejected. DurinDoor checks the shape of the cookies and does not contact the provider, so use **Validate** afterwards. Replacing the cookie on an existing connection clears a pending sign-in-again state. The pairing is kept in server memory, so run a single DurinDoor process behind the address the extension uses.

## Validation

**Validate** posts to `/api/providers/validate` with a 10 second limit. Grok Web, Copilot Web, ZenMux Free, Suno and Udio skip network validation rather than creating a conversation or generation; this does not prove the cookie works. ZenMux Free still rejects a pasted cookie missing `ctoken` locally. Perplexity Web and ChatGPT Web use read-only session requests; an expired or incomplete ChatGPT Web cookie (such as a missing `.1` chunk) fails with a message asking for every chunk. Microsoft 365 Copilot Web checks that both fields are present. Kimi Web calls the site's model list endpoint with the access token. A provider with no probe answers `Provider validation not supported`.

A passing probe means the site accepted the cookie at that moment. It does not keep the session alive.

## Limits

- Tool calling is usually off. Kimi Web, for example, declares `tools: false` for every model. Use an API or OAuth provider when your client needs tools.
- The model list is whatever the registry declares for that site, and the site can change or drop models without notice.
- These providers do not report quota to the [Quota Tracker](../features/quota-tracking.mdx). For Grok Web, ChatGPT Web, ZenMux Free, Suno and Udio the **Usage** card shows only what DurinDoor itself recorded for that saved session in the last 30 days (requests, estimated tokens, per model). It is not your subscription's remaining allowance, which none of these sites exposes through a stable API. Music jobs show as requests with no tokens; Suno clip durations are kept in the usage ledger, not on the card. Token counts are estimates of about four characters per token.

## When the session ends

Most cookie sessions have no proactive refresh or expiry tracking. ChatGPT Web can save cookies rotated by the site, but rotation does not prevent expiry or revocation. The temporary dashboard-login jar discards expired cookies before saving. Kimi Web is the exception: with a refresh token in the paste, it renews its access token on a 401 (see [Kimi Web](./kimi-web.mdx#refresh)). A 401 or 403 from upstream puts that connection on the normal two minute cooldown and the request moves to the next connection or combo member. The connection stays active, so the same rejection repeats after the cooldown.

If automatic recovery fails, sign in to the site again, copy a fresh cookie, and paste it over the old one with **Edit**. Saving a new cookie on a web-cookie connection replaces the stored value, keeps the connection's name, priority and settings, and clears the cooldown and error state recorded against the old cookie, so the next request uses the new one right away. Other connections of the same provider are not touched. Pasting the same value again changes nothing. Signing out of the site in your browser usually kills the session DurinDoor holds too.

Keep one browser profile for the account you hand to DurinDoor, and avoid signing out of it.

After saving a supported session, send one short request and check **Usage**. A skipped validation is not a successful probe. HTTP 501 `provider_port_pending` means no credential change can enable that provider in this build.

### Copilot Web sessions

Copilot Web accepts a pasted access token, a bearer header, a cookie containing `access_token`, a JSON object containing `access_token` (and optionally the exact `https://copilot.microsoft.com` origin), or a HAR. HAR credentials are taken only from requests to that exact HTTPS origin; other origins are ignored. An invalid supplied credential is rejected locally. Each request starts a fresh personal conversation. An expired or revoked session must be replaced; no refresh token is retained for this manual flow.

Microsoft 365 Copilot Web uses a separate Chathub path and access token. Set `providerSpecificData.tier` to `work` or `enterprise` for the work profile; `edu` and `included` select the education profile. Individual accounts retain their existing defaults. If a Microsoft 365 stream rewrites text already sent to the client, the stream reports an error; retry without streaming to receive the final snapshot. Manually supplied Microsoft 365 tokens are not refreshed automatically.

## Grok Web

`grok-web` (alias `gw`) sends chat requests to `grok.com` with your signed-in `sso` session. It is separate from the `xai` API provider and the Grok CLI device flow; their credentials do not work here.

1. Sign in at grok.com. In DevTools, Application, Cookies, `https://grok.com`, copy the `sso` value. Or copy the whole `Cookie` request header from the Network tab.
2. In **Providers → Grok Web**, paste it and save. Accepted forms: the bare value, `sso=<value>`, or a full header. A full header is sent as pasted and must contain `sso=`; a header without it is rejected locally with HTTP 401 and nothing is sent to grok.com.
3. **Validate** and **Test Connection** are skipped for Grok Web. Its only chat endpoint creates a conversation per probe, so a skipped result does not prove the cookie works. Send one short request to confirm.
4. Models are the registry list (`grok-3` to `grok-4.2`); unlisted ids pass through and map to `grok-4.1-fast` when DurinDoor has no mapping for them. The same session answers Chat Completions, Messages and Responses clients, with JSON or streaming. Tools and image generation are not supported.

Recovery: HTTP 401 or 403 means the session expired (message: re-paste your `sso` cookie); 429 means grok.com is rate limiting you. With more than one Grok Web connection the request falls back to the next one. To recover a connection, paste the fresh cookie with **Edit** as above. Signing out of grok.com in that browser profile ends the session.

Known limits: no cookie rotation is written back (unlike ChatGPT Web), so a renewed `sso` must be pasted by hand. Paired `sso-rw` handling beyond forwarding it from a pasted header is untested. DurinDoor does not emulate browser attestation or work around access controls; if grok.com challenges a session, use a different session or provider.

## ZenMux Free

`zenmux-free` (alias `zmf`) sends chat requests to `zenmux.ai` with your signed-in session. It is separate from the `zenmux` API-key provider; their credentials do not work for each other.

1. Sign in at zenmux.ai. In DevTools, Network, copy the whole `Cookie` request header from a zenmux.ai request. It must contain `ctoken=`.
2. In **Providers → ZenMux Free**, paste it and save. A leading `Cookie:` and line breaks are tidied. A paste without `ctoken` is rejected locally with HTTP 401 and nothing is sent to zenmux.ai.
3. **Validate** and **Test Connection** only check that `ctoken` is present, then skip the network call. Send one short request to confirm the session.
4. Models are the registry list (for example `zmf/deepseek/deepseek-chat`). The same session answers Chat Completions, Messages and Responses clients, with JSON or streaming. Tools are off for every model. Each request goes to the chat endpoint only: the saved cookie is never sent to a token-counting or any other URL, and the context check uses a local estimate.

Recovery: HTTP 401 or 403 from zenmux.ai is reported as "cookies expired or invalid" and cools that connection down; the request falls back to the next ZenMux Free connection if there is one. HTTP 402 is reported as free-tier quota exhausted and keeps its status. To recover, sign in again, copy a fresh header and paste it with **Edit**; the cooldown is cleared at once and other connections are untouched.

Known limits: there is no refresh flow and no expiry time, so the first sign that a session ended is a 401. Non-streamed replies carry an estimated token count (about four characters per token). No attestation is emulated and no access control is bypassed; a session zenmux.ai refuses has to be replaced.

## Suno and Udio

`suno` and `udio` are music providers, not chat providers. A chat request to either returns HTTP 501 (`provider_port_pending`). They run through the music routes with the saved session cookie.

1. Sign in at suno.ai or udio.com and copy the session `Cookie` header from a request to the site's API in the Network tab.
2. In **Providers**, pick Suno or Udio, paste it and save. Each saved connection keeps its own cookie. The dashboard credential format is unchanged.
3. **Validate** and **Test Connection** are skipped. The only generic probe would submit a generation and could spend credits, so a skipped result does not prove the cookie works.
4. Discover models with `GET /v1/models/music`. They are not listed by `GET /v1/models`. Suno ids are `chirp-fenix`, `chirp-crow`, `chirp-v4` and `chirp-v3-5`; Udio is `udio-default`.
5. Submit with `POST /v1/music/generations` (or `/v1/audio/music`) using a stored DurinDoor API key. The JSON body takes `model`, `prompt` and optional `instrumental`, `title`, `tags`, `lyrics`, `duration`. The answer is `status: "submitted"` with a `request_id` (the clip or track ids, comma separated) and an `x-9router-connection-id` header naming the account that took the job.
6. Poll with `GET /v1/music/generations/{request_id}`, the same API key, and that connection header. The status moves from `submitted` to `completed` (or `failed`). Suno clips that are `streaming` count as still pending; Udio is complete only when every track is finished. A completed job returns audio URLs, is recorded once in usage, and later polls replay the stored result without contacting the provider.

Account boundaries: a job is bound to the connection and API key that created it. Polling with another key, another connection, or an id DurinDoor never accepted answers 404, and polling never moves to a sibling account.

Recovery: a 401 or 403 on submit cools that connection down and the submit falls back to the next Suno or Udio connection. A 401 on a poll is returned to you as is, because the job exists only on the account that created it; the job stays open. Paste a fresh cookie with **Edit** and poll again with the same connection id: the poll uses the new cookie.

Known limits: no expiry time or refresh flow is known for either site, so the first sign that a session ended is a 401. DurinDoor has no timeout for a job: a poll that keeps answering `submitted` has to be abandoned by the client. Both are unofficial cookie integrations whose request shapes can change without notice. No attestation is emulated and no access control is bypassed; a session the site refuses has to be replaced.
