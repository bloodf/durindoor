title: ZCode
description: Staged provider for a local ZCode app-server over the V4 stdio protocol. Off by default, text-only and unverified against a live runtime.
---

ZCode (`zcode`, alias `zc`) runs one text-only turn per request against a `zcode app-server` process on the same machine. The ZCode profile you are signed in to owns the Z.ai credential. DurinDoor never reads, stores or forwards it, and there is no API key or cookie to import.

This provider is **staged and unverified**. Tests use an in-memory fake process that speaks the documented V4 NDJSON frames. No live ZCode runtime, profile, account or model list has been run against it. Treat every statement here as the documented contract, not tested behavior.

## Read this first

- **Dispatch is off by default.** A connection must set `providerSpecificData.enableSessionDispatch` to the boolean `true`. Anything else, including the string `"true"`, makes every request fail with HTTP 403 `zcode_dispatch_disabled` before any process starts. Each connection opts in on its own.
- **It re-serves a Z.ai plan through the gateway.** Every client of this DurinDoor instance spends the plan of whichever profile the local ZCode CLI is signed in to. Do not enable it for people who should not use that plan, and check Z.ai's terms for your plan first.
- **Tool restriction is requested, not proven.** DurinDoor creates every session with a tool denylist and no MCP servers, and repeats the denylist on every turn. The [pinned V4 contract](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/docs/zcode-protocol.md) does not show that the runtime enforces either field, so the gateway also watches the conversation projection. If ZCode reports a tool or sub-agent row, or asks for an interaction such as an approval, the turn ends with HTTP 502, a stop command is sent and the process is killed. The gateway never approves anything on the runtime's behalf.

The existing Z.ai and GLM providers are separate and unchanged. See [Z.ai and GLM account providers](./catalog.mdx).

## Set up

1. Install ZCode and sign in once so the local profile holds the plan credential. DurinDoor does not drive the sign-in.
2. Make sure `zcode app-server` starts on the gateway host. If the binary is not on `PATH`, set `DURINDOOR_ZCODE_BIN` to its absolute path in the DurinDoor environment. A connection cannot change the executable, so stored data cannot redirect it.
3. Add the provider once under **Providers** so a connection row exists; it needs no key.
4. Opt the connection in by setting `providerSpecificData.enableSessionDispatch` to `true` on that row. Until then it refuses to dispatch.

Cookie capture: **not applicable.** ZCode authenticates through the local profile, so the cookie capture extension, pasted `Cookie:` header, cURL and HAR import flows do not apply. The staged module exports an intentionally empty `zcodeCookieProfile` so the registration batch can see that.

## How a request runs

- One process and one session per request, closed afterwards. Nothing is shared between requests or between connections, so two connections never see each other's history, and a request that is cancelled or fails tears its process down.
- The child gets an allowlisted environment (`PATH`, `HOME`, locale and temp-directory variables). Other variables, including provider keys in the gateway's own environment, are not passed. Its working directory is a fresh empty scratch directory removed afterwards.
- Frames are newline-delimited JSON. The gateway sends `createSession`, subscribes to `conversation/<sessionId>`, sends `sendText`, then reads the projection until the session reaches a terminal phase. The command ACK only records admission; the result comes from the projection.
- Chat history is flattened into one text turn. Images, request `tools`, tool results and assistant tool calls are rejected with HTTP 400 before any process starts.
- Both the OpenAI chat route and the Anthropic Messages route work, JSON and streamed. Text appears as the assistant row grows. Usage is returned only when the runtime reports it.

## Models

The staged catalog lists `glm-5.3` and `glm-5.2`, which follows OmniRoute's list for this provider. The documented V4 stdio interface does not expose a standalone model list, so other ids pass through to the runtime unchanged and the runtime decides whether it can use them. A model id starting with `-` is refused.

## Errors

| Situation | Result |
| --- | --- |
| Connection did not opt in | 403 `zcode_dispatch_disabled` |
| Tools, tool history or non-text content in the request | 400 |
| Executable missing or failed to start | 503 `zcode_unavailable` |
| Process exits or errors before the turn ends | 502 |
| Command ACK `rejected` | 400 |
| Command ACK `failed` or `stale`, runtime tool call or approval request, interrupted turn | 502 |
| Session error with provider status 401 or 403 | 401 |
| Session error with provider status 429 | 429 |
| No answer within the request or turn timeout | 504 |
| Too many concurrent sessions (default 4) | 429 |

A stream that fails before any text keeps its HTTP status. A stream that fails later ends with an in-band error event and `[DONE]`.

## Limits and not verified

- Live runtime behavior is untested: the framing around frames, the `*` wildcard in the denylist, whether the runtime honors `toolDenylist` and `toolDisallowlist`, snapshot and delta field names, the usage fields and the error attribution shape are all taken from the pinned schemas and could differ in a real build.
- OmniRoute's own fixture uses a binary header and value encoding that does not match first-party V4 NDJSON, so none of its transport was ported.
- The default turn timeout is 10 minutes and the request timeout is 30 seconds.

See `internal/docs/zcode-v4-compatibility-1252.md` in the repository for the pinned first-party contract review.
