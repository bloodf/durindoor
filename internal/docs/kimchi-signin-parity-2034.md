# Kimchi compatibility investigation (#2034)

The catalog cache keys entries by endpoint and a hash of the actual bearer credential. A profile ID or username is not an entitlement boundary: different credentials for the same profile can see different catalogs. `tests/unit/kimchi-signin-parity.test.js` reproduces that case with closed outbound mocks. This does not establish isolation of the separate process-wide model metadata map, which is keyed only by model ID.

The pinned recursive source inventories for [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI/tree/6faa8d20b2673404cff70a2f2d9537ae0d0e684d), [EasyCLIProxyAPI](https://github.com/router-for-me/EasyCLIProxyAPI/tree/e4223d5eefa22a3301ca7e2a28d05897432b07f9), and [OmniRoute](https://github.com/cheaper-inference/OmniRoute/tree/e3c1531afd07d5e06f7ffab658584a7ae2e3627e) contain no Kimchi-named paths. This path search alone does not rule out generic compatible-provider or plugin support. The comparison of sign-in, refresh, catalog, request envelopes, streaming and delegation remains incomplete; no upstream parity is claimed. No live provider was contacted. The API-key flow and outbound routing were not changed.
