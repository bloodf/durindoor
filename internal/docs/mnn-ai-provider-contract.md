# MNN AI provider contract

Status: provider module and offline fixture only; production registration is pending a separate batch. Tracking issue [#1207](https://github.com/bloodf/durindoor/issues/1207); tracker [#2034](https://github.com/bloodf/durindoor/issues/2034). Scope is the documented chat API only: bearer API key, OpenAI-compatible chat completions, authenticated model discovery. The Anthropic-compatible `/v1/messages` route, the Responses API, and the image, video, audio, speech, transcription, embedding, moderation and web-search surfaces that the operator also documents are outside this integration.

## Pinned sources

- First-party contract: [MNN AI documentation](https://mnnai.ru/docs) — one OpenAI-compatible chat endpoint at `https://api.mnnai.ru/v1/chat/completions` with `Authorization: Bearer <key>`, `stream: true` over server-sent events, the standard OpenAI tools format, `reasoning_effort` for reasoning models, and an authenticated model list at `https://api.mnnai.ru/v1/models` (`GET`, same bearer header). The page names model ids such as `gpt-5.4`, `glm-5`, `mistral-medium-latest` and `claude-4.6-sonnet`, and states that the model list depends on the key. The docs page renders its prose from a locale dictionary, so the wording is paraphrased here rather than quoted.
- Operator and terms: [terms of service](https://mnnai.ru/terms-of-service) (last updated 2026-11-07) name the operator — Шустов Михаил Константинович, self-employed payer (НПД), tax id 631935067408, contact `mnnai.ru@outlook.com` — and set the credit, rate-limit, refund and abuse rules. [Privacy policy](https://mnnai.ru/privacy) (same date) names the same operator as the personal-data operator, states that request metadata kept for billing is limited to status, model name, time and cost, and states that prompts and files sent through the API are passed to third-party model providers, which implies cross-border transfer. The prior closure of issue #1207 cited absent first-party API and terms; these pages are the changed first-party evidence that resolves it.
- Port source: OmniRoute `release/v3.8.55`, pinned to [`4624250231f49ed118fb4522a9d735e4894322c6`](https://github.com/cheaper-inference/OmniRoute/tree/4624250231f49ed118fb4522a9d735e4894322c6). Its [`mnn-ai` registry entry](https://github.com/cheaper-inference/OmniRoute/blob/4624250231f49ed118fb4522a9d735e4894322c6/open-sse/config/providers/registry/mnn-ai/index.ts) registers `id`/`alias` `mnn-ai`, `format: "openai"`, `executor: "default"`, `authType: "apikey"`, `authHeader: "bearer"`, `baseUrl: https://api.mnnai.ru/v1/chat/completions`, `modelsUrl: https://api.mnnai.ru/v1/models`, `models: []` and `passthroughModels: true`. That composed executor is the generic default executor; there is no MNN AI-specific executor upstream.
- Upstream catalog mapping at that pin: none. `CHAT_OPENAI_COMPAT_MODELS` in [`open-sse/config/providers/shared.ts`](https://github.com/cheaper-inference/OmniRoute/blob/4624250231f49ed118fb4522a9d735e4894322c6/open-sse/config/providers/shared.ts) has no `mnn-ai` key, so the empty static catalog is faithful to the pinned contract, not an omission.

## DurinDoor-side implementation

- `open-sse/providers/private/mnn-ai.js` — the only new runtime file. It declares the API-key category, the bearer chat transport, `validateUrl` and `modelsFetcher` pointing at `https://api.mnnai.ru/v1/models`, an empty static catalog, `passthroughModels: true`, and `serviceKinds: ["llm"]`.
- No executor was added. The fixture exercises the existing default OpenAI-compatible executor, so request shaping, bearer auth, streaming passthrough, error surfacing, and usage accounting use shared plumbing rather than a provider fork.
- Credential validation reuses the shared registry probe: `buildRegistryProviderProbe` reads `transport.validateUrl` and issues `GET https://api.mnnai.ru/v1/models` with the bearer header, behind the normal SSRF guard and redirect policy. The shared probe accepts HTTP 200 as a valid key and HTTP 401 as an invalid one; whether the upstream answers 401 for a bad key is unverified, so the check inherits the shared policy unchanged rather than asserting a stronger one.
- Model discovery reuses the generic registry `modelsFetcher` path in `src/app/api/providers/[id]/models/fetchConnectionModels.js`. That path is single-request with an 8 s deadline, so discovery is bounded; a non-OK upstream surfaces `Failed to fetch models: <status>` instead of an empty successful catalog.
- The generic `modelsFetcher` fallback resolves each connection catalog, and the picker includes MNN AI among its live catalog providers.
- Production registry, agent index and provider catalog remain at their integration-base versions. The unit test composes the module into the registry fixture to exercise the shared paths until registration ships separately.
- `tests/__baseline__/providers-baseline.json` and `tests/__baseline__/alias-baseline.json` are unchanged. They are already stale on the base commit for more than twenty unrelated providers, they are not part of the `test:ci` gate, and refreshing them here would fold unrelated registry drift into this change.
- `internal/docs/omniroute-provider-matrix.json` and `internal/docs/provider-parity-omniroute.md` are unchanged. They are recorded evidence from a pinned OmniRoute checkout and a dated comparison; regenerating them requires that checkout, and a run without it proves nothing.

## Evidence and limits

`tests/unit/mnn-ai-provider.test.js` covers the registry contract, provider/connection exposure, model-id routing, bearer header construction, credential validation, model discovery for two connections with distinct keys, credential and quota errors, non-streaming JSON with provider-reported usage, SSE streaming, streaming usage accounting, and the discovery deadline. Every HTTP call is a local mock with synthetic placeholder keys; no MNN AI account, key, plan or billed request was used.

Not verified: live endpoint behavior, plan entitlements, the exact error envelope MNN AI returns for a bad key or an exhausted quota, model availability, pricing, rate limits and reliability. The documented `GET /v1/models` call carries the key and is the only discovery surface ported; if the upstream later answers it without authentication, the key check would pass for an invalid key and would need revisiting.

Only the chat route is covered by the module and fixture. The operator also documents an Anthropic-compatible `POST https://api.mnnai.ru/v1/messages` with an `x-api-key` header, and a Responses route. Neither appears in the pinned provider contract — the upstream entry declares one transport only — so the alternate was not added. DurinDoor's existing Anthropic transport machinery could carry it later, but doing so would extend the upstream contract rather than port it, and it would need its own first-party review of the request and response shapes. Neither is advertised to users.
