# Muse Spark Web investigation — #2034

Status: since #2342, Muse Spark Web supports session dispatch when the connection explicitly sets `enableSessionDispatch` to `true`. The executor refreshes a short-lived token through Meta's browser-backed login flow, then sends chat requests over Meta's WebSocket; without the opt-in, dispatch remains guarded and returns HTTP 501 `provider_port_pending`. See [the provider guide](../../docs/providers/muse-spark-web.mdx) and `open-sse/executors/muse-spark-web.js`. The registered model IDs remain a static catalog, not proof of live model discovery.

Reference pins used for this investigation:

Its server binds Muse Code model and relay routes, and the SDK binds the Meta executor and model catalog. The inspected core server and SDK contain no Muse Spark Web session contract. The local `muse-code` device grant and `meta-llama` API key are separate provider identities from the web-cookie session. The focused mock regression described here predates #2342: it covered web-login session expiry, static catalog identities, OAuth provider separation, fail-closed dispatch for both web aliases, and isolated parser snapshots and authentication errors. It did not verify live session validity, upstream protocol, model discovery, real expiry responses, or end-to-end sign-in. No live provider, browser, or account was used for that investigation. The later #2342 implementation added guarded browser-token and WebSocket dispatch; these historical limitations are not claims about the current implementation.

The response parser follows OmniRoute's `open-sse/executors/muse-spark-web/response-parser.ts` error-state and security-block classifications: an assistant `streamingState: ERROR` is a failure, and security-block text maps to 403. Current dispatch also parses Meta WebSocket response events in the executor.

## Saved-cookie lifecycle (#2034)

Offline lifecycle evidence recorded before #2342 is `tests/unit/provider-cookie-lifecycle-muse-yuanbao-hugging.test.js`. It uses the real database, provider routes, validate and test routes, `/v1/models`, `handleChat`, the Messages and Responses routes, account fallback, executors and the usage route; only credentials and outbound bytes are synthetic, and `fetch` is closed by default. The source pins above are the 2026-11-20 snapshot and were reused, not re-fetched. No provider request, real session, browser or Docker was used for that evidence.

At the time of this lifecycle check, the dispatch guard was closed. The recorded checks through every entry point (Chat Completions JSON and stream, Messages, Responses, direct executor and translate-path `buildHeaders` and `buildUrl`) observed HTTP 501 `provider_port_pending`, no outbound request, no credential in any response, the static three-model catalog in `/v1/models`, per-account rows untouched, and re-paste through the Edit route storing the new cookie without changing the guard. #2342 subsequently added opt-in session dispatch.

Gaps found and fixed (DurinDoor-original):

- **Validate and Test Connection sent the saved cookie.** The generic probe POSTed `Authorization: Bearer <cookie>` to `https://www.meta.ai/api/graphql`, bypassing the dispatch guard. Both now return `skipped` through `src/lib/providers/conversationProbe.js` without any request.
- **The guard locked and rotated accounts.** `chatCore` flattens the guard body to `[501]: ... runtime execution is not ported yet`, which dropped the `provider_port_pending` type that `checkFallbackError` matched, so every connection was locked for 30 seconds and the router tried each sibling. `checkFallbackError` now also matches the guard's own 501 wording, so no cooldown or fallback is recorded. The same wording covers every provider behind `UnsupportedOmniRouteWebSessionExecutor`.
