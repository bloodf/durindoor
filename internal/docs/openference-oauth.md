# Openference OAuth source and validation

DurinDoor implements the authorization-code PKCE flow from OmniRoute PR [#9869](https://github.com/cheaper-inference/OmniRoute/pull/9869), merged as `6f3738b0097d7476bdc14b4a0b16d42ef8ddc8d9`. Reviewed current OmniRoute main `2c4aa9e9af21e2ad27440c4c478c10282154a596`, especially `src/lib/oauth/providers/openference.ts`, `src/lib/oauth/constants/oauth.ts`, and `open-sse/config/providers/registry/openference/index.ts`. The qualification snapshot was `61e07fb7e0d4e1e76111495d3718c9e4d06d2a62`. DurinDoor main `32927dc48c404e70874b1023b7df37947c69f41c` contains the separate `openference-api` provider only.

[Openference's public documentation index](https://docs.openference.com/llms.txt) describes API-key authentication, model discovery and OpenAI-compatible chat, but does not document the OAuth registration or grant contract. An operator must provide an approved client ID; no OmniRoute client identity or secret is embedded. An account-backed verification of the OAuth grant, refresh, model access, tool and streaming behavior and billing remains outstanding. No brand assets are redistributed. No models or pricing are hardcoded.

The server flow binds state, PKCE verifier, redirect, client ID and egress selection to the login. The stored client ID scopes later refreshes; the connection's egress selection applies to refresh and discovery. Discovery failures are returned to the caller rather than represented as an empty successful catalog. The generic chat executor and accounting pipeline handle OpenAI-format requests and responses. `tests/unit/openference-provider.test.js` exercises synthetic credentials and closed mocked transports; it does not establish live support.
