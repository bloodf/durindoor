## Local contract checked

- Provider identity/auth registration: `open-sse/providers/registry/*.js`, exposed through `src/shared/constants/providers.js`; web-cookie executors are registered in `open-sse/executors/index.js`.
- Import rules: `src/shared/utils/cookieImportContract.js`, `src/lib/providers/cookieImport/`, the provider `cookieImport` profiles, and dashboard `CookieImportModal.js`. Server-side origin and credential allowlists apply to dashboard and extension handoff. Manual-only credentials remain manual-only.
- Sign-in and expiry: provider `webLogin` profiles use the isolated login service (`src/lib/webLoginSession.js` and `src/proxy.js`); provider-specific expiry/rotation is implemented in the executor and `src/sse/handlers/chat/singleModel/dispatch.js`. Web-cookie sessions without a supported refresh contract require re-import after expiry. This is not OAuth refresh.
- Dispatch: `src/sse/handlers/chat/singleModel/dispatch.js` persists rotated cookie credentials with an expected-credential guard. HuggingChat and Muse Spark dispatch remain per-connection opt-in. Web-cookie probes are skipped where a probe would create a real conversation/generation; Perplexity has a read-only session check.
- Offline evidence: `tests/unit/provider-cookie-import-contracts.test.js`, `provider-cookie-import-dashboard.test.js`, `provider-cookie-capture-extension.test.js`, `api/provider-cookie-import*.test.js`, `api/providers-web-login*.test.js`, `web-session-redirects.test.js`, `web-session-shared-transport-redirects.test.js`, the `provider-cookie-lifecycle-*.test.js` files, and the provider-specific dispatch tests. These establish mocked behavior only.

## Disposition and next unit

**Proven parity:** The established DurinDoor cookie providers have local registry, executor and offline import/lifecycle evidence as listed above. OmniRoute is not evidence that browser sign-in, credentials or current vendor endpoints work live. No live provider accounts were used. CLIProxyAPI and EasyCLIProxyAPI contribute no additional cookie contract in the pinned revisions.

**Registered (2026-11-27):** `inner-ai-web`, `poe-web`, `venice-web` and `v0-vercel-web` are registered web-session identities with their own executors; the `inner-ai`, `poe`, `venice` and `v0-vercel` API-key identities are unchanged. All four take dashboard Cookie header, cURL or HAR import on the exact origins above, plus manual paste. All four also have extension capture, with one exact-origin, one-cookie entry each in the compiled extension table and host permission list; existing entries were not widened. Inner.ai Web's optional account email travels only on the private dashboard pairing, never through the extension; Venice Web captures only from the exact `clerk.venice.ai` origin. None has web login. Usage is recorded per connection by the real chat route (v0 JSON keeps upstream counts; the others record the gateway estimate). Evidence is mocked only; no live acceptance is claimed.

**Live-only verification:** Gemini Web, Muse Spark Web, Arena and the four sessions registered above still need authorized account checks to establish current sign-in/session acceptance. These checks do not block mocked implementation and are not evidence of current provider reliability.

**Dead or non-actionable upstream:** SYNTX is absent from the pinned OmniRoute web-cookie catalog; DurinDoor's existing `syntx` note records an unavailable public API route. Do not count it as a current web-cookie gap. OmniRoute's `inner-ai` catalog row is a current cookie contract, despite local `inner-ai` being API-key auth, so it is now registered as the separate `inner-ai-web` identity. OAuth/API-key-only upstream rows are excluded.

**Lane boundary:** This refresh does not take claims from open #2642 (TrustedRouter review lane) or #2311 (web-session executor architecture lane). It does not prescribe or implement the shared executor refactor; the next unit is provider identity and behavior coverage only.


### Firefly browser registration (#2034)

`adobe-firefly-web` is registered as an experimental, explicitly enabled per-connection ordinary-browser image/video provider. Operator mappings and fresh server-owned profiles are required; no Adobe selectors ship. Authenticated host setup, stored model discovery, and synchronous b64_json media routes are implemented and tested with closed synthetic mocks only. No live UI compatibility, sign-in, entitlement or consumer API parity is claimed. `adobe-firefly-api` remains the distinct Services entitlement; `adobe-firefly` and `firefly` remain closed legacy raw identities. See [the internal contract](firefly-consumer-browser-contract.md) for ownership and evidence limits.
