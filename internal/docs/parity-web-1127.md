CLIProxyAPI and EasyCLIProxyAPI provide OAuth/device-auth and desktop-client contracts in the requested repositories, but no matching web-cookie provider catalog, browser-cookie importer, or cookie-session executor. Their OAuth/API-key providers are outside this inventory. OmniRoute is therefore the only one of these pinned sources with actionable web-cookie source contracts in this comparison.

## Local contract checked

- Provider identity/auth registration: `open-sse/providers/registry/*.js`, exposed through `src/shared/constants/providers.js`; web-cookie executors are registered in `open-sse/executors/index.js`.
- Import rules: `src/shared/utils/cookieImportContract.js`, `src/lib/providers/cookieImport/`, the provider `cookieImport` profiles, and dashboard `CookieImportModal.js`. Server-side origin and credential allowlists apply to dashboard and extension handoff. Manual-only credentials remain manual-only.
- Sign-in and expiry: provider `webLogin` profiles use the isolated login service (`src/lib/webLoginSession.js` and `src/proxy.js`); provider-specific expiry/rotation is implemented in the executor and `src/sse/handlers/chat/singleModel/dispatch.js`. Web-cookie sessions without a supported refresh contract require re-import after expiry. This is not OAuth refresh.
- Dispatch: `src/sse/handlers/chat/singleModel/dispatch.js` persists rotated cookie credentials with an expected-credential guard. HuggingChat and Muse Spark dispatch remain per-connection opt-in. Web-cookie probes are skipped where a probe would create a real conversation/generation; Perplexity has a read-only session check.
- Offline evidence: `tests/unit/provider-cookie-import-contracts.test.js`, `provider-cookie-import-dashboard.test.js`, `provider-cookie-capture-extension.test.js`, `api/provider-cookie-import*.test.js`, `api/providers-web-login*.test.js`, `web-session-redirects.test.js`, `web-session-shared-transport-redirects.test.js`, the `provider-cookie-lifecycle-*.test.js` files, and the provider-specific dispatch tests. These establish mocked behavior only.

## Disposition and next unit

**Proven parity:** The established DurinDoor cookie providers have local registry, executor and offline import/lifecycle evidence as listed above. OmniRoute is not evidence that browser sign-in, credentials or current vendor endpoints work live. No live provider accounts were used. CLIProxyAPI and EasyCLIProxyAPI contribute no additional cookie contract in the pinned revisions.

**Implementable additions:** The next bounded implementation unit is the three distinct chat-session identities `inner-ai-web`, `poe-web`, and `venice-web`; keep existing API-key provider identities intact. Their acceptance is the per-row criteria above plus offline fixed-origin, expiry, model-discovery, JSON and SSE coverage and provider docs. `v0-vercel-web` is a separate follow-on with the same gates after its cookie/expiry contract is made explicit from the pinned executor. No one should mark these shipped until the code and focused mocks land.

**Live-only verification:** Gemini Web, Muse Spark Web, and Arena still need authorized account checks to establish current sign-in/session acceptance. These checks do not block mocked implementation and are not evidence of current provider reliability.

**Dead or non-actionable upstream:** SYNTX is absent from the pinned OmniRoute web-cookie catalog; DurinDoor's existing `syntx` note records an unavailable public API route. Do not count it as a current web-cookie gap. OmniRoute's `inner-ai` catalog row is a current cookie contract, despite local `inner-ai` being API-key auth, so it remains in the implementable list. OAuth/API-key-only upstream rows are excluded.

**Lane boundary:** This refresh does not take claims from open #2642 (TrustedRouter review lane) or #2311 (web-session executor architecture lane). It does not prescribe or implement the shared executor refactor; the next unit is provider identity and behavior coverage only.
