## Network boundary

Every candidate in this batch moves or reads across the gateway's outbound boundary, and the dispositions follow that boundary rather than the diff size.

The only ported residual reads one operator-configured endpoint per configured connection, using the connection's own stored credential, through the existing provider request helper. It adds no new egress path: the request goes through `createProviderRequest(context)` in `open-sse/services/quota/providers/openaiCompatible.js:147`, the same helper and proxy resolution every other quota adapter uses, so a compatible quota read inherits the per-connection proxy settings and the tracker's timeout and response-size bounds. It introduces no second URL authority: the request target comes from `providerSpecificData.quotaEndpoint.url`, which the operator sets on the connection alongside the compatible node's base URL, and the ported change adds no URL construction of its own.

Upstream #4999's shape is weaker on this axis in one respect and stronger in another. It is weaker because it accepts an absolute URL in `quotaPath`, so a node's quota path can point at an authority unrelated to the node's `baseUrl`; the local surface keeps the quota URL inside the same operator-supplied connection configuration as the rest of the compatible-provider settings, and DurinDoor's SSRF guard (`src/shared/utils/ssrfGuard.js`) is the existing control for host validation on server-side fetches. It is stronger because upstream's version writes the balance into a bespoke dashboard shape that never reaches the quota store, while the local version persists a validated snapshot, so a compatible provider's credit balance participates in the same routing and preflight decisions as every other provider's quota.

Upstream #3584 is the one candidate whose network effect is disqualifying rather than merely different. Its `quotaGuard.evaluateQuota` performs a live provider fetch from inside `getProviderCredentials`, and its `Promise.race` timeout rejects the routing decision without aborting the underlying request. DurinDoor keeps that fetch out of the routing path entirely, so the routing decision never waits on a quota endpoint.

## Automatic connection pausing

DurinDoor pauses a connection automatically when its remaining quota crosses a configured floor, and it does so from persisted observations rather than from a synchronous probe.

The mechanism is `resolveQuotaRoutingFloor` (`open-sse/config/quotaSelection.js:46`), which resolves a floor ratio with connection → provider → dimension → global precedence and defaults to disabled (`routingFloorEnabled: false`). The floor is applied in two places. `src/shared/services/quotaSelection.js:21` `isProfileBelowRoutingFloor` marks a candidate below the floor, and `src/shared/services/quotaSelection.js:90` `rankQuotaConnections` drops it from the eligible pool; `src/sse/services/auth.js:959-980` then returns `allRateLimited` with `localQuotaFloor: true` and status 503 when no eligible candidate remains, so a caller sees an exhausted provider rather than a silent fallback. The same floor bounds reservation grants in `src/lib/db/repos/quotaReservationsRepo.js:255`, so a paused account cannot be reserved against either.

Two properties matter for correctness and are preserved. First, the pause is **derived, never stored**: the floor is compared against a fresh observation each time, so an account recovers on its own once the window rebounds or resets. Second, it is **fail-open**: `evaluateProviderQuotaPreflight` (`src/shared/services/providerQuotaPreflight.js:365`) treats unknown, stale, missing, foreign-source and repository-error observations as "not paused", so a quota endpoint that is down or a tracker that has not run yet never takes an account out of rotation.

Upstream #3584's model is the same idea with a different substrate — a per-window threshold map on the connection and a `lastQuotaSnapshot` blob on the same record — and it is not ported because its substrate is weaker on both properties above: the threshold map is free-form and unvalidated at rest, and the snapshot that drives the decision is fetched live inside the routing path, so an unreachable quota endpoint costs routing latency rather than failing open. Upstream's own dashboard hunk in this PR also leaves an unbalanced JSX block in `src/app/(dashboard)/dashboard/usage/components/ProviderLimits/index.js`, which is a further reason not to lift the diff wholesale.

## Permission and credential handling

No candidate in this batch changes who may read a credential or who may perform a privileged action.

The ported residual sends the connection's own stored API key to the connection's own configured quota URL, using the same credential-selection helper (`connectionCredential(connection, "apiKey", "accessToken")`) and the same `auth` modes the adapter already supported. It introduces no new secret, no new credential field, and no new caller: the adapter runs inside the existing tracker, which is operator-triggered and already bounds outbound quota reads.

Upstream #4321 would change credential handling, which is why it is excluded rather than deferred: `{{API_KEY}}` interpolation places the secret into operator-chosen header names, and header suppression removes a default `Authorization` header, so the operator gains control over where the credential appears on the wire. DurinDoor keeps that surface closed; its only operator-supplied header surface is the quota read's static `headers` map, and its executor-level extra-header mechanism copies a single named credential field into a single registry-fixed header.

Upstream #5269 would add a privileged mutation. Its `POST` redeems a reset card — an irreversible upstream state change — behind a same-origin and content-type guard, an in-flight lock and a one-shot "never retry the consuming request" rule. DurableDoor's existing reset-credit redemption already lives behind the dashboard operator surface for the providers that support it, and the work order excludes automating credit redemption, so nothing from that PR was ported.

Upstream #5351's request-detail endpoint is a permission change in the opposite direction: it would require a dashboard session JWT for the payload-bearing read while leaving the list endpoint redacted. DurinDoor currently has no route that returns the unredacted payload at all, so there is no current exposure to close and no permission surface to widen in this track. The local redaction in `src/app/api/usage/request-details/route.js` is unaffected by this batch.

## Ported residual

`port(upstream): #4999 - read a remaining-only credit balance for compatible providers`

Upstream #4999 accepts a compatible provider that publishes only what is left — `{"credits": 5099.44}` — and reports it as a balance. DurinDoor's compatible-provider mapping could not express that: `buildQuotaRow` required `total` to resolve and returned no row otherwise, so such a provider produced `malformed` and no quota at all. The existing local guarantee was deliberate and is preserved: a mapping that resolves only `used` still yields no row rather than a fabricated 0/0.

- Exact code location: `open-sse/services/quota/providers/openaiCompatible.js`, `buildQuotaRow`. A mapped `total` remains authoritative — when it resolves the row is the bounded `quotaRow` as before, and when it does not resolve the row is dropped rather than degraded into a balance. Only a mapping that does not map `total` and does map `remaining` produces the new row, built with the codebase's existing `remainingQuotaRow` helper (`open-sse/services/quota/normalize.js:184`), the same construction already used for remaining-only balances by `open-sse/services/quota/providers/balances.js:45,57,82` and `open-sse/services/quota/providers/codingPlans.js:717,788`. The resulting row carries an unknown scale (`limitKind: "unknown"`, `limit: null`, `remainingRatio: null`), so it claims no utilization percentage and reaches the `exhausted` state only at exactly zero — the behavior `open-sse/services/quota/normalize.js:108-121` `deriveState` gives a remaining-only row.
- Backward compatibility: `remaining` is a new optional mapping key. A configuration that does not map it resolves exactly as before. A configuration that maps both `total` and `remaining` keeps the bounded reading and ignores the balance, so no existing meaning changes.
- Offline test: `tests/unit/openai-compatible-quota-endpoint.test.js` — "reads a remaining-only credit balance without inventing a total", "reads a zero remaining balance as exhausted", "keeps a mapped total authoritative when it does not resolve", and "prefers the mapped total over remaining when both are mapped". The pre-existing case "never reports a resolved quota when only one axis resolves (no 0/0 illusion)" still passes unchanged. All runs use an injected `fetchImpl`, so no provider target is contacted.
- Documentation: `docs/providers/openai-compatible-nodes.mdx` and `internal/docs/product/providers/openai-compatible-nodes.mdx` now describe the `remaining` mapping and its precedence against `total`.
