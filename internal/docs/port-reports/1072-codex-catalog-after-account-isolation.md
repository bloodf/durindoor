## #5511 — live Codex catalog, `/v1/codex/models`, `/v1/models` live resolver

### Existing parity (verified equivalents)

- **Codex CLI already gets the `{"models":[...]}` catalog shape.** `buildModelsResponse` selects a Codex-CLI envelope when the request carries `originator: codex_cli_rs` or a Codex-ish User-Agent, and answers `{models: [...]}` ([src/app/api/v1/models/_shared.js:5](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/_shared.js:5), [:16](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/_shared.js:16), [:97](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/_shared.js:97)). The rows carry `slug`, `display_name`, `supported_in_api`, `supports_search_tool`, `tool_mode`, `multi_agent_version` and `context_window`. The upstream PR's central complaint — Codex clients are handed the OpenAI `{object,data}` list and fall back to their own bundled metadata — therefore does not apply to this fork's existing surface.
- **Same upstream catalog URL and CLI identity.** Both sides read `https://chatgpt.com/backend-api/codex/models?client_version=<registry cliVersion>` with `originator: codex_cli_rs` and the Codex CLI User-Agent: [src/app/api/providers/[id]/models/modelsConfig.js:545](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/providers/[id]/models/modelsConfig.js:545) and [open-sse/services/usage/codex.js:101](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/services/usage/codex.js:101).
- **Account binding is stronger here than in the proposed snapshot.** Upstream's `accountIdOf` reads `workspaceId || chatgptAccountId || accountId` raw. The fork resolves the same three legacy aliases through one shared helper that trims, rejects header-unsafe values, detects conflicting aliases, and falls back to the `chatgpt_account_id` inside the OAuth id_token ([open-sse/shared/codexAccountId.js:39](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/shared/codexAccountId.js:39)), and the usage, quota, image and dashboard-discovery paths all use it. `tests/unit/codex-account-identity.test.js` covers the precedence and the conflict case.
- **The raw Codex catalog entries already survive locally.** The dashboard parser keeps the upstream row intact (`{...model, id, name}`) and only adds `-review` variants and a `minimal_client_version` floor ([modelsConfig.js:162](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/providers/[id]/models/modelsConfig.js:162), [open-sse/providers/models/helpers.js:7](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/providers/models/helpers.js:7)). The upstream PR body's premise that per-connection discovery "normalizes entries to `{id,name}`" is therefore not a defect of this fork's dashboard path.
- **Live context windows and reasoning levels are already read from the upstream catalog.** `extractApiCapabilities` reads `context_window` through `CONTEXT_KEYS` and turns `supported_reasoning_levels` into `thinkingEfforts` ([open-sse/services/modelMetadata.js:4](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/services/modelMetadata.js:4), [:157](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/services/modelMetadata.js:157)), and the Codex live resolver feeds those entries through `materializeSyncedModel` ([src/app/api/v1/models/buildModelsList.js:185](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/buildModelsList.js:185)).
- **Registry variants keep their own capabilities, as upstream intends.** Upstream's `mergeCodexRegistryModels` refuses to shrink a `[1m]`/review variant to the base model's window. The fork's equivalent is `getModelUpstreamId`, which resolves a registry row through `upstreamModelId` and leaves variant capabilities alone ([open-sse/config/providerModels.js:230](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/config/providerModels.js:230)).

### Architecture-specific exclusions

- **The persisted snapshot file has an existing local counterpart, so a second one is not warranted.** Upstream persists `DATA_DIR/codex-model-catalog.json` to survive a balancer whose last account dies. This fork already stores a synced catalog per provider in the database, with its own retention and retirement rules ([src/lib/db/repos/syncedModelsRepo.js:38](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/lib/db/repos/syncedModelsRepo.js:38)). A second raw-file snapshot would duplicate that store.
- **A global merge across every active Codex account is not this fork's contract.** Upstream merges all active connections into one catalog because Codex catalogs are per-plan. #2133 moved the opposite way for endpoint-bound providers: `CONNECTION_SCOPED_SYNC_PROVIDERS` is `["mlx", "opencode-server"]`, and `/v1/models` passes the caller's key scope down through `getRequestConnectionScope` → `allowedConnectionIds` → `catalogEntryForConnection` ([src/lib/modelAutoSync/connectionScope.js:10](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/lib/modelAutoSync/connectionScope.js:10), [src/sse/services/modelAccess.js:79](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/sse/services/modelAccess.js:79), [src/lib/modelAutoSync/catalog.js:70](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/lib/modelAutoSync/catalog.js:70)). Upstream's unscoped merge applied verbatim to a key-scoped caller would widen that caller's catalog to accounts it may not use.
- **The token-refresh policy is a different, established contract.** Upstream refreshes the Codex token only after a 401/403 and persists the result, because Codex rotates the refresh token on every use. The fork's catalog paths never refresh: the live resolver fails open to an empty list and the dashboard fetch reports the status without refreshing ([open-sse/services/usage/codex.js:287](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/services/usage/codex.js:287), [fetchConnectionModels.js:166](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/providers/[id]/models/fetchConnectionModels.js:166)); the fork's proactive refresh by lead time belongs to the dispatch path, not to catalog reads. Both sides use the same deduped `refreshCodexToken`, with the fork's variant additionally proxy-aware ([open-sse/services/tokenRefresh/providers.js:370](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/services/tokenRefresh/providers.js:370)).
- **Fallback and reconnect are out of the upstream patch's scope.** The four upstream paths touch no fallback code. This fork's account fallback, per-model locks, cooldowns and connection-recovery leases are provider-agnostic and already cover Codex accounts ([open-sse/services/accountFallback.js:53](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/services/accountFallback.js:53), [src/lib/routing/connectionRecovery.js:26](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/lib/routing/connectionRecovery.js:26)).
- **`/v1/codex/models` is a new surface here and is not proposed.** The fork has no such route, and the existing `/v1/models` already answers a Codex CLI client in the `{"models":[...]}` shape, so a second route would add surface without adding a client-visible capability.

### Defensible focused residual

- **The served Codex-CLI catalog synthesizes the client-gating fields instead of carrying the upstream ones.** `toCodexModel` hard-codes `tool_mode: "auto"` and `multi_agent_version: null`, and the fork has no occurrence of `use_responses_lite`, `available_in_plans` or `minimal_client_version` in any response path ([src/app/api/v1/models/_shared.js:16](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/_shared.js:16)). The upstream catalog rows are already available verbatim in the dashboard parser, so extending the existing `/v1/models` Codex branch to pass the upstream Codex fields through would be a same-surface change: no new route, no new provider capability, no new endpoint. It needs offline coverage before it is attempted.
- **The Codex catalog is still account-blind in the two surfaces #2133 scoped.** The live resolver reads the catalog of the *first* active Codex connection ([buildModelsList.js:712](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/buildModelsList.js:712), [:1119](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/buildModelsList.js:1119)), and the auto-synced Codex catalog is stored under the provider key, so one account's plan becomes the provider-wide row ([src/lib/modelAutoSync/runner.js:201](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/lib/modelAutoSync/runner.js:201), [syncedModelsRepo.js:38](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/lib/db/repos/syncedModelsRepo.js:38)). Codex is per-plan upstream, and the fork's own sync layer already excludes provider-wide snapshots for exactly this reason on two other providers ([src/lib/modelAutoSync/catalog.js:32](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/lib/modelAutoSync/catalog.js:32)). Resolving the Codex catalog from the caller's scoped connections, using the #2133 scope mechanism, is the same-surface form of this residual; upstream's global merge is not an equivalent and must not be ported as-is. Any change here needs a product decision and offline tests first.

## #5560 — GPT-6.1 `[1m]` variants and extended-context routing

### Existing parity (verified equivalents)

- **Upstream's conditional marker handling already exists here in a more general form.** Upstream keeps the `[1m]` marker only when the registry resolves the bracketed id as a variant (`markerRoutable`), and strips it otherwise. The fork reaches the same outcome through `decodeClaudeCodeModelId`, which returns the id untouched when it is exactly routable and only strips the suffix when the unmarked id is routable ([src/app/api/v1/models/_claudeCompat.js:36](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/_claudeCompat.js:36), [src/sse/services/model.js:236](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/sse/services/model.js:236)). The fork's check is registry-wide rather than provider-scoped, so it covers every provider that publishes a bracketed id, not only Codex.
- **Registry variants already resolve to their base model.** Upstream's new rows rely on `upstreamModelId`; the fork's `getModelUpstreamId` already resolves registry rows through `upstreamModelId` for the `-review` quota family ([open-sse/config/providerModels.js:230](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/config/providerModels.js:230)), so the mechanism the upstream rows depend on is present.
- **The `[1m]` advertisement rule the fork uses is already evidence-bound.** `projectClaudeCodeModel` only advertises `[1m]` for a model whose resolved window is at least 1,048,576, and never widens the marker to another spelling ([src/app/api/v1/models/_claudeCompat.js:16](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/_claudeCompat.js:16)).

### Architecture-specific exclusions

- **There is no upstream `stripModelContextMarker` here, so the upstream diff site does not exist.** The fork has no `open-sse/utils/modelMarkers.js`; context suffixes are decoded on the Claude-shaped route only, through `decodeClaudeCodeModelId` ([src/sse/handlers/chat.js:490](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/sse/handlers/chat.js:490)). On the OpenAI-shaped routes a bracketed Codex id is forwarded verbatim and the Codex backend answers `model_not_found`; on the Claude-shaped route the suffix is stripped and the request lands on the base model window. That is the fork's established shape, not a port of the upstream strip.
- **The upstream PR's fourth change has no counterpart.** Upstream stops re-appending the marker to `requestedModel`; the fork has no `requestedModel` parameter in `handleSingleModelChat` at all.
- **The 872,000 window is an unverified claim in the upstream source itself.** The upstream PR states that the live Codex catalog reports `context_window: 500000`, `max_context_window: 872000` and `supports_experimental_context: false` for both 6.1 models, and that no prompt above 500k was sent, so 872k on the 6.1 pair is unverified. `supports_experimental_context` appears nowhere in the upstream tree, and `872000` appears only in the capability constant and its test. The fork has no extended-context Codex concept at all: no `[1m]` registry row for any Codex model, and no `CODEX_EXTENDED_CAPS` equivalent.
- **The fork's Codex context windows come from a different source than upstream's.** Upstream publishes a Codex-specific window per model (`gpt-6.1-sol` 272,000, `gpt-6.1-terra` 500,000). The fork derives the Codex window from the OpenAI API table — `CODEX_CATALOG_CAPABILITIES` reuses `OPENAI_API_CAPABILITIES` ([open-sse/providers/vendorModelCapabilities.js:125](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/providers/vendorModelCapabilities.js:125)) and the `*gpt-6.1-terra*` / `*gpt-6.1-sol*` patterns point at the same audited OpenAI rows ([open-sse/providers/capabilities.js:901](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/providers/capabilities.js:901)), both at 1,050,000. Adopting upstream's 872,000 constant would introduce a third number that neither source proves for this fork.
- **The upstream rows also carry flags this fork handles differently.** Upstream's `gpt-6.1-sol` / `gpt-6.1-terra` rows carry `responsesLite: true` and `thinkingLevels: ["low","medium","high","xhigh","max"]`; the fork's rows carry neither, and the fork derives effort levels from capabilities instead ([src/app/api/v1/models/buildModelsList.js:807](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/src/app/api/v1/models/buildModelsList.js:807)). The fork does use `responsesLite` for its own 6.2 rows ([open-sse/providers/registry/codex.js:64](../../../orq-tornf6-audit9r-code-5d940f68a5a3c723/open-sse/providers/registry/codex.js:64)). That flag difference is not part of the #5560 patch, and adding it would change dispatch shaping for a model this fork has not verified.

### Defensible focused residual

- None. The two candidate changes in #5560 are an advertised extended-context variant and its window. Both rest on a figure the upstream source itself marks unverified, and this fork publishes Codex windows from a different, already-sourced table, so adding the rows would advertise a capability the local sources do not support. The upstream chat-entry change is already covered above by the fork's own decode path. No Codex `[1m]` variant, no extended-context capability and no 872,000 constant is proposed.
