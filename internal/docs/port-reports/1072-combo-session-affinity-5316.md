# #1072 combo session affinity: 9router #5316

## Disposition

**Partial existing behavior; narrow combo-session functionality remains distinct and unimplemented.** This is an assessment only. No product, authentication, credential, test, or GitHub changes were made. No provider traffic was sent.

## Exact source and final diff

Inspected open [9router #5316](https://github.com/decolua/9router/pull/5316) at head `c0cd9e8e5b68b7629f5151e484f9d6b50fe19678` (unchanged when rechecked on 2026-11-21), with merge base `1855aa44473e88feac9d3f131b9c0c5fc9706b68`. The exact head is the merge of the source branch with that upstream base. Compared the final base-to-head diff, not only the PR summary: 55 changed paths, including 10 runtime service/config/handler utilities, combo dashboard controls, shared account/model-reference routing across chat and media, and focused tests. The affinity core is in `open-sse/services/combo.js`, new `open-sse/services/comboSession.js`, `open-sse/config/sessionAffinity.js`, execution-result normalization and model-reference parsing; account selection/admission changes are a separate, substantially broader slice.

The relevant combo contract is opt-in sticky behavior for fallback and round-robin. It retains both the successful combo member and the actual execution target (account) by session, scoped by client API key, with a process-local sliding two-hour TTL and 5,000-entry cap. It records only after usable JSON or stream content; failures and empty outputs do not establish success. If a pinned member/account becomes unusable, or routing inputs/policy no longer match, the mapping is invalidated/re-anchored. Concurrent first dispatches for the same session serialize. Once streamed output is committed, no new fallback starts. The final diff also adds strict/prefer account fallback policy and account constraints across many endpoints; those are not equivalent to combo-member affinity and are not recommended as part of a narrow follow-up.

## DurinDoor comparison

- **Already present:** `open-sse/services/combo.js` has ordered fallback, round-robin request-count rotation, weighted selection and fallback-winner pointer advancement. Conversation affinity for round-robin is keyed by combo and a derived conversation key, bounded to one hour/1,000 entries, but is active only when `comboStickyRoundRobinLimit > 1`. It records the starting rotation index before dispatch, rather than committing the actual successful fallback member. Failed pinned-member affinity is released by the #6733 path. Thus a repeated session with the default sticky limit of 1 rotates each request; fallback combos have no cross-request successful-member pin.
- **Already present for accounts:** `src/sse/services/auth.js` has session-affinity for round-robin provider selection and stateless `cache-affinity` account selection. Selection still runs after available-account filtering and respects key/account restrictions; an unavailable or excluded sticky account falls through to another eligible account. `tests/unit/provider-session-sticky.test.js` documents stable account choice, distinct-session distribution, re-selection when an account is excluded, and request-count behavior without a session. This does not pin the combo member that succeeded, and it does not prove a shared session namespace is isolated by client key.
- **Inapplicable #4975/System One:** #4975's System One decision model, adaptive confidence/hysteresis, strict-lock/per-turn smart policy, and its router-specific dashboard do not describe this narrow fallback/round-robin retention contract. DurinDoor uses Jev/task classification and existing smart-scoring/task routing, not System One. Do not infer adoption of #4975 or its decision/router features from this comparison.
- **Inapplicable #4704:** #4704's intelligence-score-managed combo membership, Artificial Analysis leaderboard refresh and range/exclusion editor concern how members are selected/configured, not which successful member a conversation retains. They remain a separate feature question.
- **Narrow residual:** successful-member/account re-anchoring across fallback turns, opt-in for both fallback and round-robin, success-only commitment, bounded expiry/capacity and invalidation when membership/policy/account eligibility changes. Key isolation and account admission must remain invariants if this is ever implemented. This report does not authorize auth/account-routing changes.

Read the existing local behavior in `open-sse/services/combo.js`, `src/sse/services/auth.js`, `open-sse/utils/sessionManager.js`, `src/sse/handlers/chat.js`, `tests/unit/combo-rr-fallback-advance.test.js`, and `tests/unit/provider-session-sticky.test.js`. These establish the distinctions above; no suite was run. No live provider, credential store, or runtime account data was accessed.

If the residual is later authorized for implementation, one ordinary offline fixture should seed two synthetic API keys with disjoint allowed connection sets and two synthetic eligible accounts per set. For each key, issue a sticky fallback combo request whose first model's first account returns a synthetic 429 and whose second account returns usable JSON; repeat the same session and assert the successful member/account is tried first. Then remove that account from the key's allowed set and repeat: assert it is never attempted, another account eligible to that key may serve, and the other key's session remains isolated. Use mocked handlers/auth selection and synthetic responses only; do not weaken key or account admission to make the pin succeed. This fixture would distinguish the missing success-committed combo pin from current request-count rotation while checking admission at the actual selection boundary.
