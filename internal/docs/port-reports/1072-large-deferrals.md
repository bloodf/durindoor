# #1072: qualification of remaining large and conflicting 9router ports

Reviewed 2026-11-20 against DurinDoor `1362dabff4f994ea6941705d5888fb9541b730a9` (worktree source) and current 9router PR metadata. All six upstream PRs remain open; #5655 is draft. This is a source, metadata, and test-definition review only. It does not claim runtime behavior or upstream acceptance.

## Decisions

### [#4291](https://github.com/decolua/9router/pull/4291) — compressed full request-detail archive and body analysis

Upstream currently proposes optional TimsLite/Zstd storage, time-forward deduplication, removal of request-body truncation, and a full-body analysis view (58 files; +10,152/−278). The fork already has request-detail observability, bounded row count and configured age cleanup, redaction, metadata/detail views, and an export endpoint: `src/lib/db/repos/requestDetailsRepo.js`, `src/lib/dataRetention/runner.js`, `src/app/api/logs/export/route.js`, `src/app/(dashboard)/dashboard/profile/page.js`. Existing tests include `tests/unit/usage-request-details-redaction.test.js`, `tests/unit/request-details-metadata-ui.test.js`, and `tests/unit/observability-enabled.test.js`.

Disposition: applicable need (large request bodies can be truncated), but not a direct storage replacement. Smallest complete slice is a separately configured, bounded full-body archive with explicit retention and deletion semantics, redaction before persistence, stable detail lookup/export, and UI analysis only for records whose full body is available. Preserve observability opt-in, current retention controls, lite-backup exclusion of `requestDetails`, and fail-closed behavior when archive data is unavailable. Do not silently make all bodies durable or change existing retention defaults. Owner decision needed on whether full bodies may be persisted, archive retention/cleanup and backup semantics, and whether this is enabled by an explicit setting. Ready slice: no; acceptance command therefore not applicable.

### [#5465](https://github.com/decolua/9router/pull/5465) — live model capability probing

Upstream proposes one real minimal request per model, persisted verdicts, retry scheduling, optional audio probes, and picker filters (11 files; +1,678/−2). The fork has static/live provider catalogs and capability metadata (`open-sse/providers/capabilities.js`, provider model discovery) but no per-model measured verdict store or probe-backed picker. Existing capability tests include `tests/unit/combo-capabilities.test.js` and `tests/unit/combo-capability-detection.test.js`.

Disposition: applicable gap, but the advertised probe is a real inference call and may incur cost, mutate provider state, consume quotas, or expose account activity. Smallest complete slice is an explicit user-triggered, one-model-at-a-time probe for supported providers, using the selected account scope, minimal deterministic payload, bounded concurrency/timeouts, and stored sanitized verdicts with clear staleness/clear controls. No background sweep, automatic paid calls, audio pass, or probe-driven admission/routing until owners approve policy. Preserve opt-in paid-provider behavior and existing account-scope checks. Owner decision needed on eligible providers, per-call consent/cost notice, persistence/retention, and automatic retry policy. Ready slice: no offline-only acceptance command.

### [#5466](https://github.com/decolua/9router/pull/5466) — leaderboard-based combo ordering

Current PR adds aihot.news scraping (including a sandboxed challenge script), caching, fuzzy bindings, rankings API and combo editor (38 files; +5,754/−681); it stacks on #5464, whose unique prerequisite must be checked before any port. Existing combo ordering/editing is local (`src/lib/combos/comboSort.js`, `src/app/(dashboard)/dashboard/combos/page.js`); the fork has no leaderboard data source, bindings or score-based sort. Related tests: `tests/unit/combo-management.test.js`, `tests/unit/combo-smart-scoring.test.js`, `tests/unit/combo-weighted-members.test.js`.

Disposition: applicable optional convenience, not a routing capability. Smallest complete slice is a pure offline ranking function over a supplied, versioned leaderboard snapshot, exact/owner-confirmed model bindings, stable tie handling, and an explicit reorder action that retains every combo member and leaves fallback execution unchanged. Do not import challenge-solving or silently fetch external data. Owner decision needed on an approved snapshot/source and freshness/license policy; review #5464 dependency. Ready offline slice if owner supplies the snapshot contract: `cd tests && node node_modules/vitest/vitest.mjs run --maxWorkers=2 unit/combo-management.test.js unit/combo-smart-scoring.test.js unit/combo-weighted-members.test.js`.

### [#5574](https://github.com/decolua/9router/pull/5574) — per-member System One criteria and combo prompts

Upstream adds member descriptions and router instructions for its Smart Router, plus per-combo prompts propagated through nested combos (13 files; +407/−19). DurinDoor has Jev tier classification, not upstream's per-member System One router; current combo strategy state and editor are in `src/app/(dashboard)/dashboard/combos/page.js`, while System One routing is guarded and implemented via `open-sse/rtk/systemInject.js` and provider-node routes. Existing combo tests include `tests/unit/combo-management.test.js`, `tests/unit/combo-access-control.test.js`, `tests/unit/combo-weighted-members.test.js`; the fork explicitly does not inject upstream's unsupported `systemPrompt` (`open-sse/rtk/systemInject.js`).

Disposition: partially applicable. Do not port member criteria into Jev tier classification or add an upstream Smart Router. The smallest complete local slice is optional per-combo prompt text appended at the established system-injection boundary, persisted through existing combo strategy settings, inherited outer-to-inner exactly once for nested combos, with size limits and empty-default compatibility. It must apply only to chat requests routed through combos; preserve client prompt order, provider-native formats, and System One/Network boundaries. Network remains its separately guarded node route and Provider Sign-in remains its own account/OAuth flow; neither becomes combo prompt configuration. Owner decision needed on prompt size and whether nested prompts concatenate or override. Ready offline acceptance: no deterministic focused test already covers this behavior; add tests with a later implementation before calling it ready.

### [#5655](https://github.com/decolua/9router/pull/5655) — opt-in Antigravity desktop BYOK/MITM and Windows controls

Draft PR combines direct provider routing, loopback MITM hardening, management-response adaptation, translator changes, and Windows install/restore controls (36 files; +2,292/−47). The fork already has Antigravity as a dedicated OAuth provider and executor, plus a separate MITM subsystem; see `open-sse/providers/registry/antigravity.js`, `open-sse/executors/antigravity.js`, `src/mitm/`, `tests/unit/antigravity-mitm.test.js`, and MITM lifecycle/security tests. This is not an absent Antigravity provider. A desktop BYOK selector is a separate integration.

Disposition: only a narrowly opted-in desktop-routing policy may apply. Smallest complete slice is the security core: disabled-by-default explicit policy, allowlisted provider/model targets, loopback-only listener, strict host/target checks, strip desktop credentials before forwarding, validate TLS, bound body/time, suppress raw request dumps, and prove no unrelated process is terminated. Keep Windows controls and translator changes independently reviewable. Preserve standard Antigravity OAuth/provider sign-in and do not fold credentials or BYOK into Provider Sign-in. Network configuration remains separately owned and must not be repurposed as a MITM setting. Existing relevant tests: `tests/unit/antigravity-mitm.test.js`, `tests/unit/mitm-launch-gate.test.js`, `tests/unit/mitm-sanitize-headers.test.js`, `tests/unit/mitm-peer-owner.test.js`, `tests/unit/mitm-server-bootstrap.test.js`. Owner/security review required for target policy, certificate trust lifecycle, platform support and management response semantics. No ready slice: deterministic offline acceptance command not applicable; this needs a separate security work order.

### [#5754](https://github.com/decolua/9router/pull/5754) — API keys restricted to selected accounts

Current PR proposes API-key account restrictions (52 files; +1,964/−424). Fork already stores combo connection allow-lists and API-key account scope, with intersection/admission coverage in `src/lib/combos/comboManagement.js`, `tests/unit/combo-connection-allow-list.test.js`, `tests/unit/api-key-provider-account-scope.test.js`, and `tests/unit/security-authorization-matrix.test.js`. This is comparable enforcement, but not proof the PR's key-management lifecycle or every dispatch path is covered.

Disposition: potentially applicable only as a gap audit and minimal extension of existing scope enforcement. Smallest complete slice is account-scope configuration on a key, validated against owned/visible connections, enforced before provider lookup/dispatch and at every fallback/combo member, with deny-by-default handling for stale/deleted IDs and redacted management responses. Preserve current admin/account checks and intersect key scope with combo allow-lists; never broaden a key's access. Owner decision needed on empty-scope meaning (unrestricted vs deny-all), legacy-key migration, CLI vs dashboard key administration, and deletion/revocation behavior. The source PR must be compared by exact changed paths before treating this as an implementation gap. Ready offline acceptance command: `cd tests && node node_modules/vitest/vitest.mjs run --maxWorkers=2 unit/api-key-provider-account-scope.test.js unit/combo-connection-allow-list.test.js unit/security-authorization-matrix.test.js`.
