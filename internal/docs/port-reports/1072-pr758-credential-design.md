## Proposed components and authorization

1. A management API owns enrollment, explicit enable and disable, status, manual retry, and deletion. Require an authenticated dashboard session or authorized CLI identity even when dashboard login is optional. Require fresh dashboard-password verification for enrollment, credential replacement, and enabling password-based recovery, following the sensitive database operation's rate-limited dual-auth pattern. Enforce same-origin or the existing authenticated CLI exception; never expose a secret in status responses. Bound input size and account count. A dashboard session alone must not silently enable recovery.
2. A provider-specific Antigravity adapter builds fixed OAuth endpoints and expected scopes using existing OAuth configuration. It validates the returned account identity against the enrolled connection before any update. A browser worker receives one scoped job and returns only a one-use authorization code and state through a private channel. It owns a fresh browser context and temporary profile, closes them on all exits, and has a hard deadline. No arbitrary URL, proxy, executable path, or browser flag comes from the request.
3. A scheduler service owns durable, non-secret job state and invokes the existing provider refresh path. It starts only under an explicit operator-enabled lifecycle, defaults off, and never starts as a side effect of a read endpoint. It does not create a second independent token writer. Its management status contains sanitized state, timestamps, and error categories only.

The login worker uses the explicitly approved `puppeteer`, `puppeteer-extra`, and `puppeteer-extra-plugin-stealth` dependencies. Stealth is not evidence that Google permits automated login or that login will succeed. Stop on CAPTCHA, MFA, account verification, changed terms, unfamiliar screens, or consent requiring a decision. Mark the connection as requiring interactive reauthorization; never solve challenges, skip security prompts, or accept terms on the user's behalf. An initial authorization must include informed consent for the requested OAuth scopes and for any optional recovery credential retention. Revoke consent by disabling recovery and deleting its retained credential.

## Secrets and lifecycle

Prefer the existing OAuth refresh token. Password retention is separately opt-in, off by default, and is not required for ordinary scheduling. Without that opt-in, an invalid refresh token leads to interactive reauthorization. A future implementation must define a dedicated encrypted recovery-credential record bound by authenticated associated data to connection ID and field. Use the existing storage key and encryption facilities with a distinct explicit secret classification, not the upstream crypto format or an opaque JSON blob presumed to be encrypted. Fail closed when the key is unavailable. Decrypt only in the authorized worker for the duration of a job; do not return plaintext or ciphertext through management APIs, logs, events, traces, crash reports, browser output, or normal exports. Scrubbed export excludes it; any credential-bearing backup or import needs explicit existing dual authorization and a reviewed portable encryption and key policy. Backups already made cannot be remotely erased.

Enrollment or replacement writes only the selected connection after verified OAuth exchange and identity matching. Password replacement is an explicit operation; a blank or omitted field never deletes or overwrites a stored secret. Disable stops new jobs and invalidates in-flight work but retains the credential until the user requests deletion. Deletion removes the recovery credential and disables recovery atomically, without deleting existing access or refresh tokens. Connection deletion cascades its recovery record. Reset, import, restore, and key rotation need explicit migration and rollback plans; never rewrite existing stored secrets merely to enable this feature. Clear transient buffers and close browser contexts promptly, while recognizing JavaScript cannot guarantee memory zeroization. Remove temporary browser files on success, failure, cancellation, and startup cleanup, with restrictive permissions.

## Rotation, concurrency, and recovery

Schedule from persisted expiry with a bounded lead time and jitter. Missing expiry does not justify an immediate repeated login. A scheduled refresh, gateway refresh, manual retry, reauthorization, disable, deletion, and credential edit must share a per-connection cross-process ownership protocol before any provider call that can consume a single-use refresh token. A compare-and-swap at write time alone is insufficient: two callers may already have spent the same token. Add a database-backed lease with unique owner, generation, expiry, and a fencing token, acquired atomically on each supported database. All existing refresh call sites must participate before the scheduler can be enabled. Renew the lease during a bounded operation and stop work on renewal failure. Completion writes token pair, expiry, and job state in one transaction only if the lease generation, credential revision, active state, and account identity still match. Preserve the old refresh token when the provider legitimately omits a replacement. A stale worker discards its result and never overwrites a newer reauthorization. Do not hold a database transaction open during network or browser work.

A lease cannot undo an external token exchange after a crash or partition. Do not assume expired leases make replay safe for a single-use token. Persist an attempt marker before dispatch, distinguish a known pre-dispatch failure from an uncertain provider outcome, and on uncertain outcome stop automatic reuse and require reconciliation or interactive reauthorization. A timeout, process kill, or lease loss after dispatch is uncertain unless the provider contract proves otherwise. No fencing token can fence the external provider. Evaluate the same ambiguity for authorization-code exchange. On startup recover due jobs from durable state without replaying uncertain operations. Duplicate ticks coalesce; cap global and per-account browser concurrency, queue length, operation duration, and resource use. Shutdown cancels work, closes contexts, and records uncertainty when dispatch may have occurred.

Disabling recovery or deleting its password advances the commit fence. If an exchange was dispatched or already uncertain, the lease remains uncertain even though recovery is disabled. A reauthorization that retains the same refresh token cannot resolve that uncertainty; a newly issued refresh token advances the generation and permits a new lease. Recovery and the scheduler remain disabled pending the other gates in the port report.

This is a partial fix. The generic Antigravity refresh fallback without a connection ID remains open: its reachability with stored credentials has not been established, and it may bypass the lease. Cross-route concurrency and crash coverage across both database engines remains incomplete. A follow-up must resolve those gaps and obtain independent review before this issue can be considered closed.

Classify invalid grant as reauthorization required, optionally starting one explicitly enabled password recovery attempt after the refresh lease is acquired. Authentication rejection, CAPTCHA, MFA, policy or consent changes, and account mismatch stop automatic attempts. Network and rate-limit failures before dispatch use bounded exponential backoff with jitter and provider `Retry-After`, with a maximum retry budget. Unknown or post-dispatch failures use the uncertainty rule. Preserve the last usable access token until expiry; never log token values, passwords, callback URLs, page text, screenshots, or raw provider errors. Provide actionable redacted error categories and an operator reset for exhausted retry budgets.

## Network and browser isolation

Use a sandboxed, unprivileged browser and keep Chromium's sandbox enabled. A context is not an operating-system security boundary; run the worker with a restricted filesystem, no host credentials or debugging port, resource limits, and enforced network egress policy. Permit only reviewed HTTPS Google OAuth and identity endpoints and required static resources, by exact hostname and port. Apply enforcement to every navigation, redirect, subresource, popup, worker, WebSocket, DNS resolution, and actual connection, not just the initial URL. Reject private, loopback, link-local, metadata, multicast, IPv6-mapped and nonpublic destinations, DNS rebinding, alternate IP encodings, insecure schemes, and unapproved proxies. Browser request interception alone is not sufficient DNS or connection enforcement. If the deployment cannot enforce these restrictions, leave browser login disabled.

Generate state and PKCE verifier per attempt with cryptographic randomness. Match the callback's scheme, host, port, and path exactly, reject duplicate or missing parameters and mismatched or replayed state, and intercept the expected callback before network access; never use a URL prefix match or send a code to a local listener. Exchange the code only at the fixed token endpoint with the bound verifier. Validate issuer, audience, expiry, and stable subject using the existing verified identity path before binding the connection. If a necessary Google redirect or resource is not in the reviewed allowlist, fail closed and update the reviewed provider policy before enabling it.

## Dependencies, deployment, and coordination

A future implementation must add the three approved packages to the appropriate runtime manifest and lockfile, pin a compatible Chromium revision, and account for install scripts, browser download size, supported architectures, licensing, vulnerability updates, and offline installs. No dependency changes are made by this report. Explicitly trace runtime and transitive dependencies into Next standalone output and the packed `cli/app` artifact, rather than assuming the upstream Docker copy script matches DurinDoor's build. Verify Chromium and its system libraries in the supported image, run non-root with sandbox support, and document unsupported platforms. Do not download a browser at service startup or silently fall back to an unverified system binary. Keep normal gateway startup functional when the optional worker is disabled or unavailable. Review package supply chain and the cost of distributing Chromium before shipping.

This work crosses authentication, credential storage, database, shared refresh, packaging, and deployment boundaries. Coordinate with concurrent owners of those areas before implementation and rebase the design against their merged changes. It requires full local CI, independent security and integration review, both database engines, standalone and packed CLI smoke checks, and separate owner-controlled disposable Docker validation under the repository's gate policy. The design is not authority to change the production gateway or host services.

## Acceptance tests for a future port

All tests use synthetic credentials, fake clocks, controlled DNS and fake provider/browser transports unless an owner separately approves a disposable live environment.

- Authorization: optional dashboard login does not expose management routes; missing session, wrong password, cross-origin request, excessive body, and unauthorized CLI are rejected without a job or secret write. A permitted enable records explicit consent; status and ordinary exports contain no secrets.
- Lifecycle: enrollment binds a verified subject; wrong identity, bad state, duplicate callback parameters, replay, wrong callback origin or path, and token exchange failure preserve the old row. Omitted password preserves it; disable fences an in-flight job; deletion removes only recovery material. Missing or wrong encryption key fails closed. Test scrubbed and authorized backup paths and both database engines.
- Rotation: concurrent scheduler, manual, and gateway refresh across processes result in one provider dispatch. A rotated token pair persists atomically, an omitted replacement preserves the prior refresh token, and reauthorization or deletion during work prevents a stale commit. Lease expiry and fencing prevent stale commits; crash after dispatch enters uncertain state and never blindly reuses the token. Verify restart, clock changes, lease renewal failure, and database unavailability.
- Failures: bounded retries honor `Retry-After`, survive restart without a burst, and stop at the budget. CAPTCHA, MFA, terms, consent changes, invalid grant without opted-in recovery, and wrong account require user action. Assert cancellation and every error close the context and delete temporary profiles. Assert logs, traces, API responses, and exceptions contain no synthetic secret or callback code.
- Isolation and packaging: block redirects and subresources to loopback, private IPv4 and IPv6, metadata, rebinding, alternate encodings, WebSockets, and popups at the actual network boundary. Verify exact allowed callback interception and no local callback connection. Exercise a fake browser through standalone and packed CLI artifacts with the feature enabled and disabled; verify missing Chromium fails closed without breaking gateway startup. Run sandbox and egress checks in a disposable owner-controlled container.

## Review corrections and implementation gates

This section takes precedence over conflicting statements above. It specifies required work, not capabilities already present. Product work remains on hold. No password recovery or scheduler may ship until all gates below pass independent security review and behavioral tests.

- Authorization: add every management endpoint to the dashboard guard's always-protected policy. Verify the actual session or machine-bound CLI token at the handler boundary as well as a rate-limited fresh dashboard password for enrollment, replacement, and enablement. If no password is configured, refuse these operations until one is configured; optional dashboard login is not an authorization bypass. Apply the existing origin and CSRF rules to browser requests and test the CLI exception. Do not assume the database route's policy automatically applies to new routes. Require explicit consent for each connection and scope; do not automate a new or changed consent screen.
- Identity and OAuth: `src/lib/oauth/services/antigravity.js` currently builds an authorization request without PKCE, exchanges a code without a verifier, and retrieves user info without establishing the verified identity path claimed above. Implement and test PKCE support with the actual Google client and redirect configuration before enabling this flow. Obtain a stable subject through an authenticated Google userinfo response or a correctly validated ID token, and persist a verified subject on enrollment. A legacy connection without a verified subject requires interactive reauthorization to establish one; an email match is insufficient. If the provider cannot support these requirements, leave recovery disabled.
- Encryption: `src/lib/crypto/columnCrypto.js` creates a master key when absent, so simply calling it does not prove an existing credential can be decrypted. Distinguish first enrollment from missing key for an existing record and fail closed before key creation in the latter case. Define an unambiguous versioned AAD encoding of connection ID and field, classify the field as sensitive throughout storage and export, and verify tampering, wrong AAD, missing key, restore, and both database engines. Do not claim existing backup portability until a reviewed key transfer design exists; omit recovery credentials from all exports and imports in the initial port.
- Rotation: enumerate and migrate every Antigravity token exchange and writer, including gateway forced refresh, proactive refresh, manual actions, OAuth replacement, and any catalog or background caller, to one database-coordinated protocol before enabling scheduling. A process-local mutex or existing refresh helper alone is insufficient. Persist a generation, owner, expiry, and pre-dispatch attempt marker using atomic database transactions and database time. Condition every commit on the current generation, lease, connection existence, and enablement. Disable, deletion, and reauthorization advance the generation atomically. Lease expiry after dispatch marks the attempt uncertain and blocks another dispatch, including from gateway and manual paths; it does not authorize retry. Persist token pair and clear the marker in the same transaction. If the result cannot be committed, require reconciliation or interactive reauthorization. Document the availability impact and test actual multi-process races on SQLite and PostgreSQL.
- Isolation: use an independently enforced worker network boundary that checks the resolved address at connection time, including redirects, DNS changes, WebSockets, and browser child processes. Deny direct egress around that boundary and block QUIC, DNS-over-HTTPS, and proxy bypasses unless explicitly controlled. The token exchange and userinfo requests also use fixed endpoints with enforced destination policy and no ambient proxy credentials. If the deployment cannot prove this boundary, disable browser recovery. A callback interception must prevent the request before any local connection, and match exact scheme, host, port, and path, with one state and one code.
- Logging: map errors to an allowlisted category at each browser, OAuth, IPC, scheduler, and API boundary. Never forward raw exceptions, URLs, browser console output, page text, screenshots, network dumps, tokens, passwords, or codes to logs, traces, events, or responses. Existing Antigravity methods include raw provider response bodies in exceptions, so do not pass those exceptions through unchanged. Disable browser diagnostics and crash artifacts containing session data; test synthetic secrets through every failure path.
- Packaging: the root manifest does not currently declare the three Puppeteer packages, and `next.config.mjs` and `cli/package.json` do not establish their inclusion or a Chromium distribution. Before implementation, decide and review exact pinned dependencies, lockfile changes, supported OS and architecture, compatible Chromium version, license, browser installation and update mechanism, and standalone, Docker, and packed CLI inclusion. No download or dependency install may occur at gateway startup. Browser absence, unsupported platforms, or failed sandbox setup must disable recovery without stopping the gateway. A fake-browser artifact test proves module inclusion and fallback, not real Chromium sandbox or egress enforcement; run separate owner-controlled real-browser boundary tests before release.

The acceptance tests above are release criteria for a future implementation. Use synthetic identities and a controlled OAuth server for unit and integration tests, with explicit crash points before dispatch, after dispatch, after provider success, and before commit. Test actual worker process termination and restart, rather than only mocking a rejected promise. Prove the multi-process protocol through the public gateway and management entry points. Use a disposable owner-controlled container and controlled DNS and network endpoints for real egress tests; do not require real Google credentials or exercise Google login in CI. A real provider compatibility check requires separate operator authorization and disposable credentials. Failure to demonstrate any gate leaves the feature disabled and the port blocked.
