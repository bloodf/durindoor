# PR 758 credential rotation port

The management API now rejects enrollment, replacement and enablement until verified subject provenance and scope-bound consent are implemented. Status does not treat legacy editable subjects or legacy enable flags as evidence of recovery readiness. Existing retained credentials are unchanged and can still be deleted. This is a fail-closed interim guard, not a recovery implementation.

The scheduler is hard-disabled pending the release gates below. An enable request records and returns disabled, and an existing enabled setting cannot start a tick. The stored-credential browser caller remains unimplemented; this does not establish recovery parity.

## Stored-credential wiring reassessment

### Generic refresh follow-up

The generic Antigravity and `agy` handlers now refuse refresh without a connection ID. The exported generic `refreshAccessToken` also refuses both aliases, so it cannot bypass the connection-bound handler. `tests/unit/antigravity-refresh-no-id.test.js` exercises all three generic entry points with synthetic credentials and asserts that no request is dispatched.

This does not establish that every stored connection uses the lease. `AntigravityExecutor.refreshCredentials` still calls its network method directly. The fallback in `chatCore.js`, and the refresh paths in `embeddingsCore.js` and `imageGenerationCore.js`, call executor refresh directly. Their reachability with stored Antigravity credentials and their cross-process behavior remain unproven. Do not enable recovery or the scheduler until those paths are fenced or proven unreachable, with public-entry-point concurrency and crash evidence on both database engines and independent security review. Verified identity provenance, scope-bound consent, and the stored-credential caller remain unimplemented.

On this checkout, the new generic-entry-point file passed both tests. A run of that file with `antigravity-recovery-wiring-758.test.js` and `antigravity-rotation-758.test.js` passed 26 tests and failed one: the dispatched-worker management-fence test raised `SQLITE_BUSY` (`database is locked`). An earlier run without the native SQLite binding failed three worker tests; rebuilding the local binding allowed the rerun. The lock failure remains unresolved and the run is not a SQLite concurrency gate. PostgreSQL cross-route tests and independent review were not run for this follow-up.

### Blockers for the production caller

- The connection's `providerSpecificData.antigravitySubject` is editable connection data. The OAuth mapper writes userinfo there, but the rotation route and lease seed also accept that same field without proof of its origin. Neither its presence nor the copied lease subject proves a verified Google identity. A trusted binding must be written only by a verified interactive OAuth exchange, and recovery must compare the recovered verified subject to that binding before committing tokens. Legacy rows require interactive reauthorization.
- The enable route accepts no explicit scope consent, and `enableAntigravityRecovery` persists only a timestamp and subject. A safe implementation needs an explicit retention choice and the exact approved scope set bound to the connection and credential revision, with changed scopes requiring renewed consent. The current timestamp cannot be migrated as consent.
- The lease and refresh protocol must atomically fence that trusted binding and consent against replacement, disable, deletion, and in-flight completion. `leaseSql.js`, `refreshProtocol.js`, and their rotation test are owned by the separate fence work; coordinate the interface and its SQLite and PostgreSQL tests before wiring a caller.
- A stored-password caller must not run until the verified identity and consent checks, the shared dispatch protocol, independently enforced sandbox and egress, and cross-process entry-point evidence all pass review. Browser environment flags do not prove those boundaries. Existing enroll and enable endpoints can still record a credential or enabled state; neither constitutes authorization to execute recovery.

The management `enable` action currently records `consentRecordedAt` without receiving an explicit consent choice or binding consent to scopes. That timestamp is not evidence of informed consent. Enrollment stores a password against an existing subject, but does not verify a browser callback or the recovered account identity. `recoveryPasswordForJob` and `runBrowserRecovery` have no production caller. Unknown browser screens and the full account-identifier flow have not been proven by browser fixtures.

The browser helper's two environment variables are configuration assertions, not proof of a Chromium sandbox or enforced network egress. They must not be treated as release authorization. Cross-process coverage through every required gateway and management entry point, independent security review, and the real-browser isolation gates remain unproven. The scheduler remains hard-disabled; do not invoke the browser helper with stored credentials or enable recovery on this evidence.

The focused `antigravity-recovery-wiring-758.test.js` file covers the disabled scheduler, callback shape and state, browser consent and challenge stops, unauthenticated status access, and connection-bound encrypted synthetic passwords. It does not establish a production recovery caller, verified recovered subject, or informed consent for credential retention.

## Follow-up: retry reset status

Once the database clock shows that the lease has expired, reset records and reports `uncertain_dispatch`; it cannot clear that state. The focused SQLite test covers both states. The browser worker can enter a supplied password on the recognized Google password screen. It stops at consent and security challenges without clicking them. The worker has no production caller supplying the stored credential, and it does not enter an account identifier or handle unrecognized login screens. ## Upstream disposition

| Upstream behavior | Disposition |
| --- | --- |
| Isolated browser context and stored recovery password | Separate encrypted recovery table. Temp profile mode `0700`, removed on every exit. Global browser cap 1. |
| Types the Google password and clicks consent or a challenge | The worker types a supplied password only on the recognized Google password route and stops on consent or security challenges. ## Review corrections

1. **PKCE and subject.** Dashboard `flowType` is `authorization_code_pkce`. Missing challenge or verifier fails closed. Subject is userinfo `sub`, or v1 `id` when `sub` is absent. `openid` was not added. Sign-in still succeeds when the subject is absent. Enrollment and enablement refuse recovery until `providerSpecificData.antigravitySubject` is a non-empty string. Interactive reauth and a changed refresh token advance the generation. Email is not an identity check.
2. **One writer.** Both network dispatch sites use the lease: `open-sse/executors/antigravity.js` `refreshCredentialsDetailed`, and `refreshAntigravityProvider` for `antigravity` and `agy`. The handler commits inside the lease and sets `rotationCommitted`, so `checkAndRefreshToken` does not write again. The executor does not acquire a second lease. `checkAndRefreshToken` does not take the lease at the top. Public `refreshCredentials` and `refreshGoogleToken` still return `null` or `{error:"invalid_grant"}`.
3. **Encryption and export.** `masterKeyPresent` reads and does not mint. First enrollment may mint through `encryptField`. An existing recovery row with a missing key fails closed. AAD is `antigravity-recovery:v1:<connectionId>:recoveryPassword`. The recovery password is not stored in `providerSpecificData`. Export does not select the lease or recovery tables. Import rejects those payload keys and drops rotation rows whose connections are gone. A matching refresh-token revision keeps `dispatched`, `uncertain`, and `reauth`. A different token advances the generation.
4. **Browser boundary.** `classifyBrowserUrl` intercepts or blocks before DNS. `evaluateBrowserRequest` allows a resolution only when every address is public. Reviewed HTTPS port 443 hosts: `accounts.google.com`, `oauth2.googleapis.com`, `www.googleapis.com`, `openidconnect.googleapis.com`, `ssl.gstatic.com`, `www.gstatic.com`, `fonts.gstatic.com`, `apis.google.com`. `assertPublicUrlResolved` is not reused. Recovery launches only when `DURINDOOR_ANTIGRAVITY_BROWSER_RECOVERY=1` and `DURINDOOR_ANTIGRAVITY_EGRESS_ENFORCED=1`. Tests inject a browser with `boundary: "test"`. The management route does not accept a caller-supplied browser.
5. **Route, logs, packaging.** `/api/oauth/antigravity/rotation` is on `ALWAYS_PROTECTED`. The handler checks JWT or machine CLI, same-origin (CLI exception), and a rate-limited `x-9r-password` for enroll, replace, enable, and scheduler enable. The built-in default password is refused for those actions. Body limit 8192. `cli/package.json` does not depend on puppeteer.

## Lease details that the tests cover

- SQLite: parent `BEGIN IMMEDIATE` plus the quota write lock; two worker threads acquire; exactly one claim and one `busy`.
- A `dispatched` lease that has not expired stays `dispatched`. The next acquire is `busy`, including after `SIGKILL` of the holding process. Expired `dispatched` becomes `uncertain` on the next acquire and blocks reset, including `force`.
- An aborted browser navigation still returns a captured callback code. That check uses an injected browser, not Chromium.
- Five non-consuming releases exhaust the pre-dispatch budget. `force` still acquires. Reset works only from `idle`.
- `invalid_grant` is `reauth`, not `uncertain`. HTTP 429 is non-consuming backoff. Documented shortcut: `ponytail: 429 treated as non-consuming; upgrade if a provider trace shows rotation on 429`.

Migration 37 creates both tables. PostgreSQL uses `translateCreateTable`, so epoch-millisecond columns are `BIGINT`. The generator wrote `src/lib/db/migrations/postgres/037-antigravity-rotation.js` and the postgres index. Those files are generated.

## Gates not demonstrated

- Pinned Chromium sandbox. Chrome-for-Testing `157.0.8103.78` was not downloaded. System Chrome 158 is not a substitute.
- Owner-container egress, including browser child processes, redirects, QUIC, and DNS-over-HTTPS.
- Interception before any local connection. The system-Chrome measurement accepted TCP connections.
- A clean stealth-plugin load.
- Real Google credentials or a live token exchange. None were used.
- Fake-browser and injected-browser checks prove fail-closed behavior, profile cleanup, and callback capture after an aborted navigation. They do not prove a Chromium sandbox.

Leave `scheduler` off and leave both browser environment variables unset until those gates pass. Recovery is not launched from `invalid_grant`. This is not full parity with upstream PR 758.
