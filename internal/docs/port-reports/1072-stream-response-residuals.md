## DeepSeek DSML in buffered responses (review residual)

#2068 added DSML decoding to the streaming path and to the buffered JSON completion, and #2072 added provider-content normalization to the forced-SSE → JSON path. The two never met: `handleForcedSSEToJson` (provider forced streaming while the client asked for a JSON body) aggregates the upstream frames into plain text and projects that text into the client dialect without decoding it. A client asking for Chat Completions, Claude Messages, Gemini or Responses JSON therefore received the raw `<|DSML|…>` markup instead of a structured tool call, while the surrounding text, reasoning and usage were delivered normally.

The buffered path now runs the same normalizer before the client-format projection, following the #2072 precedent: `normalizeDsmlCompletion` decodes the aggregated OpenAI completion, and `normalizeDsmlClaudeMessage` decodes the native Claude message that overlays the projection and the native Claude body of a non-streaming provider reply (DeepSeek also serves a Claude transport). A decoded frame keeps its tool id, arguments and surrounding literal text; existing structured calls, reasoning and usage are preserved; the turn reports the tool-call finish reason; and the response is still delivered as one JSON body. Frames the parser does not recognize — malformed, incomplete, oversized or literal text — stay text, and models outside the DeepSeek family are untouched. The already shipped streaming normalization is unchanged.

Evidence: `tests/unit/deepseek-dsml-buffered-response-review.test.js` covers all four client formats, every split point of a frame, structured calls that already exist next to a frame, ordinary provider text, invalid and literal snippets, non-DeepSeek models, the native Claude transport, a buffered provider body answered as client SSE and the streaming path. No provider calls, browsers, Docker or full-suite runs were used.
