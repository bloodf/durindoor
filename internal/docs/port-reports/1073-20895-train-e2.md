Tests: `#20167 Claude stream: parameterless tool closes with {} arguments`.
- **#20204** — partly ported, partly already covered.
  - Ported: bare block-object `content` for system and user messages, empty system text dropped, MIME-wrapped base64 compacted for images, PDFs and tool-result images, and a positive `budget_tokens` for `thinking: {type: "enabled"}` without one (in `openai-to-claude.js`); the rotating billing line removed from Gemini and Antigravity system text and inline tool-result media kept as Gemini media parts (in `openai-to-gemini.js`). Tests: `#20204 OpenAI → Claude request fixes` and `#20204 OpenAI → Gemini request fixes`.
  - Already covered, assertions added: Claude temperature (kept unless thinking is active, via `openaiToClaudeRequest.finalize`) and the Gemini 4 sampling omission (`applyGemini4RequestRules`, including a `models/` prefix).
  - Not changed: forced tool choice. DurinDoor already keeps thinking and downgrades a forced `tool_choice` to `auto` (`enforceClaudeToolChoiceThinking`), which avoids the same upstream 400; switching to dropping thinking would change that behavior. Remote tool-result image URLs stay visible in the Gemini result text, as an existing conformance test requires; only inline media moves to its own part.
  - Not applicable: the Antigravity system-role change; DurinDoor's envelope never merges system text into `contents[0]`.
- **#20206** — partly ported, partly already covered.
  - Ported: a Gemini image part that carries a thought signature is no longer swallowed (`gemini-to-openai.js`), and images DurinDoor cannot attach to a Kiro request are named in the message text (`openai-to-kiro.js`). Tests: `#20206 Gemini response, Claude → Gemini and Kiro`.
  - Already covered, assertions added: explicit Gemini 2.5 Flash thinking disable (central `applyThinking`), `[Tool error]` kept on unsigned Claude tool results, and Kiro `status: "error"` from the tool message's `is_error` flag.
  - Not ported: Gemini 2.5 Pro still receives a zero thinking budget for a disable request, because that comes from the shared capability table (`*gemini-2.5*`), not the translator, and an existing test pins a zero budget for it.
  - Not applicable: the trailing think-tag buffer (DurinDoor's Gemini stream converter has no textual reasoning-tag parsing) and the Kiro conversation-id seed (DurinDoor derives the id from the session resolver, not from the clock line).
- **#20240** — not applicable, no product change. DurinDoor has no `<previous_tool_result_context>` wrapper or content escaping; replayed tool results are plain `[Historical tool result for …]` text. A test asserts a literal `&` is not rewritten.

## Ported in this unit

- **#20293 Mistral subscription quota and plan** — not applicable, no product change. DurinDoor has no Mistral usage mapper: `open-sse/services/usage.js` has no `mistral` handler, `open-sse/config/providerQuota.js` has no Mistral adapter config, `mistral` is not in `USAGE_SUPPORTED_PROVIDERS`, and `src/lib/usage/providerLimits.js` does not exist. The upstream change extends an existing fetcher; here it would be a new billing endpoint integration, which this lane excludes. Proof: `tests/unit/omni-nov21-provider-usage-plans.test.js` pins the missing handler, adapter and feature flag.
- **#20347 Command Code plan aliases and caps** — not applicable, no product change. The upstream patch edits `open-sse/services/usage/command-code.ts` (`PLAN_ID_ALIASES`, `PLAN_CREDIT_CAPS`, credits total and used from the cap) and reads the `/alpha/billing` endpoints. DurinDoor has no Command Code usage mapper (`commandcode` and `command-code` have no usage handler, quota adapter or usage feature flag; only the executor, model catalog and translators exist), so there is no current fallback to amend. Adding the fetcher would be a new endpoint integration. Proof: `tests/unit/omni-nov21-provider-usage-plans.test.js`.
- **#20372 plugin onRequest once per client request** — not applicable, no product change. DurinDoor has no plugin `onRequest` hook: `open-sse/handlers/chatCore.js` runs no plugin gate, there is no `src/lib/plugins` module and no hook registry, so there is no per-attempt call to memoize across account failover. Adding the gate would introduce a plugin system, which this lane excludes. Proof: `tests/unit/omni-nov21-chatcore-request-a.test.js` (#20372 block) pins the absence of the hook runner, gate and `onRequest` registration under `open-sse/` and `src/`.
