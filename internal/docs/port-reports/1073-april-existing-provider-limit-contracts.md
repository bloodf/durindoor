## Current implementation and fixture evidence

**MiniMax / MiniMax-CN.** Both are installed providers with API-key usage enabled in [`minimax.js`](../../../open-sse/providers/registry/minimax.js) and [`minimax-cn.js`](../../../open-sse/providers/registry/minimax-cn.js). [`usage.js`](../../../open-sse/services/usage.js) dispatches both to [`usage/minimax.js`](../../../open-sse/services/usage/minimax.js), which tries the configured endpoint sequence, handles token-plan and coding-plan count semantics separately, surfaces per-model quota rows, supports count and percentage-only M-series data, and formats `MiniMax-M*` / `general` as `M-series`. The typed quota path also has both provider configs in [`providerQuota.js`](../../../open-sse/config/providerQuota.js) and a `minimax` adapter in [`quota/providers/codingPlans.js`](../../../open-sse/services/quota/providers/codingPlans.js).

Offline fixtures cover token-plan usage-count rows, coding-plan remaining-count rows, non-text model rows, percentage-only M-series data, and stale/error handling in [`minimax-usage.test.js`](../../../tests/unit/minimax-usage.test.js). The typed adapter fixture checks endpoint fallback and count semantics in [`provider-quota-fetchers.test.js`](../../../tests/unit/provider-quota-fetchers.test.js). The public #1516 patch adds an older fetcher with a representative text-model selection and two aggregate `session (5h)` / `weekly (7d)` rows; current behavior is broader and already covers its demonstrated presentation goal.

**CrofAI.** The provider itself is already installed in [`crof.js`](../../../open-sse/providers/registry/crof.js), and the typed quota config maps its `/usage_api/` response through the `crof` adapter in [`providerQuota.js`](../../../open-sse/config/providerQuota.js), [`quota/providers/index.js`](../../../open-sse/services/quota/providers/index.js), and [`quota/providers/balances.js`](../../../open-sse/services/quota/providers/balances.js). The normalizer preserves the API's contract without guessing a plan cap: `usable_requests` becomes an unknown-limit `requests:daily` row when present, and `credits` becomes an unknown-limit `balance:usd` row. A null daily field omits only the daily row. [`provider-quota-normalizers.test.js`](../../../tests/unit/provider-quota-normalizers.test.js) covers separate daily/credit dimensions, exhausted versus available state, and rejection of an empty payload; [`provider-quota-policy.test.js`](../../../tests/unit/provider-quota-policy.test.js) checks daily exhaustion before balance fallback.

The UI's generic quota path selects providers using [`USAGE_SUPPORTED_PROVIDERS`](../../../src/shared/constants/providers.js), derived from registry `features.usage`; API-key eligibility is separately derived from `features.usageApikey`. CrofAI's registry entry currently declares neither flag. Thus typed provider quota retrieval and normalization exist, but the usage feature allowlists omit CrofAI, leaving the existing UI refresh/visibility wiring as the demonstrated narrow gap. The current typed metadata intentionally cannot provide a measured percentage or reset countdown because the normalized API fields do not contain a total allocation or reset timestamp.

## Dispositions

- **#1516 — Do not port; already covered and superseded.** MiniMax and MiniMax-CN are configured and present in the current legacy usage and typed quota paths. Existing offline tests verify the endpoint and model-quota contracts, and current usage presentation is more complete than the PR's text-only aggregate rows. No missing setup or display behavior was demonstrated.
- **#1606 — Do not port its usage-fetcher implementation; accept only registry eligibility wiring as a narrow gap.** CrofAI provider setup and a typed `/usage_api/` quota adapter already exist. The public patch's guessed 1,000-request total, synthesized 05:00 UTC reset, and unlimited `$` credit display are not represented by the current typed contract and should not replace its unknown-limit rows. The observable gap is that CrofAI lacks the registry usage feature flags consumed by current support lists. If the intended Limits UI continues to use those lists, the narrow change is to enable `usage` and `usageApikey` for the existing `crof` registry entry; do not add a second endpoint fetcher or inferred quota metadata.

## Offline acceptance for the narrow CrofAI gap

After the registry flags are enabled, ordinary offline checks should establish that `USAGE_SUPPORTED_PROVIDERS` and `USAGE_APIKEY_PROVIDERS` include `crof`, the existing typed fixture still produces only `requests:daily` and `balance:usd` with unknown limits, null `usable_requests` omits the daily row, and the Limits UI offers CrofAI for its existing snapshot/refresh path. Use mocked responses only; no credential or provider access is needed. Relevant existing coverage is `tests/unit/provider-quota-normalizers.test.js` and `tests/unit/provider-quota-policy.test.js`; add or adjust an offline registry/UI assertion if those lists are the actual blocker.
