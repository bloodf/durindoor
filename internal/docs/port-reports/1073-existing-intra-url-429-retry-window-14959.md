# #1073: Existing same-URL 429 retry window

## Source comparison

Reviewed the named OmniRoute PR [#14959](https://github.com/cheaper-inference/OmniRoute/pull/14959), integration commit [`4b120aa0ad4cf31c640145527611bd94d59dad5d`](https://github.com/cheaper-inference/OmniRoute/commit/4b120aa0ad4cf31c640145527611bd94d59dad5d), against supplied PR head [`0628c03ed6c191fac69f00a803e31da1b71c99dd`](https://github.com/cheaper-inference/OmniRoute/commit/0628c03ed6c191fac69f00a803e31da1b71c99dd). The integration patch changes OmniRoute `open-sse/executors/base.ts` by checking `shouldSkipIntraRetryFor429(response)` before its existing same-URL 429 retry. The new helper prefers `Retry-After`, otherwise parses a detailed JSON retry hint from a cloned body, and skips the same-account retry when the hint exceeds 4,000 ms. Its accompanying tests cover long header/body hints, short hints, no hint, and keeping the body readable. The patch's changelog describes handing the 429 back for rotation/lockout after one upstream call.

This report compares that named runtime patch, not the rest of the PR or later changes, to the current fork runtime.

## Local behavior and finding

**Finding: demonstrated gap.** The active path exists, but only when effective policy grants at least one 429 in-place retry:

- [`open-sse/config/runtimeConfig.js`](../../../open-sse/config/runtimeConfig.js) sets `DEFAULT_RETRY_CONFIG[429]` to zero and retains legacy `RETRY_CONFIG` of two attempts at 2,000 ms. The effective executor config merges defaults with provider config. Therefore the usual default alone does not create a 429 retry; provider-specific `retry` config or an explicit operator `requestPolicy` can enable it.
- [`open-sse/providers/registry/opencode.js`](../../../open-sse/providers/registry/opencode.js) configures seven 429 retries at 800 ms. The shared [`open-sse/executors/base.js`](../../../open-sse/executors/base.js) `tryRetry` path schedules those retries against the same URL before it reaches `shouldRetry` and URL fallback. The 800 ms configured delay is shorter than the 4,000 ms sample boundary in #14959, so a longer server hint can be ignored and the same throttled account called repeatedly.
- Operator skip/retry rules and the per-request transport attempt ceiling are resolved in `runtimeConfig.js` and `BaseExecutor.execute`. A `retry` rule overrides the configured status attempts up to `maxTransportAttempts - 1`; a `skip` rule prevents the generic retry. Any hint-based acceptance rule must run after those existing rules have resolved the allowed retry, and must not add retries or bypass the ceiling. Explicit retry means retry policy wins over provider hook vetoes only for the documented Antigravity capacity-veto exception; a new hint gate should preserve operator intent deliberately and narrowly.
- Provider-owned behavior is already present: [`open-sse/executors/antigravity.js`](../../../open-sse/executors/antigravity.js) parses header/body retry hints, caps accepted hints at 10 seconds, and vetoes longer hints; it also uses its provider-specific transient/error rules. [`open-sse/executors/opencode.js`](../../../open-sse/executors/opencode.js) retries only an identified transient overload response and vetoes quota/access failures. The generic base calls these `computeRetryDelay` hooks as part of retry scheduling. A generic change must preserve those provider-owned decisions rather than replace them.
- On a declined retry, the base currently returns the upstream response (or proceeds to the existing next-URL fallback when configured), preserving the final response for caller-side account handling. Before a retry or URL fallback it settles the provider dispatch as fallback and cancels the discarded response. The account fallback classifier in [`open-sse/services/accountFallback.js`](../../../open-sse/services/accountFallback.js) distinguishes explicit exhausted-quota evidence from ordinary transient 429s and retains cooldown/fallback rules. `providerAttemptContext.js` settles or transfers quota-bearing dispatch tickets. A hint gate should use that existing path so it neither consumes/replaces the response nor duplicates usage/fallback accounting.

## Smallest behavior-preserving acceptance boundary

For a 429 response, first resolve the existing configured attempts, operator skip/retry rule, and per-URL transport ceiling exactly as today. Only if this evaluation would perform an in-place same-URL retry, optionally inspect a retry hint. If a valid explicit server wait is longer than the remaining same-URL retry window, decline that retry and let the existing flow return/fallback with the original response. Keep the configured retry count and delay/window as the comparison basis; do not change the number of attempts, delays, or transport ceiling. Do not let the hint gate defeat an explicit operator retry rule (including its ceiling), and do not alter skip-rule behavior.

The read must be optional and bounded, on a clone: prefer a valid `Retry-After` header; otherwise use supported provider/body hint parsing. Missing, malformed, unreadable, or oversized hint evidence is a non-match and retains current retry behavior. Caller abort during inspection must propagate as abort. Do not inspect bodies on fast paths where the resolved retry allowance is zero, status is not 429, or the provider hook has already made the retry decision unnecessary. Preserve provider-owned hooks and their vetoes/caps. When a retry is declined, leave the original status, headers, and body readable for existing account fallback and client response handling; settle dispatch/accounting only through existing response ownership paths.

The comparison should be against the effective remaining local retry window, not a universal fixed threshold: with `n` retries and delay `d`, account for the delay(s) remaining before that retry window expires, while respecting provider hook delays. If the first wait is itself longer than the server hint, local retry is not necessarily futile. This is narrower and more behavior-preserving than copying OmniRoute's fixed 4,000 ms constant, particularly for OpenCode's seven 800 ms retries and operator overrides.
