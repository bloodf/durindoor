## How the preserve option reaches the wire

In the pinned patch, `shouldPreserveCacheControl` signals that markers from a caching-aware client should be retained, but that alone does not authorize explicit OpenAI-body fields. `providerHonorsOpenAIFormatCacheControl(provider)` is the narrower gate. `translateRequest` passes the resulting preserve option into the source-to-OpenAI translator, which carries system/message text markers, and into `filterToOpenAIFormat`, which otherwise removes `cache_control`. The option is consumed along the Claude-to-OpenAI path; it is not a global passthrough switch.

In this checkout, `translateRequest` derives the intermediate `preserveCacheControl` option from `PROVIDERS[provider]?.quirks?.preserveCacheControl` for OpenAI targets, then uses the same provider quirk at final OpenAI filtering. The Claude-to-OpenAI translator preserves marked system and message text only when that option is true. Therefore the practical local gate is the provider registry quirk, not a Xiaomi-specific cache-support predicate.

## Current local behavior and fixture evidence

- **DashScope:** `alibaba` declares `transport.quirks.preserveCacheControl`; `alicode`, `alicode-intl`, and `alitp-intl` also declare it. `tests/unit/dashscope-claude-cache.test.js` uses ordinary mocked bodies to show marked system and user text blocks survive Claude-to-OpenAI conversion for these providers, retain their block boundary, and remain absent for Groq. It also verifies that unmarked text does not gain a marker and billing-header cleanup retains the appropriate cache boundary. `tests/unit/alicode-cache-control-2069.test.js` independently verifies that the generic OpenAI filter strips by default and preserves only when the option is true.
- **Xiaomi cloud OpenAI API:** `open-sse/providers/registry/xiaomi-mimo.js` declares cloud OpenAI and native Claude transports. Its v2.6 models are OpenAI-format-only; its other catalog models can use the cloud Claude transport. The provider has no `preserveCacheControl` quirk. Thus a Claude-format client routed through the OpenAI transport currently loses explicit markers at the Claude-to-OpenAI step and final filter. Same-format OpenAI requests skip translation, so this audit does not establish that all Xiaomi cloud requests lose markers; it establishes the narrow Claude-to-OpenAI bridge gap addressed by #5013’s Xiaomi allowlist entry.
- **Native Messages:** the Xiaomi registry separately declares an `/anthropic/v1/messages` cloud transport. Matching Claude source/target formats bypass translation, leaving the native Messages request body intact. The local source supports that dispatch path, but this audit makes no claim about Xiaomi’s service-side interpretation of markers beyond the public patch’s explicit OpenAI-format allowlist.
- **Account-service route:** `open-sse/executors/xiaomi-mimo.js` switches eligible v2.6 models to `mimo-server-<region>.xiaomimimo.com/api/route/chat/completions` only after a `mimoPassToken` is present and the account cookie is resolved; it renames the model to `xiaomi/<id>`. `tests/unit/xiaomi-mimo-executor.test.js` uses mocked credentials and cookie/session fixtures to prove cloud URL/key ownership versus account URL/cookie ownership. The registry comment also states this route speaks OpenAI format. Neither these fixtures nor the public cache allowlist establish account-route support for explicit cache markers. Do not extend the cloud claim to this route without separate evidence.
- **Generic and implicit-cache handling:** `open-sse/translator/formats/openai.js` strips `cache_control` by default. Existing DashScope quirk opt-ins preserve markers. No equivalent quirk is set for `openai`, `codex`, or `azure`, so their implicit prefix caching does not turn on explicit marker forwarding. The public patch’s narrower explicit allowlist makes the same distinction.

## Disposition — OmniRoute #5013

**Adopt the narrow Xiaomi explicit-marker behavior for the Xiaomi cloud OpenAI API bridge, with a route-specific qualification.** The DashScope preservation behavior is already present locally, and the public patch’s separate explicit-marker allowlist is the relevant precedent for keeping implicit-cache providers stripped. The demonstrated local gap is the missing Xiaomi preserve path for Claude-to-OpenAI translation to its cloud OpenAI API. Do not describe the distinct account-service endpoint as supported based on this evidence. Native Messages already bypasses this translation path.

Ordinary offline acceptance for any follow-up implementation: a mocked Claude-format request routed to Xiaomi’s cloud OpenAI transport retains exactly the client-marked system/message text blocks; unmarked blocks remain unmarked; a generic implicit-cache OpenAI provider still has markers stripped; and a separate account-route fixture must not assert marker support absent evidence. Preserve existing DashScope fixtures. No product code or tests were changed for this report.
