### [#8](https://github.com/cheaper-inference/OmniRoute/pull/8) — `fix(oauth): prevent connection test from corrupting valid tokens`

Pinned head `a2ba189b80bf3912963b0cef337e7fa6dcfd040b`, merge `16ab4b0ead3ebb1b835755a87ffd4b4d756e9354`, merged 2026-02-13T21:09:52Z. Complete changed paths (1/1, `hasNextPage=false`): `src/app/api/providers/[id]/test/route.js`.

Status: `PROVIDER SIGN-IN LANE`.

Evidence. Upstream diff. The patch adds one condition to the reactive refresh branch of `testOAuthConnection`: the refresh is attempted only when `isTokenExpired(connection)` holds, in addition to the pre-existing "not refreshed yet, has a refresh token" conditions. Upstream's `isTokenExpired` reads `expiresAt`/`tokenExpiresAt` and treats the credential as expired within a five-minute lead window. The upstream file also refreshes on `403` as well as `401`. The accompanying error strings change from "Token invalid or revoked" to "Token expired and refresh failed" and "API returned {status} after token refresh" to distinguish the post-refresh failure from the initial failure. The stated effect is that a transient upstream 401/403 — for example a rate-limit response surfaced as 403 — no longer triggers a refresh, so a still-valid stored token is not rotated away by the connection test.

Local comparison. The upstream path `src/app/api/providers/[id]/test/route.js` exists locally but is a thin route wrapper (25 lines) that delegates to `testSingleConnection`; the credential logic lives in `src/app/api/providers/[id]/test/testUtils.js`, so the shared filename does not settle the comparison. In that local file:

- `isTokenExpired` exists at `testUtils.js:364` and is implemented as `shouldRefreshCredentials(provider, connection)`.
- The expiry value is computed at `testUtils.js:391` (`const tokenExpired = isTokenExpired(connection)`), but it is used only for the proactive branch at `testUtils.js:400-414` and the expiry-only configs at `testUtils.js:416-420`.
- The reactive branches are not gated on it: `testUtils.js:426` (`initial.status === 401 && config.refreshable && !refreshed && connection.refreshToken`), `testUtils.js:449-453` (the Cline path, which refreshes whenever the probe reports the invalid-token error), and `testUtils.js:485` (`res.status === 401 && config.refreshable && !refreshed && connection.refreshToken`). None of the three consults `tokenExpired` or `isTokenExpired`.

So a still-valid credential that receives a transient 401 or 403 from the upstream probe is currently refreshed and overwritten. The local offline test `tests/unit/provider-test-rotation-skip.test.js` documents this as intentional in one direction ("genuine expiry is handled by the reactive, serialized 401 path", header comment at lines 9-10) and covers only the proactive skip for rotating providers; no local test covers the reactive path, so the upstream gate is not present and not otherwise asserted locally.

**Required existing behavior (description only; no product edit was made):** when the provider connection test observes a 401 or 403 from the upstream probe, DurinDoor must attempt a credential refresh only if the stored credential is actually expired or otherwise due for refresh according to the local expiry helper (`isTokenExpired` / `shouldRefreshCredentials` in `src/app/api/providers/[id]/test/testUtils.js` and `open-sse/services/oauthCredentialManager.js:92`). A transient 401/403 against a still-valid token must fail the test without rotating the stored credential, so the test cannot replace a live token with a newly minted one. The local proactive-refresh and rotating-provider guards at `testUtils.js:392-414` and the Codex rotation skip must keep their current behavior, and the failure surfaced to the operator should distinguish "credential expired and refresh failed" from a generic invalid-or-revoked credential.

Boundary note. This row is assessed on its own merits as a fix on an existing local surface (the provider connection test), not as new-provider or sign-in work: it introduces no provider and does not change how credentials are obtained. If the orchestrator treats credential refresh as part of the sign-in/auth-flow lane, this row moves there unchanged; the evidence above is lane-independent.
