## Local evidence and scope boundaries

- `open-sse/services/combo.js::getComboModelsFromData` resolves `auto/<family>` through `resolveAutoCombo` before saved combo lookup; saved combos use exact-name matching. There is no slash-basename expansion. The comments document why basename matching was removed: a saved combo must not capture genuine `provider/model` routing. Existing coverage includes `tests/unit/auto-combo-resolver.test.js`, `tests/unit/combo-prefix-resolve.test.js`, `tests/unit/combo-case-insensitive.test.js`, and `tests/unit/combo-routing.test.js`.
- Saved-combo execution filters context-ineligible members before rotation/scoring, applies strategy ordering, context-size ordering and capability/task reordering, then calls the optional quota ranker. `tests/unit/combo-context-requirements.test.js`, `tests/unit/combo-smart-scoring.test.js`, `tests/unit/combo-weighted-members.test.js`, `tests/unit/combo-weighted-round-robin-port.test.js`, and `tests/unit/combo-patches.test.js` record those boundaries. These are not evidence that source-only OmniRoute auto candidates have equivalent semantics.
- The local Jev path is a task-classification upgrade in `handleComboChat` for task-routing strategies; it is not a new provider pool or quota score. `tests/unit/jev-smart-routing.test.js` covers fallback to heuristic classification and explicitly protects the chat path's Jev call. Keep this behavior; do not replace it with OmniRoute's mode/metric changes.
- Served-model reporting is already exercised by `tests/unit/combo-model-usage-attribution.test.js` and `tests/unit/combo-connection-usage-attribution.test.js`. The four pinned patches do not justify changing its model identity, usage attribution, or publication rows.
- PR #4483's exact PR-head diff consists of the quota-cutoff opt-in and fallback change plus its local settings fixture and size-baseline bookkeeping. The `providerWildcard.ts` addition appears in the enclosing merge, not in the pinned PR-head diff, and is excluded from this disposition.
- PR #4455's shadow-sampling RNG change is a random-selection implementation detail. PR #4590's eviction case is specifically shadow-metric capacity behavior. Neither establishes a request to add, expose, or publish new metrics data in DurinDoor.

No implementation is authorized by this report. The only demonstrated narrow gap is the missing local counterpart to #4483's distinct auto-candidate hard-cutoff/fallback policy; its ordinary offline acceptance criteria are stated in that row. No assertion is made about live provider quota freshness or production behavior.
