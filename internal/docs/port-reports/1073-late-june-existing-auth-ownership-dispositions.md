## Dispositions

### #4729 — Bearer alongside `x-api-key` for third-party Anthropic-compatible gateways

**Source patch scope.** `open-sse/executors/default.ts` adds a bearer fallback in the `anthropic-compatible-*` header branch: when an API key is present and no `Authorization` header has been set, a `baseUrl` that is neither empty nor the official Anthropic host receives `Authorization: Bearer <effectiveKey>` next to the existing `x-api-key`. Official `api.anthropic.com` and an empty `baseUrl` keep `x-api-key` only. The patch adds `tests/unit/executor-default-anthropic-compatible-bearer.test.ts` with three cases: third-party gateway gets both headers, official host gets `x-api-key` only, empty `baseUrl` treated as official.

**Current local behavior.** [default.js](../../../open-sse/executors/default.js) already emits both headers. The `anthropic-compatible-*` auth descriptor ([default.js:665](../../../open-sse/executors/default.js)) sets `x-api-key` for the API-key branch and `Authorization: Bearer` for the OAuth branch, and the compatibility block at [default.js:762](../../../open-sse/executors/default.js) adds `Authorization: Bearer <credentials.apiKey>` for a non-official host when no `Authorization` is already present. The official-host test is stricter than the source patch: local resolves it with exact hostname equality through [anthropicHost.js](../../../open-sse/utils/anthropicHost.js), while the source patch uses a `.includes("api.anthropic.com")` substring test. A look-alike host such as `api.anthropic.com.evil.test` is therefore third-party locally and correctly receives the bearer, where the source substring test would have classified it as official and suppressed the bearer.

**Fixture evidence.** [anthropic-official-baseurl-host.test.js](../../../tests/unit/anthropic-official-baseurl-host.test.js) asserts `Authorization: "Bearer key"` for a third-party host and for a look-alike host, and asserts no `Authorization` for the genuine official host and for an empty `baseUrl`. [claude-header-forwarding.test.js](../../../tests/unit/claude-header-forwarding.test.js) covers the same `anthropic-compatible-*` branch for identity-header stripping and beta-flag handling.

**Disposition: `already present`.** The local behavior covers the source patch and is a superset of it on the official-host check. No gap is demonstrated by this patch's diff, so no acceptance case is required.

### #4787 — Cline WorkOS token shape and client-identification headers

**Source patch scope.** A new `src/shared/utils/clineAuth.ts` exports `getClineAccessToken`, `getClineAuthorizationHeader` and `buildClineHeaders`. The token helper prefixes a non-empty, non-already-prefixed token with `workos:`; the header helper adds the Cline client-identification set (`HTTP-Referer`, `X-Title`, `User-Agent`, `X-PLATFORM`, `X-PLATFORM-VERSION`, `X-CLIENT-TYPE`, `X-CLIENT-VERSION`, `X-CORE-VERSION`, `X-IS-MULTIROOT`) and attaches `Authorization` only when a usable token exists. The patch wires the helper into two call sites, `DefaultExecutor.buildHeaders` (a `cline` case) and `buildProviderHeaders` in `open-sse/services/provider.ts`, and adds `tests/unit/cline-workos-auth-token-shape.test.ts`.

**Current local behavior.** The helper exists locally at [clineAuth.js](../../../open-sse/shared/clineAuth.js), re-exported for the app layer at [src/shared/utils/clineAuth.js](../../../src/shared/utils/clineAuth.js), and exports the same three symbols. It is wired into the executor through the `clineHeaders` hook at [default.js:257](../../../open-sse/executors/default.js), applied after generic auth at [default.js:699](../../../open-sse/executors/default.js) so the normalized token is not overwritten. The other source call site, `buildProviderHeaders` in `open-sse/services/provider.ts`, has no local counterpart file; local [provider.js](../../../open-sse/services/provider.js) resolves format and transport only. The local surfaces that the source call site serves are already routed through the helper: [clineModels.js:52](../../../open-sse/services/catalogs/clineModels.js), [clinepassModels.js:19](../../../open-sse/services/catalogs/clinepassModels.js), [usage/clinepass.js:44](../../../open-sse/services/usage/clinepass.js), [tokenRefresh/providers.js:796](../../../open-sse/services/tokenRefresh/providers.js) and [testUtils.js:191](../../../src/app/api/providers/[id]/test/testUtils.js).

The local token rule is deliberately narrower than the source rule, and the difference is intentional. The source prefixes any non-empty token; local prefixes only a WorkOS-JWT-shaped token (`/^eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+/`), because ClinePass API keys (`clp_…`) are opaque strings the API accepts verbatim and rejects with HTTP 401 when prefixed.

**Fixture evidence.** [cline-auth-token-prefix.test.js](../../../tests/unit/cline-auth-token-prefix.test.js) pins the local rule: a JWT is prefixed, an already-prefixed token is left untouched (including a differently-cased prefix), a `clp_` key is returned verbatim, a non-string yields the empty string, and no `Authorization` header is added when no usable token exists.

**Disposition: `already present`, with a recorded local divergence.** The auth transport shape the patch adds is present and fixture-pinned. Adopting the source rule as written would regress ClinePass keys, so the source rule is not a candidate for import. No gap is demonstrated by this patch's diff.

### #4884 — Qoder PAT exchanged for a `jt-*` job token before the Cosy chat call

**Source patch scope.** `open-sse/services/qoderCli.ts` gains `isQoderPatToken`, `parseQoderJobTokenResponse`, `exchangeQoderJobToken`, `resolveQoderJobToken` and `__clearQoderJobTokenCache`, with an in-memory cache keyed by the PAT and a default ~24h job-token lifetime. `open-sse/executors/qoder.ts` replaces the raw PAT on the Cosy fallback path with the resolved job token, and `validateQoderCliPat` exchanges the PAT before its validation request. The patch adds `tests/unit/qoder-jobtoken-exchange-4683.test.ts` and extends `tests/unit/qoder-executor.test.ts`.

**Current local behavior.** The exchange already exists locally in [qoder.js](../../../open-sse/executors/qoder.js). `isQoderPat` matches the `pt-` prefix at [qoder.js:642](../../../open-sse/executors/qoder.js); `exchangeJobToken` POSTs `{ personal_token: pat }` to the regional `jobToken/exchange` endpoint through `proxyAwareFetch` at [qoder.js:646](../../../open-sse/executors/qoder.js); `fetchUserIdForJobToken` resolves the account identity at [qoder.js:679](../../../open-sse/executors/qoder.js), which the COSY signing path requires; and `resolvePatCredential` caches per PAT and per region with a five-minute pre-expiry buffer at [qoder.js:706](../../../open-sse/executors/qoder.js). The PAT branch consumes it at [qoder.js:743](../../../open-sse/executors/qoder.js). The local implementation is a superset of the source patch: it also resolves the user identity, supports the China region endpoint, and honours the connection proxy.

The source patch's `open-sse/services/qoderCli.ts` has no local counterpart file; the local equivalent surfaces are the executor above and the provider test route.

**Fixture evidence.** [qoder-cn-region-4176.test.js](../../../tests/unit/qoder-cn-region-4176.test.js) mocks `/api/v1/jobToken/exchange` to answer `{ token: "jt-cn-token", expires_in: 3600 }` and `/api/v1/userinfo` to answer an account id, then drives a PAT connection through exchange, model catalog and chat POST, asserting every call routes through the China gateway. [provider-quota-fetchers.test.js:434](../../../tests/unit/provider-quota-fetchers.test.js) pins the international exchange URL.

**Disposition: `already present`.** The credential-exchange behavior the patch adds is present locally and is exercised offline. No gap is demonstrated by this patch's diff.

### #5214 — Antigravity preserves the stored `refresh_token` when the upstream response omits it

**Source patch scope.** `open-sse/executors/antigravity.ts` changes the refresh result mapping from `typeof tokens.refresh_token === "string" ? tokens.refresh_token : credentials.refreshToken` to `typeof tokens.refresh_token === "string" && tokens.refresh_token ? tokens.refresh_token : credentials.refreshToken`, so an empty-string upstream value no longer overwrites the stored token. The patch adds `tests/unit/antigravity-refresh-empty-token-3850.test.ts` with three cases: empty-string `refresh_token` preserves the existing token, omitted `refresh_token` preserves the existing token, and a real rotated token still replaces the stored token.

**Current local behavior.** The local executor already preserves the stored token: [antigravity.js:605](../../../open-sse/executors/antigravity.js) maps `refreshToken: tokens.refresh_token || credentials.refreshToken`, and an empty string is falsy, so the stored token survives. The same preservation is generalized across the refresh paths in [tokenRefresh/providers.js](../../../open-sse/services/tokenRefresh/providers.js) — every mapping there uses `tokens.refresh_token || <stored>`, including `refreshGoogleToken` at [providers.js:287](../../../open-sse/services/tokenRefresh/providers.js), which serves the Antigravity, `agy` and `gemini-cli` proactive handler registered at [tokenRefresh.js:249](../../../open-sse/services/tokenRefresh.js). The application layer adds a second guard: [providerCredentials.js:145](../../../src/shared/services/providerCredentials.js) returns null for an empty secret in `optionalSecret`, so `refreshToken` is written only when the value is non-empty ([providerCredentials.js:376](../../../src/shared/services/providerCredentials.js)).

**Fixture evidence.** [antigravity-refresh-failure-scope.test.js:113](../../../tests/unit/antigravity-refresh-failure-scope.test.js) drives `AntigravityExecutor.refreshCredentials` against a token response that omits `refresh_token` entirely and asserts a healthy result; [antigravity-flow.test.js:148](../../../tests/unit/antigravity-flow.test.js) asserts that a real rotation persists and that a second account is untouched.

**Disposition: `already present` for the runtime behavior; `narrow residual` for offline coverage.** The runtime behavior matches the source patch, but no local fixture pins the Antigravity-specific empty-string `refresh_token` case. The only local fixture that feeds an empty `refresh_token` is [kimi-signin-parity.test.js:203](../../../tests/unit/kimi-signin-parity.test.js), which is a sign-in payload-rejection case rather than a refresh-persist case. The gap is a missing offline regression pin, not a wrong runtime result.

**Ordinary offline acceptance for a later runtime-only change.** Add a focused unit fixture that mocks the Antigravity OAuth token endpoint and asserts: (1) a response carrying `refresh_token: ""` leaves the returned refresh token equal to the stored one; (2) a response omitting `refresh_token` leaves it equal to the stored one; (3) a response carrying a real rotated token replaces the stored one; (4) through the application coordinator, the persisted connection row keeps the original refresh token when the upstream value is empty and is updated when the upstream value is real. The fixture uses synthetic values only, needs no provider traffic and no credential access, and must not weaken the existing rotation, reauth or expiry behavior.

### #5294 — Compare-and-swap guard on the OAuth refresh persist

**Source patch scope.** `open-sse/services/tokenRefresh.ts` gains a `CasGuard` type and the symbols `runWithCasGuard`, `getActiveCasGuard`, `getCasGuardStats` and `_resetCasGuardStats`, plus `casGuardShouldSkipPersist`. The guard carries the refresh token the caller presented and a `reread` callback; immediately before each of the two persist chokepoints inside `getAccessToken` it re-reads the row's current refresh token and skips the write when a concurrent writer already rotated the row past the presented value. The caller still receives the new access token, and with no active guard the behavior is unchanged. `open-sse/handlers/chatCore.ts` builds the `reread` from `credentials.connectionId` and wraps the refresh in `runWithCasGuard`. The patch also rebaselines `config/quality/file-size-baseline.json` and adds `tests/unit/token-refresh-cas-guard-4038.test.ts` with three cases: skip the persist on a concurrent rotation, persist when the row is unchanged, and no guard means the persist always runs.

**Current local behavior.** The same protection is present locally and is implemented as an atomic compare-and-swap write rather than a best-effort pre-persist re-read. [providerCredentials.js:301](../../../src/shared/services/providerCredentials.js) captures `expectedRefreshContext = providerRefreshContext(connection)` before the network refresh; the fingerprint carries the refresh token itself ([providerCredentialContext.js](../../../src/shared/utils/providerCredentialContext.js)). The commit at [providerCredentials.js:447](../../../src/shared/services/providerCredentials.js) passes that fingerprint to the repository, and [connectionsRepo.js:521](../../../src/lib/db/repos/connectionsRepo.js) re-reads the row under the SQLite writer lock and returns `{ applied: false, connection: existing }` when the fingerprint no longer matches, so a concurrent rotation is not overwritten and the winner's connection is returned with `refreshed: false`. The request path uses this coordinator through the app-injected refresher ([chat.js:1418](../../../src/sse/handlers/chat.js)), and the core documents that contract at [chatCore.js:1604](../../../open-sse/handlers/chatCore.js). Local additionally reconciles a rotation that already won: [providerCredentials.js:246](../../../src/shared/services/providerCredentials.js) re-reads the row with backoff delays and adopts the winner instead of pinning a false reauth, and [refreshSerializer.js](../../../open-sse/services/refreshSerializer.js) serializes cross-connection refreshes inside a rotation group, which the source patch does not.

The source patch also rebaselines `config/quality/file-size-baseline.json` and edits `CHANGELOG.md`. The local tree has no `config/` directory and no equivalent quality baseline file, so that part of the patch has no local counterpart; it is repository bookkeeping rather than behavior.

**Fixture evidence.** [provider-credentials.test.js](../../../tests/unit/provider-credentials.test.js) asserts that a stale rotation rejected by compare-and-swap yields the current credential winner with `refreshed: false` and no persist of the losing values; that a concurrent `invalid_grant` recovers the repository winner; and that sibling providers in one rotation group never refresh concurrently.

**Disposition: `already present` on the request-path persist; `narrow residual` on one persist surface.** The request-path persist the source patch guards is guarded locally and more strongly, and the local fixture already pins the skip-on-concurrent-rotation outcome. One local persist surface is not guarded: the OAuth branch of the generic persist helper [tokenRefresh.js:224](../../../src/sse/services/tokenRefresh.js) calls `updateProviderConnection(connectionId, updates)` without a refresh-context fingerprint. Only the cookie-rotation branch of the same helper passes one ([tokenRefresh.js:186](../../../src/sse/services/tokenRefresh.js)). That helper is the persist used by the proactive `checkAndRefreshToken` path ([tokenRefresh.js:281](../../../src/sse/services/tokenRefresh.js)), by the media handlers and by the model-catalog routes. This report records the surface as read; it does not claim to have triggered the race, and no such attempt was made.

**Ordinary offline acceptance for a later runtime-only change.** A narrow follow-up should make the proactive persist carry the same fingerprint: (1) `updateProviderCredentials` should accept and forward a refresh-context fingerprint on its OAuth branch, and the proactive `checkAndRefreshToken` path should pass the fingerprint captured before the network refresh; (2) when the fingerprint no longer matches, the write must be skipped and the stored winner returned rather than overwritten; (3) a normal refresh with an unchanged row must still persist; (4) an existing cookie-rotation write must keep its current behavior; (5) the rotation-group serialization and the concurrent-rotation reconciliation must keep their current outcomes. The acceptance is an ordinary offline unit fixture over mocked repository responses: no provider traffic, no credential access, no database-engine change, and no edit to the request-path coordinator that is already guarded.

## Independent non-auth scope, recorded separately for Upstream review

The following parts of the named patches are independent of credential handling. Their scope is recorded here for Upstream review only. None of them is folded into the auth dispositions above, and none is planned or performed here.

- **#4787 — Cline client-identification header set.** `buildClineHeaders` emits `HTTP-Referer`, `X-Title`, `User-Agent`, `X-PLATFORM`, `X-PLATFORM-VERSION`, `X-CLIENT-TYPE`, `X-CLIENT-VERSION`, `X-CORE-VERSION` and `X-IS-MULTIROOT` alongside the credential. These are client-identification values, not credential material. Local already emits the same set through [clineAuth.js](../../../open-sse/shared/clineAuth.js); the two trees differ only in the product name carried in `User-Agent` and `X-CLIENT-TYPE`.
- **#4884 — exchange-failure fallback.** The source `resolveQoderJobToken` returns the original PAT when the exchange fails, on the stated ground that behavior is then no worse than before. Local instead raises a Qoder exchange error and surfaces a 401-shaped reauth outcome ([qoder.js:664](../../../open-sse/executors/qoder.js), [qoder.js:778](../../../open-sse/executors/qoder.js)). This is a failure-mode difference, not a credential-shape difference.
- **#5294 — quality baseline and changelog.** `config/quality/file-size-baseline.json` (2103 to 2181 lines for `open-sse/services/tokenRefresh.ts`) and `CHANGELOG.md`. Repository bookkeeping only; the local tree has no `config/` directory and no equivalent baseline file.
