## Existing behavior and fixture evidence

**#4485, Antigravity envelope fields.** The patch removes Claude/OpenAI thinking keys at the Google Cloud Code envelope boundary. Local [`antigravity.js`](../../../open-sse/executors/antigravity.js) already has `ANTIGRAVITY_REQUEST_BLACKLIST` containing `output_config`, `thinking`, `reasoning_effort`, `reasoning`, `enable_thinking`, `thinking_budget`, and `thinkingConfig`; `stripBlacklisted` applies it to both the inner request and outer body. This is the same boundary protection. The existing [`antigravity-mitm.test.js`](../../../tests/unit/antigravity-mitm.test.js) fixture verifies removal of conflicting native `thinkingConfig` fields when a reasoning override is applied in the MITM request path; it does not exercise the executor envelope blacklist. The [`antigravity-tool-thinking-bridge-port.test.js`](../../../tests/unit/antigravity-tool-thinking-bridge-port.test.js) fixture separately verifies model-tier mapping. No direct executor-boundary fixture is cited here, and no additional acceptance case is indicated by the pinned patch.

**#4661, Haiku adaptive/effort constraints.** The upstream patch adds a late Haiku guard that rewrites adaptive thinking to enabled with a 10,000-token budget and removes `output_config.effort`. Local behavior gates this by model generation instead of applying the broad Haiku-name predicate: [`normalizeClaudePassthrough`](../../../open-sse/translator/formats/claude.js) downgrades adaptive thinking and strips effort for `isLegacyHaikuModel`, while Haiku 5.5 has the `claude-adaptive` capability. OpenAI-to-Claude translation also selects the native budget shape for legacy Haiku and adaptive format for Haiku 5.5. The fixtures in [`claude-haiku-adaptive-thinking.test.js`](../../../tests/unit/claude-haiku-adaptive-thinking.test.js) exercise native passthrough and translated requests across both generations, preserve other output configuration, and retain explicit adaptive settings on Haiku 5.5. Applying the upstream all-Haiku predicate would override the newer model's supported caller settings. No gap demonstrated.

**#4853, temperature conflict.** The patch strips temperature for Claude 4 Opus/Sonnet based on model name, plus whenever the translated result enables thinking. Local [`paramSupport.js`](../../../open-sse/translator/concerns/paramSupport.js) drops `temperature` for Claude models; [`openai-to-claude.js`](../../../open-sse/translator/request/openai-to-claude.js) also has a finalizer that removes it when normalized thinking is active and non-disabled. The [`omni-claude-thinking-sampling-presence.test.js`](../../../tests/unit/omni-claude-thinking-sampling-presence.test.js) fixtures establish that absent sampling fields stay absent, explicit temperature is removed on active-thinking translation, disabled/no-thinking requests keep the direct-translation value, and the executor wire does not reintroduce it. Explicit `top_p`/`top_k` remain governed by their own support rules. These checks protect caller intent and avoid a synthetic default. No additional code is needed.

**#5480 and the omission-default question.** This PR changes an upstream default-injection branch so it only injects adaptive thinking when the caller is identified as Claude Code. Local source has no corresponding Claude-specific automatic adaptive-thinking injection branch: `chatCore.js` applies `applyThinking` to the existing request intent, and the executor's `applyRequestDefaults` only adds thinking when explicit operator `requestDefaults` are configured. Native Claude passthrough normalizes present fields but does not synthesize adaptive thinking for an omitted field. The [`thinking-unified.test.js`](../../../tests/translator/thinking-unified.test.js) fixtures establish explicit disable precedence, explicit client display preservation, and adaptive output for explicit reasoning intent; [`claude-haiku-adaptive-thinking.test.js`](../../../tests/unit/claude-haiku-adaptive-thinking.test.js) records explicit native and translated Haiku behavior. The current local Claude Code contract therefore does not require an omission default from #1997: an omitted thinking field remains omitted unless caller intent or an operator setting supplies it. No broad default or new configuration feature is warranted.
