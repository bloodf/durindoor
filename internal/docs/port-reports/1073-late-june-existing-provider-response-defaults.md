## Current behavior and local fixture evidence

### #4850 — Qoder provider native error framing

Upstream adds a self-contained `unwrapQoderEnvelope` peek to [`open-sse/executors/qoder.ts`](https://github.com/cheaper-inference/OmniRoute/blob/63b1bea70f6f4320863122cf839dd414ec921ac2/open-sse/executors/qoder.ts). It reads the first SSE event; when the embedded `statusCodeValue` is not 200 it returns a **real HTTP error Response** (`sub-400` → 502, `401`/`403` → `authentication_error`, otherwise `provider_error`) with the body passed through `sanitizeErrorMessage`; on success it re-creates the stream with the first chunk prepended. The upstream motivation is explicit: because the HTTP status is 200, combo routing and account fallback never fire.

The local executor has since diverged well past that point and does **not** carry the upstream's envelope handling shape. [qoder.js](../../../open-sse/executors/qoder.js) peeks only the first `data:` frame in `peekQoderBillingFrame()` ([qoder.js:386](../../../open-sse/executors/qoder.js)) and classifies it into exactly three outcomes:

1. **Billing** — `isBillingBlock()` matches Qoder codes `112` and `110` or a `pricingUrl` key ([qoder.js:324](../../../open-sse/executors/qoder.js), [:305](../../../open-sse/executors/qoder.js)) → a synthetic **403** JSON response ([qoder.js:496](../../../open-sse/executors/qoder.js)).
2. **Queue** — a `10605` queue signal → a synthetic **503** `qoder_model_queued` response carrying `rate_limit_error` and the `x-qoder-queue-delay-ms` header ([qoder.js:501](../../../open-sse/executors/qoder.js)).
3. **Every other non-200 `statusCodeValue`** (401, 403, 429, 500, anything else) — the peek declines to classify it and returns the frame for replay ([qoder.js:427](../../../open-sse/executors/qoder.js)); the stream transform then sees `statusVal !== 200` and calls `emitFailure()` ([qoder.js:561](../../../open-sse/executors/qoder.js)), which enqueues `data: {"error":{"message":"Qoder upstream stream failed","type":"stream_error"}}` **inside a 200 body** while the wrapper keeps `status: response.status` = 200 ([qoder.js:623](../../../open-sse/executors/qoder.js)).

So the embedded status and the embedded body are both discarded for case 3: a quota or auth refusal delivered by Qoder inside an HTTP-200 envelope reaches a streaming client as a 200 response carrying a generic in-stream error, and the client is told nothing about the upstream status.

Local fallback is not absent, but it is **content/EOF-gated rather than status-gated**. `peekStreamForContent()` ([streamContentPeek.js:160](../../../open-sse/utils/streamContentPeek.js)) extracts the in-stream error payload through `extractStreamErrorPayload()` ([streamLifecycle.js:72](../../../open-sse/utils/streamLifecycle.js)); combo consults it at [combo.js:1733](../../../open-sse/services/combo.js) and the single-model path consults it through `holdForEarlyEof()` ([chat.js:738](../../../src/sse/handlers/chat.js)). Both fire only when the upstream stream terminates or errors **before any content** inside the peek window (`STREAM_EARLY_EOF_PEEK_MS`, [runtimeConfig.js:126](../../../open-sse/config/runtimeConfig.js)). A held-open upstream socket yields a 200 plus an error frame and no retry. Non-streaming clients instead see a **502** from `createSSEErrorResult()` ([sseToJsonHandler.js:260](../../../open-sse/handlers/chatCore/sseToJsonHandler.js)), which the account-fallback rules treat as transient and fallback-able ([accountFallback.js:320](../../../open-sse/services/accountFallback.js)).

Local already owns a richer client-facing error taxonomy than the upstream patch assumes, and it deliberately differs from it. [errorConfig.js](../../../open-sse/config/errorConfig.js) maps 401 → `authentication_error`/`invalid_api_key`, 429 → `rate_limit_error`, 502 → `server_error`, and maps a bare **403 → `permission_error`/`permission_denied`**, explicitly so a plain refusal is not misread as quota exhaustion ([errorConfig.js:10](../../../open-sse/config/errorConfig.js)). The upstream patch classifies an embedded 401 **and** 403 as `authentication_error`, which would contradict that local decision.

Local fixtures already pin the three existing outcomes, and they pin case 3 in exactly the shape described above:

- [qoder-billing-fallback.test.js](../../../tests/unit/qoder-billing-fallback.test.js) — billing first frame → 403 with the raw body ([:47](../../../tests/unit/qoder-billing-fallback.test.js)); `10605` → 503 with `x-qoder-queue-delay-ms: 30000` ([:60](../../../tests/unit/qoder-billing-fallback.test.js)); a billing frame that starts past the 64 KiB peek cap stays **200** and fails through the generic path ([:170](../../../tests/unit/qoder-billing-fallback.test.js)).
- [qoder-executor-billing.test.js](../../../tests/unit/qoder-executor-billing.test.js) — executor returns a synthetic 403 for a billing first frame; HTTP-200 envelopes with billing-shaped bodies stay 200.
- [qoder-queue-replay.test.js](../../../tests/unit/qoder-queue-replay.test.js) — queue replay with re-signing returns 200; the attempt cap returns 503 `qoder_model_queued`; billing is not replayed.
- [omni-qoder-model-queue-scope.test.js](../../../tests/unit/omni-qoder-model-queue-scope.test.js) — queue is a distinct type from quota/billing, the queue 503 is fallback-able and model-scoped, and combo advances to the next member.
- [qoder.test.js](../../../tests/unit/qoder.test.js) — a `statusCodeValue: 500` envelope yields a sticky "Qoder upstream stream failed" with no upstream text and no `[DONE]` ([:494](../../../tests/unit/qoder.test.js)); a `statusCodeValue: 503` envelope does the same ([:524](../../../tests/unit/qoder.test.js)).

**No local fixture pins a first-frame non-200, non-billing, non-queue envelope to an HTTP error status.** The only local fixtures for that case assert the opposite: a 200 status with a generic in-stream failure. The upstream fixture [`tests/unit/qoder-unwrap-error-envelope.test.ts`](https://github.com/cheaper-inference/OmniRoute/blob/63b1bea70f6f4320863122cf839dd414ec921ac2/tests/unit/qoder-unwrap-error-envelope.test.ts) asserts the opposite contract — embedded 429 → real HTTP 429, embedded 302 → 502, embedded 401 → 401 with `authentication_error`, empty stream → 502, and an executor-level case that mocks `globalThis.fetch` and asserts the returned response status is 429. That mock proves the upstream case is reachable without provider traffic.

A boundary must be recorded here: the upstream `qoder.ts` at the PR base is 251 lines and contains **no** billing, quota-code, or queue handling at all (zero matches for `isBillingBlock`, `parseQoderQueueInfo`, `10605`, `pricingUrl`). The upstream patch is therefore the first envelope handling upstream ever had, while the local executor's billing/queue/quota-disable machinery was added independently afterwards. A verbatim port of `unwrapQoderEnvelope` would run **before** the local peek and would preempt both local outcomes: an embedded 403 carrying code `112` would become `authentication_error` instead of the local quota-disable 403, and an embedded 403 carrying `10605` would become `authentication_error` instead of the local retryable queue 503.

### #5019 — provider requested reasoning

Upstream makes CodeBuddy CN reasoning params opt-in: `reasoning_summary:"auto"` is added **only** when the client explicitly set `reasoning_effort`; `reasoning_effort` is dropped for `"none"`/`"off"`; and plain requests are left with both fields unset. The upstream rationale is that forcing `reasoning_effort:"medium"` plus `reasoning_summary` on plain requests trips CodeBuddy's content filter and returns an error.

The local executor already implements exactly this contract in [codebuddy-cn.js:57](../../../open-sse/executors/codebuddy-cn.js)–[:67](../../../open-sse/executors/codebuddy-cn.js): the `"none"`/`"off"` branch deletes `reasoning_effort` without setting `reasoning_summary`; the `else if (eff)` branch sets `reasoning_summary = "auto"`; and the trailing comment records that forcing reasoning on plain requests makes CodeBuddy trip its content filter. The branch structure is identical to the upstream head, including the comment that the gateway has no `"none"` value.

Local fixture evidence is a one-to-one port of the upstream fixture: [codebuddy-reasoning-optin.test.js](../../../tests/unit/codebuddy-reasoning-optin.test.js) pins all three upstream cases — no reasoning requested → `reasoning_effort` and `reasoning_summary` both `undefined`; explicit `reasoning_effort: "high"` → effort `"high"` plus `reasoning_summary` `"auto"`; `reasoning_effort: "none"` → both `undefined`. The file is the same upstream case set adapted to the fork's Vitest harness and `.js` import path, and it has been present since the fork baseline commit. Adjacent local fixtures cover the surrounding reasoning surface: [codebuddy-thinking-levels.test.js](../../../tests/unit/codebuddy-thinking-levels.test.js) pins the per-model supported effort sets for `codebuddy-cn`, and [opencode-go-effort-parity.test.js:192](../../../tests/unit/opencode-go-effort-parity.test.js) pins the `codebuddy-cn` / `deepseek-v4.1-flash` `xhigh` → `high` mapping.

### #5173 — provider local tool-name recovery

Upstream adds a conservative name-recovery fallback inside [`open-sse/translator/deepseekWebTools.ts`](https://github.com/cheaper-inference/OmniRoute/blob/9c591803896d070bcefcbeb522de9fc008ee7062/open-sse/translator/deepseekWebTools.ts). That module is a **provider-specific** parser for `chat.deepseek.com`, which has no native function calling: OmniRoute serializes the OpenAI `tools[]` array into a prompt contract and parses the model's text reply back into `tool_calls`. The module is layered on the shared `webTools` helpers — it imports `parseToolCallsFromText`, `getRequestedToolNames`, `resolveRequestedToolName`, `toArgumentsString` and `stripRanges` from `webTools.ts` — and adds a tokenizer with a stack walk for DeepSeek's wider zoo of ad-hoc block shapes, including the parameter style `<tool:write><parameter name="content" …>`. The PR's new behavior is one fallback inside that parser: when every explicit name-resolution path fails but `<parameter>` children were extracted, and **exactly one** requested tool's parameter-schema property keys are a superset of the extracted parameter names, adopt that tool's name; zero or more than one match keeps returning `null` so a call is never misattributed. The upstream fixture [`tests/unit/deepseek-web-tools-nameless-5154.test.ts`](https://github.com/cheaper-inference/OmniRoute/blob/9c591803896d070bcefcbeb522de9fc008ee7062/tests/unit/deepseek-web-tools-nameless-5154.test.ts) pins the unique-match case (`filePath` + `offset` → `read`), the ambiguous case (two tools sharing `filePath` + `offset` → no call), and the zero-match case.

The **shared helper lineage is present locally**. [webTools.js](../../../open-sse/translator/webTools.js) carries the same helper set under the same names: `getRequestedToolNames()` ([webTools.js:12](../../../open-sse/translator/webTools.js)), `resolveRequestedToolName()` ([webTools.js:83](../../../open-sse/translator/webTools.js)), `toArgumentsString()` ([webTools.js:100](../../../open-sse/translator/webTools.js)) and `parseToolCallsFromText()` ([webTools.js:127](../../../open-sse/translator/webTools.js)).

The **provider-specific parser has no local counterpart**. There is no `parseDeepSeekToolCalls` and no `serializeDeepSeekToolPrompt` anywhere in the tree, and no parameter-style block parsing in the local helper: `parseToolCallsFromText()` resolves a name only from the JSON body (`parsed.name`, else `parsed.command`) and then requires an exact or alphanumeric-normalized match against the requested tools; when `resolveRequestedToolName()` returns `null` the call is dropped ([webTools.js:136](../../../open-sse/translator/webTools.js)–[:138](../../../open-sse/translator/webTools.js)). The local DSML path is a different format belonging to the plain DeepSeek **API** provider: the `invoke` regex requires `name="…"` in the frame header ([dsmlToolCalls.js:6](../../../open-sse/utils/dsmlToolCalls.js)) and `parseInvoke()` returns `null` when it is absent ([dsmlToolCalls.js:14](../../../open-sse/utils/dsmlToolCalls.js)). No schema-superset name inference exists anywhere in the local runtime.

The boundary that decides this row is provider execution, not the parser. The `deepseek-web` provider is **not shipped locally**: it is closed as not planned in the local provider-parity ledger — issue #1173, "consumer-session scraping of the web chat", with the recorded outcome "No local route and no mock" ([provider-parity-current-dispositions.md:192](../../../internal/docs/provider-parity-current-dispositions.md)). The local DeepSeek surface is the API provider [registry/deepseek.js](../../../open-sse/providers/registry/deepseek.js). Because the host provider is absent, there is no route on which the upstream fallback could fire, and adding one would be a new provider integration rather than a port of an existing behavior. The earlier ledger reached the same conclusion at the path level ([1073-late-june-recovered-3-dispositions.md:223](../../../internal/docs/port-reports/1073-late-june-recovered-3-dispositions.md): "0 of 1 behavioural path(s) have a local counterpart"); the read above confirms it against the runtime code.

Local fixtures covering the adjacent tool-call-recovery surfaces are [dsml-tool-calls-port.test.js](../../../tests/unit/dsml-tool-calls-port.test.js) (DSML frame decoding, split frames, malformed frames left as text), [dsml-concern-port.test.js](../../../tests/unit/dsml-concern-port.test.js) (DSML response integration across client formats), [cursor-tool-mapping.test.js](../../../tests/unit/cursor-tool-mapping.test.js) (Cursor native `<|tool_call_begin|>` text parsing, where the name is a required capture group with no fallback), and [deepseek-dsml-buffered-response-review.test.js](../../../tests/unit/deepseek-dsml-buffered-response-review.test.js) (DSML decoding on the forced-SSE → JSON path). None of these exercises a nameless block resolved by a parameter-schema superset match.

## Dispositions

- **#4850 — narrow gap; accept a focused local port, bounded so it cannot preempt the local Qoder classifications.** The gap is narrow and demonstrable: a first-frame envelope carrying a non-200 `statusCodeValue` that is neither a billing code (`110`/`112`/`pricingUrl`) nor a queue signal (`10605`) is currently flattened to a **200** response with a generic `stream_error` frame, so the upstream status is lost and fallback becomes EOF-gated rather than status-gated ([qoder.js:561](../../../open-sse/executors/qoder.js), [:623](../../../open-sse/executors/qoder.js)). Accept a port that surfaces the embedded status as a real HTTP error **only after** the local billing and queue classifications have already declined the frame. Do **not** port the upstream peek position, its `authentication_error` typing for 403, or its unconditional precedence: the local billing 403 and queue 503 must keep their current meaning, and a bare 403 must keep the local `permission_error` taxonomy ([errorConfig.js:9](../../../open-sse/config/errorConfig.js)). Ordinary offline acceptance: a fixture in [qoder-billing-fallback.test.js](../../../tests/unit/qoder-billing-fallback.test.js), which already drives `wrapQoderSSE` through the exported `__test__` internals ([qoder.js:926](../../../open-sse/executors/qoder.js)), asserting that an embedded 429 becomes a real HTTP 429, that an embedded 401 becomes a 401 classified as an authentication failure, and that an embedded sub-400 status becomes 502. Controls: an embedded 403 carrying code `112` still returns the billing 403; an embedded 403 carrying `10605` still returns the queue 503 with `x-qoder-queue-delay-ms`; a `200` envelope still passes through with the first chunk intact and no synthetic error; and no upstream body text reaches the client in any of these cases. The upstream fixture's `globalThis.fetch` mock shows this is reachable with no provider traffic, no credentials, and no live provider call.
- **#5019 — already covered; no port.** The local executor carries the identical opt-in branches ([codebuddy-cn.js:57](../../../open-sse/executors/codebuddy-cn.js)–[:67](../../../open-sse/executors/codebuddy-cn.js)) and [codebuddy-reasoning-optin.test.js](../../../tests/unit/codebuddy-reasoning-optin.test.js) is a one-to-one port of the upstream fixture covering all three upstream cases. The requested-reasoning contract is already the local default; no source change is indicated.
- **#5173 — no port; the provider lane and the source tool bridge are absent locally.** The upstream change is a fallback inside a `deepseek-web`-specific parser. The shared helper module it builds on exists locally ([webTools.js](../../../open-sse/translator/webTools.js)), but the provider-specific parser has no local counterpart and no local parser performs schema-superset name recovery; the local helper's name resolution is an exact-match resolver that drops an unmatched call ([webTools.js:83](../../../open-sse/translator/webTools.js)). The host provider `deepseek-web` is closed as not planned with "No local route and no mock" ([provider-parity-current-dispositions.md:192](../../../internal/docs/provider-parity-current-dispositions.md)), so the behavior has no execution path to attach to. Adding the provider, a mock route, or a new provider-specific parser would be a new provider integration rather than a port of an existing behavior, and is out of scope here. No fixture is accepted for this row.

No provider traffic was sent, no credentials were read, and no outbound call was made. This report changes no product code, no test, and no workflow.
