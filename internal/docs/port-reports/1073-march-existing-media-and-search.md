Correction 2026-11-21: the eligibility of #416 and #432, and the summary that follows from them, are corrected against the owner scope of this comparison. #416 adds custom provider-node audio dispatch and #432 adds a response cache, request coalescing and a provider-listing capability; each is a **new non-provider feature**, so each is out of scope even though it lands on an endpoint this fork already serves. Reusing an existing endpoint does not turn a new capability into a correction of existing behavior, and that is the reading this report previously got wrong for these two rows. The row evidence, the source pins, the narrow #412 correction and the #422/#528 dispositions are unchanged by this correction. The factual absence of a search response cache is also unchanged — only its eligibility changed — so the April comparison of upstream #1178 that cites this report as published evidence for that absence still holds on the fact and inherits the corrected scope (`internal/docs/port-reports/1073-april-existing-gateway-routes.md`, row #1178); that citation is left as written there because this correction touches this file only.

No local rule or registry list removes `temperature`/`top_p` for `o1`, `o1-pro`, `o3` or `o3-pro`, so a client that sends them reaches the upstream reasoning endpoint with parameters that upstream rejects. The upstream mechanism differs (registry-declared per-model list plus a `chatCore` strip before the executor); the local rule table is the equivalent insertion point, and the local Responses path is where the surviving fields are copied. **Focused implementation unit:** declare the unsupported-parameter set for the OpenAI reasoning family in the local registry/rule table, strip it on the outbound path for both the chat and Responses transports, and add offline cases — a reasoning model with `temperature` and `top_p` (both removed), the same request without them (unchanged), a non-reasoning OpenAI model (both retained), and a prefixed model id (`openai/o3`) resolving to the same rule.

## Classification

**Existing runtime fixes on existing providers.** #412 is the only row whose upstream patch is a defect repair on an already-shipped provider: it declares which request parameters the OpenAI reasoning family rejects and removes them before the outbound call. The local tree has no equivalent declaration for that family, so #412 is a confirmed qualifying gap and the one focused implementation unit in the media/search area that is a pure fix.

**New non-provider features (out of scope).** #416 and #432 are out of scope for this owner scope. #416 adds custom provider-node audio dispatch; #432 adds a response cache, request coalescing and a provider-listing capability. Each is a new capability that this fork never had, so neither row repairs local behavior, and neither is a qualifying gap or a port candidate from this comparison. The endpoint reuse is the point that changed in this correction: #416 lands on `/v1/audio/speech` and `/v1/audio/transcriptions`, and #432's runtime half lands on `/v1/search`, all of which this fork already serves — but a new capability on a reused endpoint is still a new feature, not a correction to existing behavior. Neither introduces a provider catalog entry or a sign-in flow, so neither is Provider Sign-in work either: #416's node providers are explicitly credential-free and loopback-only, and #432's cache changes no credential destination.

**Provider ownership.** #432's provider half — the five upstream search provider registrations, their dashboard entries, their icons and their per-provider API-key validators — is new-provider work owned by Provider Sign-in. The local tree already carries the same five services as registry providers with matching search configuration and with the upstream ids registered as aliases, so those upstream ids are recorded here as existing behavior and no genuinely new provider arises from this row; a Provider Sign-in comparison of this surface would start from the existing alias rows rather than from new registrations. #416 and #422 add no provider rows either: they route existing operator-configured node rows onto existing endpoints.

**Authentication flows.** No row in this set introduces or changes a sign-in flow. The credential-behavior changes in #416 (credential-free local audio providers), #422 (no credential injection for credential-free embedding providers) and #528 (credentials resolved from the provider-node id) all reuse the existing credential store and the existing success-time error-clearing path; none adds a new credential type, an OAuth flow, or a token refresh path.

**Already present.** #422 (embeddings from provider nodes) and #528 (provider-node id as the embedding credential destination) are satisfied by the current resolution path, adapter dispatch and connection keying, with the divergences recorded above and a named missing fixture for #528.
