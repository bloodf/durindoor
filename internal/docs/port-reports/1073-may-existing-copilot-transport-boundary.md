## Current local behavior and fixture evidence

The local Copilot Web surface is a server-side executor, not a browser integration. `open-sse/executors/copilot-web.js` accepts an access token or credential text, starts a conversation over HTTP, then connects to `wss://copilot.microsoft.com/c/api/chat?api-version=2`. `extractAccessToken` supports bearer/cookie input and constrained HAR extraction; this does not launch or control a browser, establish a user sign-in, or reproduce client fingerprinting. The executor deliberately starts a fresh conversation for each stateless chat request.

Response projection is already represented: the executor turns Copilot `appendText` frames into OpenAI-compatible streaming content and handles `replaceText` by replacing accumulated text before completion. `tests/unit/copilot-web-executor.test.js` provides mocked WebSocket and fetch fixtures for streaming chunks, fresh conversations, and replacement text (`ReplaceThenDoneCopilotWebSocket`). These are offline protocol fixtures; no live provider request is needed.

The local tests also cover `solveHashcash` rejecting difficulty 0 and 9 and accepting a common difficulty of 1, and `solveHashcashAsync` yielding and stopping at configured work/time bounds. This provides direct fixture evidence that the bounded-work change in #2391 is already present. The session-key fixture verifies distinct keys for two tokens, no literal token in the result, and the anonymous fallback. It does not cover the HMAC or verbatim-token policies in #2394/#2396.

Other local Copilot surfaces have different roles: GitHub Copilot OAuth (`github`/`ghe-copilot`) and the VS Code integration guide are not Microsoft Copilot Web browser sessions. Microsoft 365 Copilot Web is a separate Chathub WebSocket provider and does not establish a personal Copilot browser integration.

## Acceptance for a demonstrated narrow gap

No new provider, browser/session integration, or live transport change is accepted from these rows. If a future, separately authorized change targets the observed difference in #2340, ordinary offline acceptance should use the existing Copilot Web executor test with mocked `/c/api/start` and WebSocket events. It should assert the intended session reuse/rotation contract and preserve the existing `appendText`/`replaceText` to OpenAI response projection. Keep tests deterministic and credential-free; do not exercise browser sign-in, client fingerprint emulation, or live provider traffic. The #2391 bound is already covered by existing offline cases. Any change to token-key policy suggested by #2394/#2396 needs a distinct security rationale and tests for its chosen in-memory key contract.
