### #1933 — codex bare-name disambiguation and family-native fallback

Pins: head `b2af42237a448ca56d20c5d00a383b2d0e8561ce`, merge `ec0ce5bed7bfb2d95a4941cbc68ffbf2f742dad4`, merged 2026-05-04T12:40:50Z. Complete changed paths: `src/sse/handlers/chatHelpers.ts`.

The merged patch changes one function, `resolveModelOrError`, in three ways. It adds a family regex `NON_OAUTH_MODEL_PREFIX = /^(deepseek|qwen|kimi|glm|minimax|mimo)/i` and a map `PREFERRED_BY_FAMILY = { deepseek: "deepseek", qwen: "bailian", kimi: "moonshot", glm: "zhipu", minimax: "minimax", mimo: "moonshot" }`. It reroutes a `codex/<model>` request whose model name starts with one of those families to the family-native provider, because the Codex OAuth account does not serve those models. Finally, when model resolution reports an ambiguous bare model, it now picks the family-native provider out of the candidate list instead of returning HTTP 400, and keeps the 400 only when no family rule matches.

DurinDoor's structural counterpart is `getModelInfo` in `src/sse/services/model.js:273` together with `getModelInfoCore` in `open-sse/services/model.js:117`. None of the three behaviours is present.

Reroute by family is absent. `getModelInfoCore` returns `{ provider: parsed.provider, model: parsed.model }` unchanged whenever the request string carries a provider prefix (`open-sse/services/model.js:120-125`), so `codex/deepseek-v4-pro` resolves to provider `codex` with no family check anywhere on the path. A repo-wide search for `PREFERRED_BY_FAMILY`, `NON_OAUTH_MODEL_PREFIX`, `bare-name` and `family-native` over `src/` and `open-sse/` returns nothing. The Codex registry carries no non-OpenAI rows to begin with (`open-sse/providers/registry/codex.js:63-105` lists only `gpt-*`, `codex-*` and `gpt-*-image` entries), and the only Codex-specific routing rule in the fork moves traffic the other way, pinning a bare name onto Codex at `open-sse/services/model.js:151` (`[/^codex-auto-review$/, "codex"]`).

Ambiguity handling is absent, which also makes the family auto-pick inert. DurinDoor has no reverse model-to-providers index, no `errorType: "ambiguous_model"`, and no `candidateProviders` or `candidateAliases`; a search for those identifiers over `src/` and `open-sse/` returns no hits. A bare name therefore resolves through the alias map and then through a fixed prefix table (`MODEL_PREFIX_PROVIDERS`, `open-sse/services/model.js:147-156`) whose default is `"openai"` (`inferProviderFromModelName`, `open-sse/services/model.js:163-167`). The ambiguous-model 400 does not exist either; the only nearby 400 is the generic `"Invalid model format"` at `src/sse/handlers/chat.js:901-902`, which fires when the name resolves to no provider at all and is not a combo. An unrelated ambiguity 400 exists for the video endpoint only (`src/sse/handlers/video.js:196-210`).

The closest local analogue to the intent of the upstream change is the Anthropic-to-Claude OAuth preference at `src/sse/services/model.js:280-290`, which prefers a sibling provider for a bare `claude-*` name when the API-key provider has no connection. It is scoped to one family and has no generalisation.

A mechanical port is not possible without re-deriving the provider ids: upstream's `bailian`, `moonshot` and `zhipu` do not exist in this fork (`zhipu` has no registry entry; the local equivalents are `bcp`/`bailian-coding-plan`, `kimi` and `glm`/`glm-cn`/`zai`).

**Disposition: not ported; confirmed gap.**

#1972's merged patch has three parts, and they land differently in DurinDoor.

Capability precedence is deliberately different locally. The models.dev contribution (`shared`) therefore beats the service-kind defaults but loses to local curated declarations and to live discovery. The precedence direction is the opposite of the upstream change and is intentional locally: a locally declared capability is authoritative over a third-party catalogue. This is recorded as a deliberate difference, not a defect, and no port is implied.

The provider-level default context window fallback is absent. That function resolves custom, then live, then provider, then exact, then registry, then pattern, then default, and never consults `defaultContextLength`. The only reader of the field anywhere in the tree is `open-sse/config/providerPluginManifest.js:115`, which normalises a plugin manifest entry. A registry model that declares no `contextLength` and matches no capability row therefore produces `known: false` and contributes no `context_length` to `/v1/models`.

The models.dev provider map is narrower locally. The curated table is the local mechanism that exposes context windows for the fork's provider set; the models.dev corroboration lane is narrower than upstream's expanded map. This is recorded as a coverage difference with an existing local substitute, and no separate port is implied.

### #2010 — fuzzy auto-combo routing for the `auto/*` model prefix

Pins: head `c689411ad1fe92ba295d88e71e3cd378d7f29006`, merge `7214efa86e22f066a6c159fe3d7533808f4e30bc`, merged 2026-05-07T11:49:17Z. Complete changed paths: `src/app/docs/components/DocsSidebarClient.tsx`, `src/sse/handlers/chat.ts`, `src/sse/handlers/chatHelpers.ts`.

The upstream `auto/` namespace addresses stored combos by name. The merged patch makes `resolveModelOrError` look up an exact combo for `auto/<name>`, then try `auto/best-<suffix>` and `auto/<suffix>` as fuzzy fallbacks, and, when nothing matches, answer with HTTP 400 listing the configured `auto/*` combos. The chat handler gains the same fuzzy lookup, and `handleSingleModelChat` gains a safety net that redirects into the combo flow when the resolver already found a combo. The third file carries a one-line documentation-site fix: `currentSlug` no longer defaults to `""`.

DurinDoor's `auto/` namespace is a different mechanism, not a missing one. It is a family-based virtual combo system: `open-sse/services/autoComboResolver.js:32-56` defines `AUTO_COMBO_PREFIX`, `isAutoComboId` and `familyOfAutoId`, `open-sse/services/autoComboFamilies.js:16-24` fixes the advertised families to `glm`, `minimax`, `mimo`, `zai`, `gemma`, `llama` and `gemini`, and `resolveAutoCombo` materialises the pool from the active-connections catalogue (`open-sse/services/autoComboResolver.js:95-111`, consumed at `src/sse/services/model.js:456-470`). The routing intent of the upstream change, an `auto/*` prefix that reaches a pool rather than a literal provider, is therefore already served.

The upstream naming contract is not, and cannot be, adopted as written. `parseFamilySegment` rejects any segment outside the advertised family set on purpose, so `isAutoComboId("auto/foo")` is false and `isAutoComboId("auto/best-fast")` is false (`open-sse/services/autoComboResolver.js:39-46`, pinned by `tests/unit/auto-combo-resolver.test.js:36-37`). An exact named lookup for `auto/<name>` also cannot work: a saved combo is resolved by its stored name only, and a request string containing a slash is treated as a provider/model call and never as a basename lookup (`src/sse/services/model.js:471-476`). That rule is deliberate, so that a saved combo sharing a basename cannot shadow genuine `provider/model` routing. Adding an `auto/best-*` convention would therefore collide with the reserved virtual `auto/` namespace rather than fill an empty one.

The upstream error shape and the safety net have no local counterpart and none is required. An unknown `auto/<segment>` falls through to the system `auto` provider (`open-sse/providers/registry/auto.js`, a single `auto` model) and then to the generic `"Invalid model format"` 400 at `src/sse/handlers/chat.js:901-902`; there is no list of available `auto/*` combos to show, because the set is fixed by the family table rather than by operator configuration. The redirect safety net is likewise unnecessary: DurinDoor resolves the combo before dispatch, at `src/sse/handlers/chat.js:496` and `src/sse/handlers/chat.js:581-582`, so the single-model path is never entered for a combo.

The documentation-site change has no counterpart in this fork. The fork ships no OmniRoute-style docs sidebar: `currentSlug` occurs nowhere in the tree and `src/app/` has no docs route tree. It is in any case not gateway runtime.

**Disposition: not ported; the upstream `auto/*` naming contract is superseded by a different local design.**

## Authentication and credential work

### #1885 — per-connection mutex for rotating refresh tokens

Pins: head `18b080629833b53afdf77367729ea6128a8b2660`, merge `0e8148d60299b01f28e92a4b9cdf9bf7642b88ea`, merged 2026-05-03T19:19:44Z. Complete changed paths: `open-sse/services/tokenRefresh.ts`, `src/sse/services/tokenRefresh.ts`, `tests/unit/token-refresh-service.test.ts`.

The merged patch adds a per-connection mutex to `getAccessToken` in `open-sse/services/tokenRefresh.ts`, keyed by `credentials.connectionId`, ahead of the existing token-hash de-duplication, so concurrent refreshes of one connection share a single in-flight promise even when the callers hold different token strings. It moves the database staleness check into the mutex path so a token another process already refreshed is returned without a new upstream call, renames the unrecoverable-refresh signal to `unrecoverable_refresh_error`, and exports `getConnectionRefreshMutexStatus` for diagnostics. `src/sse/services/tokenRefresh.ts` gains a matching `withConnectionRefreshMutex` wrapper used by `checkAndRefreshToken`.

DurinDoor meets all of this and goes further, through several local units.

The per-connection de-duplication exists twice. `src/shared/services/providerCredentials.js:31` holds a `credentialRefreshInflight` map keyed by `refreshKey(connection)`, which is `JSON.stringify([connection.provider, connection.id])` (`src/shared/services/providerCredentials.js:74`), and a caller that finds an entry joins it instead of starting a second refresh (`src/shared/services/providerCredentials.js:302-303`). `open-sse/services/oauthCredentialManager.js:261-283` provides `withCredentialRefreshLock`, keyed by provider, connection identity and proxy-route fingerprint, with an in-flight deadline and a bounded map.

The token-hash fallback exists and is stricter than upstream's. `open-sse/services/tokenRefresh/dedup.js` implements `dedupRefresh` over a key built from provider, old token and a proxy-route fingerprint (`proxyRouteFingerprint`, `open-sse/services/tokenRefresh/dedup.js:60-91`), so a refresh is shared only when the egress contract is identical; it also reuses a completed result for a short window and bounds the cache size (`open-sse/config/runtimeConfig.js:46-48`).

The staleness check exists. `reconcileConcurrentRotation` (`src/shared/services/providerCredentials.js:246-275`) re-reads the connection from the database after an unrecoverable refresh result and compares the refresh context through `providerRefreshContextMatches`, so a credential that another caller already rotated is adopted instead of being forced into re-authorisation.

The error-code rename is already local: `open-sse/services/tokenRefresh/providers.js:239` and `:395` return `{ error: "unrecoverable_refresh_error", code: failure.code }`, and `open-sse/services/tokenRefresh.js:49-54` recognises that code alongside the older `refresh_token_reused` spelling.

Beyond upstream, the fork also serialises the refresh across every connection in the same rotation group. `open-sse/services/refreshSerializer.js` maps Codex and the raw `openai` provider onto one `openai-auth0` lane and holds the lane for a settle gap before releasing it, because two sibling accounts refreshing concurrently would trip Auth0 refresh-token family revocation. The upstream per-connection mutex cannot see that collision, because the colliding refreshes are on different connections. The lane is entered at `src/shared/services/providerCredentials.js:345-350`.

The diagnostics export has no local gap. Upstream's `getConnectionRefreshMutexStatus` has no consumer anywhere in the merged upstream tree; the local equivalents are test-only snapshots, `__getCredentialRefreshLockSnapshotForTesting` (`open-sse/services/oauthCredentialManager.js:285-292`) and `__getRefreshDedupCacheSnapshotForTesting` (`open-sse/services/tokenRefresh/dedup.js`). Neither side exposes an operator-facing diagnostics endpoint for this state.

**Disposition: covered by an existing, stronger local mechanism.**

### #1887 — per-session sticky routing for codex

Pins: head `8e4e1e2633d26d42b4166faf379ac2d738387ec4`, merge `fa29e19863d07af859db4bf19b97584ec53c43a4`, merged 2026-05-10T03:58:08Z. Complete changed paths: `src/instrumentation-node.ts`, `src/lib/db/migrations/041_session_account_affinity.sql`, `src/lib/db/sessionAccountAffinity.ts`, `src/lib/localDb.ts`, `src/sse/handlers/chat.ts`, `tests/unit/sse-auth.test.ts`.

The merged patch replaces stubbed session-affinity functions with a database-backed implementation over a new `session_account_affinity` table keyed by session key and provider, storing the chosen connection with creation and last-seen timestamps. It adds a cleanup that deletes rows older than a thirty-minute TTL, run once at startup and then every five minutes. The chat handler derives a session-affinity key, preferring an external session header and falling back to the request session id, and threads that key into credential resolution so a session is pinned to one provider account. Startup registers the cleanup.

DurinDoor has session-to-account affinity, but a different and partly weaker mechanism.

What exists. A provider-scoped in-memory map holds session-to-connection pins (`src/sse/services/auth.js:129-163`), written when a connection is chosen (`src/sse/services/auth.js:1151-1153`) and consulted when a session-sticky connection is still available (`src/sse/services/auth.js:1044-1049`). A stateless rendezvous-hash selector sits alongside it (`src/sse/services/auth.js:165-186`), applied at `src/sse/services/auth.js:1053-1059` and `:1077-1082`. Session identity is extracted from the accepted client headers and body fields (`open-sse/utils/sessionManager.js:96`, `:139-162`) and threaded from the chat handler into credential selection (`src/sse/handlers/chat.js:1032-1036`, `:1102-1114`), where it is consumed at `src/sse/services/auth.js:685`. A session-cleanup sweep exists as a module-level interval with an unref'd timer (`src/sse/services/auth.js:188-196`) using the two-hour TTL and thirty-minute interval configured at `open-sse/config/runtimeConfig.js:41-43`.

What is absent. There is no `session_account_affinity` table, no migration for it, no database module and no re-export from the local database entry point; the schema in `src/lib/db/schema.js` holds no session-scoped table. No affinity cleanup is registered at startup; `src/instrumentation.node.js:52-103` registers operational metrics, the API-key guard, the Headroom proxy, the Kimchi user-agent updater, the data-retention scheduler and the model auto-sync, and nothing else of this kind. Upstream's affinity key extraction, which falls back to a hash of the first input text when the client sends no session identifier, has no local counterpart; `x-codex-session-id` and `x-omniroute-session` occur nowhere in the tree, and `resolveClientSessionId` returns null when no accepted header or body field is present (`open-sse/utils/sessionManager.js:139-162`).

The decisive difference is that local affinity is conditional on the operator-selected fallback strategy. Both mechanisms are gated on the strategy value: the sticky map requires `strategy === "round-robin"` and the rendezvous selector requires `strategy === "cache-affinity"` (`src/sse/services/auth.js:1047`, `:1058`), while the default strategy is `fill-first` (`src/sse/services/auth.js:965`). Upstream resolves affinity ahead of and independently of the strategy branch, so a session is pinned regardless of how accounts are otherwise chosen. Two further differences follow from the same design: the local sticky map is process-local and is lost on restart, whereas upstream's rows survive; and local affinity applies only to chat and Responses traffic, because the chat handler is the only caller that passes a session id to credential selection.

**Disposition: partly covered by a different local mechanism; confirmed gap in the durable, strategy-independent contract.**

### #1929 — image proxy resolution keyed on the connection id

Pins: head `324c22548267313b83c5834833da14702784b2d7`, merge `3f900a833e4788996d5d8dcc2e46f311a722a7d3`, merged 2026-05-04T22:23:27Z. Complete changed paths: `src/app/api/v1/images/generations/route.ts`, `tests/unit/codex-failover.test.ts`, `tests/unit/image-generation-route.test.ts`.

The merged patch changes the image-generation route in two ways. It replaces `credentials?.id` with `credentials?.connectionId` when resolving the proxy for the connection, because the credential object has no `id` field, so image requests never applied the connection's proxy. It also wraps the proxied call so that a thrown error becomes a structured `{ success: false, status, error }` result instead of propagating.

DurinDoor satisfies both, through a different arrangement. The route itself is a thin adapter with no credential lookup and no proxy resolution at all (`src/app/api/v1/images/generations/route.js:14-19`), so the upstream defect cannot exist on this path and the upstream code shape has no local counterpart.

The proxy is resolved earlier, when the connection is projected into a credential. `projectProviderCredentials` calls `resolveConnectionProxyConfig(connection.providerSpecificData || {})` and writes the resolved pool or per-connection proxy into the credential's provider data, and stamps the credential with `connectionId: connection.id` (`src/sse/services/auth.js:436-470`). Because the resolution reads the selected connection row's own configuration, the keying is inherently correct and there is no id-lookup step that could be given the wrong field. `resolveConnectionProxyConfig` resolves a proxy pool to its concrete URL at `src/lib/network/connectionProxy.js:140-190`.

The image core consumes the resolved proxy through `resolveCredentialProxyOptions(credentials)` (`open-sse/handlers/imageGenerationCore.js:74-75`, implemented at `open-sse/services/oauthCredentialManager.js:181-209`) and passes it to the request (`open-sse/handlers/imageGenerationCore.js:176-184`), where the patched global fetch routes it through the proxy agent (`open-sse/utils/proxyFetch.js:946-948`). The executor-based image adapters carry the same options (`open-sse/handlers/imageGenerationCore.js:102-112`), and the image-edit path resolves its proxy the same way (`open-sse/handlers/imageEditCore.js:139-144`). The token-refresh retry preserves the resolved proxy fields rather than replacing them (`src/sse/services/tokenRefresh.js:283-292`).

The structured error conversion is present as a shared helper that returns a superset of the upstream shape. `createErrorResult` returns `{ success: false, status, error, resetsAtMs, response }` (`open-sse/utils/error.js:661-694`), and it is applied to the fetch path (`open-sse/handlers/imageGenerationCore.js:185-190`), the executor path (`:142-150`), the upstream non-2xx reply (`:256-263`), the parse failure (`:317-329`) and the image-edit fetch (`open-sse/handlers/imageEditCore.js:139-144`).

One evidence limitation is recorded rather than claimed as a defect: no test asserts that an image request carries its connection's proxy. The proxy behaviour is exercised only through the shared credential selector (`tests/unit/strict-proxy-credentials.test.js`, `tests/unit/oauth-proxy-selection.test.js`, `tests/unit/provider-attempt-context.test.js`), not through the image path.

**Disposition: covered by a different local mechanism.**

## Confirmed gaps and safe expected behaviour

Four confirmed gaps are recorded above: the codex family reroute and ambiguity handling of #1933, the provider-level default context window fallback of #1972, the reka model discovery of #1956, and the durable strategy-independent session affinity of #1887. Each needs a new code unit; none is recorded here as an implementation, and no product decision is taken. The expected behaviour below is what a correct implementation would have to satisfy.

**#1933 — family-aware model routing.** A request that names the Codex provider explicitly together with a model from a family the Codex account does not serve should be routed to a provider that does serve that family, rather than being sent to the Codex account and failing there. When a bare model name matches more than one provider, the request should be resolved deterministically to one provider instead of silently defaulting, and the response to an unresolvable name should name the providers that could serve it. The family-to-provider mapping must be re-derived against this fork's provider ids, because the upstream ids do not exist here. Routing to a fallback provider must not bypass the normal account, quota and policy checks that a directly addressed provider would receive.

**#1972 — provider-level default context window.** A chat model served by a provider that declares a default context length, but which declares no model-level context length of its own, should report that provider default as its `context_length` in the OpenAI-compatible model list. Models owned by a combo, and models that are not chat models, should not inherit it, because their window is derived from their members or from their service kind. The value must not override a model-level or operator-set limit, and it must not be applied to a model whose provider has declared no default.

**#1956 — reka model discovery.** A request for the model list of a configured reka connection should be answered from the local preset catalogue, with the same response shape and source marker the other locally-catalogued providers use, and should not depend on an upstream model-list call. It should succeed whether or not the connection carries an API key, and it should not send the key anywhere. A preset model that the operator has since removed, or a custom model the operator added, should still be represented by the catalogue it actually comes from, so that the list stays a single unambiguous set.

**#1887 — durable, strategy-independent session affinity.** A session that can be identified should be pinned to the provider account that first served it, independently of how accounts are otherwise selected, so that a conversation does not change account mid-thread when the operator's fallback strategy is not one of the affinity strategies. The pin should survive a gateway restart, so the mapping must be stored rather than held only in process memory. A session identifier that the client does not send should still yield a stable key, derived from the request content, so that clients which send no session header are not silently excluded from affinity. The stored mapping must expire, so an abandoned session does not pin an account forever, and the cleanup must run on a schedule rather than only at startup. Pinning must not weaken any existing account, quota, policy or credential check, and it must not cause a session to be routed to an account that is not available.

Two rows need no further action. #1971 is an empty merged patch and inherits the disposition of #1972. #2010's `auto/*` naming contract is superseded rather than missing, and its documentation-site change has no counterpart in this fork.
