### #2063 — Antigravity Claude must use the Gemini Cloud Code schema

Pins: head `51deee3853e30e9ad96020273491e4f266e10aa1`, merge `afdebbc793cce519afc676fee73f2bff4da71fad`.

Local disposition: **the post-fix wire shape is already in place, through a different local mechanism.** The local Antigravity Claude path lives in the translator rather than in the executor: `open-sse/translator/request/openai-to-gemini.js:672` routes Claude models into `wrapInCloudCodeEnvelopeForClaude` (selected by `usesClaudeRequestFormat` at `open-sse/translator/validate.js:21`), and that builder already emits a Cloud Code `request` in the Gemini shape — `contents`, `systemInstruction`, `generationConfig`, `tools[].functionDeclarations`, `toolConfig` — with no `messages`, `system`, `max_tokens`, `stream` or `temperature` key (`open-sse/translator/request/openai-to-gemini.js:471-486`, `:666`). The executor consumes that one shape for every model: `open-sse/executors/antigravity.js:321-372` maps `body.request.contents`, promotes a functionResponse turn to `role:"user"`, filters thought-only and blank-text parts (`filterThoughtParts`, `:145-152`) and backfills `thoughtSignature`; `:376-390` regroups tools into a single `functionDeclarations` group under sanitized names. Local Claude models on Antigravity are real, not hypothetical: `open-sse/providers/registry/antigravity.js:87-97` lists `claude-sonnet-5-5`, `claude-opus-5-5`, `claude-sonnet-5`, `claude-sonnet-4-6` and `claude-opus-4-6-thinking`, and `tests/translator/bugs-antigravity.test.js:136` exercises the Claude-backed Antigravity path.

Local differences, recorded rather than treated as gaps:

- The local bridge is Chat → Claude-native (`openaiToClaudeRequestForAntigravity`) → Gemini contents, with a dedicated tool-use id allocator (`open-sse/translator/request/openai-to-gemini.js:506-511`) and a tool-name aliaser (`:658-664`); upstream bridges Chat → Gemini directly. Both emit `functionCall`/`functionResponse` parts keyed by the client's tool ids.
- Output ceiling. Upstream pins Antigravity Claude output at 16,384 (`ANTIGRAVITY_CLAUDE_MAX_OUTPUT_TOKENS`, upstream `open-sse/translator/request/openai-to-gemini.ts:32`, applied at `:475-481`) and carried that ceiling across this schema change. The local path sends `claudeRequest.max_tokens || 64000` (`open-sse/translator/request/openai-to-gemini.js:483`) and the local executor ceiling is 64,000 (`open-sse/executors/antigravity.js:43`, applied at `:473-475`). This is not classified as a gap: #2063 did not introduce the difference, the upstream constant is an upstream policy value rather than a verified limit for these accounts, and no provider traffic was permitted to confirm which ceiling Cloud Code enforces here. It is recorded so a later review can settle it against an account.

### #2104 — Kiro tool-use payload normalization

Pins: head `2aef379e40b278d1d2788a27a8d80c1b350ed121`, merge `4a6865650d127be0b1105ca01d46092c3b52cf59`.

Upstream change, three parts: (a) normalize the tool input schema through `normalizeKiroToolSchema`; (b) emit tool-result `status` as lowercase `"success"` instead of `"SUCCESS"`; (c) when the transcript does not end with a user turn, keep the history intact and synthesize a `"Continue"` user turn for `currentMessage`, instead of leaving the earlier user turn in place.

Local disposition: (a) and (b) are **present**; (c) is a **different local mechanism** and is the subject of gap K-1.

- (a) `open-sse/config/kiroConstants.js:115-159` defines `normalizeKiroToolSchema`, applied to every tool's `inputSchema.json` at `open-sse/translator/request/openai-to-kiro.js:269`. The local normalizer is stricter than upstream's: it also folds `allOf`/`oneOf`/`anyOf` root branches into `properties` and drops `required` entries that have no matching property. Local coverage: `tests/unit/openai-to-kiro.test.js:240` (unsupported schema keywords canonicalized while valid structure survives) and `:263` (schema assertion on `currentMessage.userInputMessage.userInputMessageContext`).
- (b) `open-sse/translator/request/openai-to-kiro.js:359` and `:371` already emit `status: "success"`, with `"error"` reserved for failed tool results (`block.is_error === true` / `msg.is_error === true`).
- (c) The local selection rule is `open-sse/translator/request/openai-to-kiro.js:437-443`: it scans history backwards and promotes the **last** `userInputMessage` into `currentMessage` regardless of trailing assistant turns. Upstream instead keeps every turn in history and synthesizes a `"Continue"` user turn. The observable consequence and the safe expected behavior are recorded as gap K-1 below. No local fixture pins this branch: `tests/unit/openai-to-kiro.test.js` and `tests/translator/bugs-kiro.test.js` assert `currentMessage` content, images, tools and thinking, but none covers a transcript that ends with an assistant turn.

### #2105 — merge adjacent user history turns after role normalization

Pins: head `e84a2286eee6c2f23b2d7f57aba8d6ecbc21ad61`, merge `149d13cb9c846d2e67030d3b8dc15d7d734559d9`.

Upstream change: after `system`/`tool` roles are normalized into user turns, the history can contain adjacent `userInputMessage` entries, which Kiro rejects. Upstream collapses them by concatenating content and merging the attached `userInputMessageContext`.

Local disposition: **already present.** `open-sse/translator/request/openai-to-kiro.js:462-491` merges consecutive `userInputMessage` entries, joining content with a blank line and concatenating the `toolResults` and `tools` context arrays so neither is dropped by the merge. The local merge runs after the `currentMessage` splice (`:437-443`) and before the tools re-injection (`:522-530`), so the merged turn is the one that carries the tools schema. One cosmetic difference: the local join is unconditional, so merging a turn whose content is empty leaves a leading blank-line separator where upstream omits it. That is a formatting artifact, not a protocol difference, and no gap is recorded for it.

### #2149 — synthesize a tools schema when history references tool calls but `body.tools` is absent

Pins: head `29d1d733bd8610d27455d81790a9524a0f81867e`, merge `1814d2bde04842945a1d59b15ccef953bf11cf52`.

Upstream change, three parts: (a) when `body.tools` is empty but the history contains tool calls, synthesize a minimal schema from the tool names found in the history; (b) attach the tools schema to the first *emitted* user turn rather than to whatever happens to sit at `history[0]`; (c) promote the tools schema to `currentMessage` by scanning the whole history, and fall back to attaching the caller's own tools directly to `currentMessage` when no user turn ever received them.

Local disposition: (b) is **present**; (a) is **deliberately replaced by a different local mechanism**; (c) is **applicable gap K-2**.

- (b) `open-sse/translator/request/openai-to-kiro.js:213` tracks `toolsInjectedToFirstUserMsg`, and `:249` attaches the schema to the first emitted user turn regardless of the turn's index — the same intent as upstream's `toolsAttached` flag.
- (a) When the client sends no tools, the local translator collapses every tool call and tool result into plain text first (`flattenToolInteractions`, `open-sse/translator/request/openai-to-kiro.js:60-105`, invoked at `:204-206`), so no structured tool content survives and Kiro's "tools required" rule never fires. The local code states the choice explicitly at `:42-59`: fabricating stub schemas would advertise a tool-calling capability the client never requested, which risks a phantom tool call on an otherwise plain turn, and the collapse keeps the request honest. Offline coverage: `tests/unit/openai-to-kiro.test.js:142` (OpenAI `tool_calls` plus a tool result flattened into history text with no tools array), `:174` (Claude `tool_use`/`tool_result` blocks), `:274` (an orphaned `tool_result` salvaged as text instead of discarded). Upstream's synthesize-and-attach and the local flatten reach the same wire outcome — the request is accepted — with different content, and the local one is the deliberately documented alternative, not an omission.
- (c) The local promotion reads the schema from `history[0]` alone (`open-sse/translator/request/openai-to-kiro.js:446`, captured before the cleanup at `:449-452` deletes the schema from every history turn) and re-injects it into `currentMessage` at `:522-530`. When the first emitted user turn is not `history[0]` — a transcript that opens with an assistant turn — or when the transcript contains no user turn at all, the schema is dropped and `currentMessage.userInputMessage.userInputMessageContext.tools` is absent. The rule it must satisfy is documented in the same file at `:42-49`: "Kiro's schema validator requires a non-empty currentMessage.userInputMessageContext.tools array whenever the history references any tool use; otherwise it returns 'Improperly formed request' (HTTP 400)." Local outbound validation does not cover this case — `tests/unit/kiro-outbound-validation.test.js:33-44` checks only the presence of the conversation id, the current model id, the current content and the history array. The same `history[0]`-only pattern is present in the sibling Claude→Kiro translator (`open-sse/translator/request/claude-to-kiro.js:307-308`), which is outside this batch and is noted only as adjacent surface.

### #2164 — degrade Responses background mode to synchronous execution

Pins: head `49b8f9b9115fa205bdd57848e3959c987acdfbf8`, merge `e5974c4ae34d757626979404c8b179efbe4848c5`.

Upstream change: the Responses → Chat request translator no longer throws 400 for `background`; it logs a `BACKGROUND_DEGRADE provider=… model=…` marker when `background === true` and strips the flag in every case, so clients that set `background:true` opportunistically work against a synchronous proxy.

Local disposition: **the behaviour is already present through a different local mechanism; the operator-visible marker is absent (gap R-2).**

- Nothing locally rejects `background`. The upstream `unsupportedFeature` guard for background mode has no counterpart: the only `unsupportedFeature` helper in the tree is `open-sse/executors/oneminai.js:209`, unrelated to Responses.
- The Responses → Chat translator deletes the flag: `open-sse/translator/request/openai-responses.js:738` (`delete result.background;`), so a Responses client that sets `background:true` against a Chat-speaking upstream runs synchronously and receives a completed response — the upstream post-fix outcome. This is the live path for `/v1/responses`: `open-sse/translator/formats.js:29-31` fixes the source format to `openai-responses` for that endpoint, `src/app/api/v1/responses/route.js` dispatches to `handleChat`, and the pivot at `open-sse/translator/request/openai-responses.js:351-352` converts the body and reaches the deletion.
- On a Responses-native transport the flag is deliberately not stripped: it reaches the upstream as a native deferred-run request, and the local runtime already understands that receipt — `open-sse/utils/responsesContent.js:32` (`isResponsesReceipt`, identifying a queued or in-progress response envelope), used at `open-sse/services/combo.js:1396`. The native path is therefore not degraded locally, which is consistent with upstream, whose change touched only the Chat pivot.
- The one upstream element absent locally is the marker: the local strip is silent, so an operator cannot see which clients are sending `background:true`. That is gap R-2.

## Confirmed applicable gaps and safe expected behavior

Four gaps are confirmed by local source. Each names the local unit to add and the behaviour that unit must produce. No product code was written for any of them in this review.

**K-1 — Kiro `currentMessage` selection must not invert the tail of the transcript.** Source: #2104 (`4a6865650d127be0b1105ca01d46092c3b52cf59`). Local site: `open-sse/translator/request/openai-to-kiro.js:437-443`. When the transcript ends with an assistant or tool turn, the local rule promotes an earlier user turn into `currentMessage` while the trailing assistant turn stays in `history`, so the two are emitted in the opposite order to the client's transcript; upstream instead keeps the history intact and supplies a user turn for `currentMessage`. Safe expected behavior: the emitted `conversationState.history` must contain every transcript turn in its original order, exactly once; `currentMessage` must be a user turn; when the transcript's last turn is a user turn, that turn becomes `currentMessage` and is removed from `history`; when the last turn is an assistant or tool turn, no earlier user turn may be promoted out of `history` and restated as the current turn — a synthesized continuation turn is used instead, and it must not restate the content of a user turn already present in `history`. A user turn must never appear in both `history` and `currentMessage`. Acceptance: offline translator fixtures for a transcript ending with an assistant turn and for one ending with an assistant tool call, asserting the order of `conversationState.history`, the identity of `currentMessage`, and the absence of duplication.

**K-2 — the Kiro tools schema must reach `currentMessage` whenever the history references tool use.** Source: #2149 (`1814d2bde04842945a1d59b15ccef953bf11cf52`). Local site: `open-sse/translator/request/openai-to-kiro.js:446` and `:522-530`. Today the schema is read from `history[0]` only, so a transcript whose first emitted user turn is not `history[0]`, or a transcript with no user turn at all, reaches the upstream with no `currentMessage.userInputMessage.userInputMessageContext.tools` while `history` still references a tool use — the exact condition the local file documents at `:42-49` as producing "Improperly formed request" (HTTP 400). Safe expected behavior: the caller's own tool declarations, and only those, must be present in `currentMessage.userInputMessage.userInputMessageContext.tools` whenever the request declares tools or the history references a tool use or tool result; the schema must be carried over from whichever history turn received it, and when no user turn received it, taken directly from the request's own `tools` array. The local no-fabrication policy stands: no stub or synthesized tool specification may be invented for a tool the client did not declare, and the existing flatten-to-text path for tool-less clients stays as it is. Acceptance: offline translator fixtures for a transcript that opens with an assistant turn followed by a user turn, and for a transcript containing only an assistant tool call, both with a declared `tools` array, asserting that `currentMessage` carries the declared schema and that the history still references the tool use.

**R-1 — a chat client's `include` array must reach the Responses request.** Source: #2154 (`fca89049c90127b48380c624879fb01bd3d5b5c8`). Local site: `open-sse/translator/request/openai-responses.js:861-866` (Chat → Responses request construction) and `:733` (Responses → Chat cleanup, which must keep dropping it). Safe expected behavior: when the incoming chat body carries a non-empty `include` array, the Responses request must carry the same entries, unchanged and in order; when the chat body carries no `include`, none may be invented; the Responses → Chat direction must continue to drop `include`, since a Responses-only field is invalid on a Chat upstream; and the Codex executor's forced `reasoning.encrypted_content` entry (`open-sse/executors/codex.js:1074-1076`) must remain authoritative for that provider, so a client-supplied `include` is unioned with it rather than replacing it. Acceptance: offline request-translator fixtures for a chat request with `include: ["reasoning.encrypted_content"]` translated to the Responses format, asserting the array survives verbatim, and a fixture asserting no `include` appears when the chat body has none.

**R-2 — a degraded Responses background request must be observable.** Source: #2164 (`e5974c4ae34d757626979404c8b179efbe4848c5`). Local site: `open-sse/translator/request/openai-responses.js:738`. The local strip is silent, so an operator cannot tell which clients depend on background mode.
