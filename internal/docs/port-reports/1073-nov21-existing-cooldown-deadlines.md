# #1073 — Compare persisted cooldown deadline handling

## Pins and exact public change

- OmniRoute PR #20777 head: [`e363aa29da5d7dd9b7f6b2a4f39a03793e302e8e`](https://github.com/cheaper-inference/OmniRoute/commit/e363aa29da5d7dd9b7f6b2a4f39a03793e302e8e), enclosing merge: [`e4b1542c1e1dc995a0195284d63f61e333f369a7`](https://github.com/cheaper-inference/OmniRoute/commit/e4b1542c1e1dc995a0195284d63f61e333f369a7).
- The PR-specific patch is the first-parent diff `e45e582292a..e4b1542c1e1dc995a0195284d63f61e333f369a7`; this avoids treating sibling changes in the PR-head merge as part of #20777. It changes `waitForCooldownAwareRetry` to accept the persisted `retryAfter` deadline, recheck `Date.now()` when its initial timer fires, and schedule the remaining interval if the deadline is still future. The direct chat retry supplies that deadline. It also updates the wait observer and adds direct early-timer, abortability, and relative-wait tests.

## Current DurinDoor behavior and evidence

DurinDoor does not implement this automatic “all accounts cooling down, wait, then retry the same request” path. `getProviderCredentials` uses the current selection time to test persisted model-lock deadlines (`requestedModelLockActive` / `requestedModelLockUntil` in [`auth.js`](../../../src/sse/services/auth.js)) and excludes active locks from eligible accounts. `summarizeBlockedConnections` returns an all-rate-limited result and a retry deadline when all blocked accounts have known deadlines. The chat handler then returns an unavailable response carrying that deadline; it does not sleep or automatically dispatch again. When another eligible account exists, selection skips the locked account and dispatches the eligible one.

Offline fixture evidence: [`omni-excluded-account-model-cooldown.test.js`](../../../tests/unit/omni-excluded-account-model-cooldown.test.js) uses a fixed `NOW`, supplies persisted model locks and quota snapshots, and verifies that (a) a locked account is not selected, (b) the shorter lock is reported for a later request, and (c) an eligible sibling is still selected. [`provider-quota-selection.test.js`](../../../tests/unit/provider-quota-selection.test.js) covers active model locks and returned retry deadlines in preflight. [`chat-quota-fallback.test.js`](../../../tests/unit/chat-quota-fallback.test.js) exercises the chat route with mocked account/quota state. These fixtures demonstrate deadline ownership in persisted account/quota eligibility and response hints rather than a retry timer.

Preflight therefore prevents dispatch before the persisted deadline under ordinary serialized selection. If a deadline expires between selection and dispatch, that is the normal boundary race for any preflight; this PR’s timer fix does not address that distinct selection-to-dispatch interval. The existing retry limits remain in force: chat accounts are attempted once per request except the bounded Antigravity capacity sweep, and total attempts are capped by `MAX_ACCOUNT_ATTEMPTS_PER_REQUEST` in `chat.js`. An already aborted request returns 499 at the handler/preflight boundaries and does not retry; the PR’s abortable wait behavior has no corresponding local wait to modify.

## Disposition

- **OmniRoute #20777: no port.** The demonstrated early-timer gap belongs to a direct retry-wait owner, which DurinDoor does not have for persisted account cooldowns. Existing selection preflight owns this behavior and returns the deadline to the caller when all accounts are blocked. The public patch’s timer behavior is not evidence of an early account dispatch in the current DurinDoor path.

No narrow gap was demonstrated; no new acceptance test is proposed. If a future DurinDoor change introduces an automatic cooldown retry wait, ordinary offline acceptance should use a mock clock and fixture deadline: let the initial timer fire while `Date.now()` remains one tick before the persisted deadline, assert no retry/dispatch and that the wait remains pending, advance the clock to the deadline and assert exactly one retry; then abort during the remaining wait and assert no retry. Include a no-deadline relative wait case and verify the established per-account and total-attempt caps.
