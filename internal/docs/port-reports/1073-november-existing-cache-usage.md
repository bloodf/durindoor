## Current behavior and evidence

- Responses usage translation in [`usage.js`](../../../open-sse/translator/concerns/usage.js) preserves cache detail counters and applies cache-inclusive accounting: already-inclusive `input_tokens` stays unchanged; flat exclusive `cache_read_input_tokens` and `cache_creation_input_tokens` are added once. [`responses-usage-detail-translation.test.js`](../../../tests/unit/responses-usage-detail-translation.test.js) exercises inclusive and exclusive forms, verifies idempotency, and checks canonical usage and cost equivalence. Claude-to-OpenAI conversion in the same module folds cache read and creation into prompt totals and emits both detail counters; the fixture assertions are in [`usage-concern.test.js`](../../../tests/unit/usage-concern.test.js).
- OmniRoute #18361 adds an internal `cache_creation_in_prompt` marker and only adds cache-write tokens back to emitted Responses `input_tokens`/`total_tokens` when that marker says the internal total excluded them; it marks the emitted count inclusive to prevent repeat addition. The local path already represents the Claude exclusive source values as separate `cache_read_input_tokens` and `cache_creation_input_tokens` and normalizes them at the Responses boundary. The paired local fixture confirms 1,000 input + 200 cache read + 30 cache creation becomes 1,230 input / 1,280 total, while the usage details preserve the cache read. The marker itself is therefore not needed to reproduce this local contract. Do not add it absent evidence of an incoming local shape that uses the same marker semantics.
- Ollama parity is present in both streaming and non-stream extraction. [`usage.js`](../../../open-sse/translator/concerns/usage.js) maps `prompt_eval_cached_count` to cache detail, clamping it to `prompt_eval_count`; [`requestDetail.js`](../../../open-sse/handlers/chatCore/requestDetail.js) uses the same native extractor for non-stream bodies. [`ollama-cached-tokens.test.js`](../../../tests/unit/ollama-cached-tokens.test.js) proves absent/invalid metadata is omitted, prompt and total remain unchanged, cached count is clamped, and canonical cost treats cached tokens as a subset. This matches the behavior sought by #19004; it does not imply any broader Ollama setup or LAN behavior.
- Responses detail parity is different from adding counters. `toResponsesUsage` copies nested input/output details, including a present null counter; completion normalization maps top-level counts but does not canonicalize those nested detail counters. The local fixture [`openai-responses-completed-usage.test.js`](../../../tests/unit/openai-responses-completed-usage.test.js) covers valid cache creation, cache reads, reasoning, and zero-filled missing counters, but does not cover explicit null or non-numeric nested counters. OmniRoute #19355 specifically coerces known detail counters to integers (and fills required counters when a details object exists), to protect strict clients parsing `response.completed`.

## Scope and acceptance

The #19355 parity gap is limited to offline normalization of `input_tokens_details.cached_tokens`, optional `cache_write_tokens`/`cache_creation_tokens`, and `output_tokens_details.reasoning_tokens` on the relevant Responses completion boundary. Ordinary offline acceptance should use local fixtures for explicit null, missing required counter in a present details object, invalid/non-finite values, valid existing integer values, and absent or null details objects; assert the source object is not mutated and that prompt/cache accounting and cost do not change. No live provider request is needed.

This comparison makes no monetary/accounting change recommendation: #18361's marker adjustment is output-contract context normalization, #19004 exposes an existing inclusive cache subset, and #19355 only normalizes detail representation. Provider setup, Ollama LAN access, and other network or device work are outside these patches' cache-detail scope and remain with their owning lanes.
