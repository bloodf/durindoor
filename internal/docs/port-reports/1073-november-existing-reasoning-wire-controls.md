Scope: compare two exact OmniRoute patches with DurinDoor's existing Claude-to-OpenAI/Codex translation and supported tool payload behavior. This covers existing supported reasoning levels and field precedence only. It does not add reasoning values, model profiles, or provider policy.

## Current DurinDoor behavior and fixtures

Claude-to-OpenAI conversion in `open-sse/translator/request/claude-to-openai.js` gives a current Claude system directive precedence, then root `output_config.effort`, then `reasoning_effort`, then `reasoning.effort`. It emits the selected value as `reasoning_effort`. It also retains a supplied `reasoning` object, allowing the Codex executor to apply its existing explicit `reasoning.effort` precedence. `open-sse/translator/index.js` captures translated thinking intent before downstream executor handling. These are current explicit carriers; the patches do not justify changing their order or broadening them.

On the Codex route, `open-sse/executors/codex.js` whitelists nested reasoning keys to `effort` and `summary`, maps `enabled:false` to `none` only when no explicit effort exists, and selects nested effort before flat `reasoning_effort`, model suffix, and the existing low fallback. It removes the flat field after constructing the Codex wire object. The model-specific resolver and existing supported effort set remain authoritative. `tests/unit/codex-client-version-and-reasoning.test.js` covers nested key filtering, disable semantics, and explicit effort over disabled state. `tests/translator/openai-to-claude-fable-integration.test.js` exercises translated `reasoning_effort: high`, Claude adaptive thinking, tool calls, and thinking-history filtering. The checked-in offline fixtures establish the existing supported path and tool envelope, but do not exercise the newly described unusable restored-metadata fallback end-to-end.

For #412, the recorded local behavior remains intact: `open-sse/translator/concerns/paramSupport.js` scopes the seven unsupported sampling fields to the native OpenAI legacy reasoning model set. `tests/unit/omni-openai-legacy-reasoning-sampling.test.js` captures both Chat-to-Responses and native Responses outbound bodies, asserting that reasoning, tools, tool choice, and token limits survive while only the recorded fields are dropped. Its preserved-model and other-provider cases prevent the new comparisons from turning into a broad field policy. See [the #412 report](1073-openai-legacy-reasoning-sampling.md) for its exact upstream pin and scope.

## Dispositions

### #18788 — already covered in the established path; narrow fixture opportunity

The patch addresses fallback when `requestedThinkingEffort` exists but is unusable: retain the translated nested or flat effort rather than treating the unusable original as an intentional override. The local Claude translator emits the chosen Claude effort into the flat OpenAI carrier, and the Codex executor already selects supported explicit nested/flat controls with established precedence. The compared local unit fixtures do not model the exact mixed-carrier case (an empty or unusable original plus a supported translated value) through translation and Codex wire construction. Treat this as a fixture opportunity, not evidence for a behavior change: preserve the local source precedence and Codex model scope. No runtime gap was demonstrated in the local supported Claude path.

Ordinary offline acceptance if the boundary is later exercised: add a local unit fixture using the normal translated Claude request path and `CodexExecutor.transformRequest`, with a supported translated level and an unusable optional metadata carrier; capture/assert the final Codex reasoning object and an accompanying supported tool payload. Include a control proving a usable explicit caller level still wins, and an existing unsupported level/model case remains governed by the current resolver. No credentials or provider traffic are needed.

### #19208 — no qualifying gap on the compared Claude-to-OpenAI/Codex path

The upstream change concerns canonical top-level `effort` normalization and cleanup on OpenAI Chat Completions. In the compared local Claude route, `claude-to-openai.js` reconstructs the target request and explicitly maps supported Claude effort carriers to `reasoning_effort`; it does not copy arbitrary top-level Claude keys such as `effort`. The OpenAI Responses translation is separately field-built and uses its existing `reasoning_effort` conversion. The target under review is the translated Claude route with supported tool payloads, so the patch's broader same-format OpenAI canonical input is not a demonstrated gap here. Do not add a general top-level `effort` policy or alter provider/Responses behavior from this comparison.

Existing offline acceptance evidence: `tests/translator/openai-to-claude-fable-integration.test.js` covers supported Claude-to-OpenAI reasoning and function tools; `tests/unit/omni-openai-legacy-reasoning-sampling.test.js` covers preserved reasoning and supported tools through OpenAI request wire filtering. For any future targeted assertion of this patch boundary, use an offline translator fixture that starts with a Claude request carrying supported `output_config.effort` plus tools, translates to the named OpenAI target, and asserts the mapped supported carrier is present while an unrelated top-level `effort` key is absent. Keep native Responses and same-format canonical OpenAI input out of that assertion unless separately scoped.
