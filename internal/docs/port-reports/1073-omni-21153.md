# OmniRoute #21153: stream status colors

Disposition: **verified implementation gap, pending port**. The operator-visible status text for abnormal stream termination exists locally and lacks upstream's outcome-based ANSI color and its controls. This is a cosmetic logging gap, not a stream protocol or lifecycle gap. No DurinDoor PR is identified as implementing it.

## Upstream evidence

The final [PR #21153](https://github.com/cheaper-inference/OmniRoute/pull/21153/files), merged as [`92f696203921581a4b0e1334beafa8e8c0c8006b`](https://github.com/cheaper-inference/OmniRoute/commit/92f696203921581a4b0e1334beafa8e8c0c8006b) with head `1f47a122873e86118d324d64b9acdf8797e6ff22`, changes seven files. Its [stream handler](https://github.com/cheaper-inference/OmniRoute/blob/1f47a122873e86118d324d64b9acdf8797e6ff22/open-sse/utils/streamHandler.ts#L220-L226) formats only the status field of the existing terminal `[STREAM]` line. The [formatter](https://github.com/cheaper-inference/OmniRoute/blob/1f47a122873e86118d324d64b9acdf8797e6ff22/open-sse/utils/streamStatusColor.ts#L12-L31) colors `complete` green, `client_disconnect` and `aborted` yellow, and `error:` red. Other statuses stay plain. Recognized `APP_LOG_COLORS` values force color on or off; otherwise stdout must be a TTY and `NO_COLOR` must be absent. An explicit true value takes precedence over `NO_COLOR`.

The [upstream tests](https://github.com/cheaper-inference/OmniRoute/blob/1f47a122873e86118d324d64b9acdf8797e6ff22/tests/unit/stream-status-colors.test.ts) cover the formatter, environment precedence, controller output and callbacks. A [separate test](https://github.com/cheaper-inference/OmniRoute/blob/1f47a122873e86118d324d64b9acdf8797e6ff22/tests/unit/console-interceptor-message-fidelity.test.ts#L228-L258) checks that its file interceptor strips ANSI sequences. The diff also documents the setting in `.env.example` and `docs/reference/ENVIRONMENT.md` and adds a changelog fragment.

## Local evidence and reconciliation

At DurinDoor head `d6196ed4f760674f3e24c44e03d336a809a83e62`, [`streamHandler.js`](../../../open-sse/utils/streamHandler.js#L35-L41) passes plain status text to `log.line` or `log.errorLine`, with a `console.log` fallback. Its [disconnect, abort and error paths](../../../open-sse/utils/streamHandler.js#L63-L105) emit `DISCONNECT: ...`, `ABORTED` and `ERROR: ...` respectively. The [logger](../../../src/sse/utils/logger.js#L51-L70) prints these messages without ANSI status formatting; `line` observes `LOG_LEVEL` and `errorLine` always prints. The colored session tag glyphs in that logger identify sessions, not outcomes. Searches of the checkout found no `APP_LOG_COLORS` or stream status color helper. The unrelated `[STREAM]` warning in `open-sse/handlers/chatCore/streamingHandler.js` and debug logger in `src/sse/utils/logger.js` are not the upstream terminal status line.

Normal completion differs: [`handleComplete`](../../../open-sse/utils/streamHandler.js#L80-L87) emits no status line, and the local streaming completion handler emits a `📊` summary through `log.line`. Thus upstream's exact line and green `complete` formatting cannot be copied verbatim. Any implementation must decide how the existing completion summary relates to outcome coloring and preserve local logging and lifecycle behavior. The absence of upstream's line or setting does not eliminate the user-visible gap for abnormal outcomes. Row 5 of [the first report](1073-nov24-commits-1.md) has the correct pending-gap disposition; row 61 of [the third report](1073-nov24-commits-3.md) correctly identifies the structural difference but its not-applicable conclusion is too broad. The first report's proposed specific implementation is not an approved port design.

The existing [interrupted stream test](../../../tests/unit/streaming-interrupted-detail.test.js) exercises client cancellation and upstream error accounting, but does not assert status colors or environment controls. Upstream's file-interceptor test cannot be assumed to apply directly to this different logging architecture; a port must verify any actual persistent log sink before deciding how to preserve plain file logs.
