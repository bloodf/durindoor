# #1073: Responses Read arguments qualification

Disposition: **report only; preserve the current Responses-to-Chat behavior**. The earlier [late-May assessment](1073-late-may-responses-tool-boundaries.md) identified a parity gap, but its proposed name-based acceptance is insufficient for this general-purpose bridge: a client can declare a different `Read` tool whose empty values are meaningful or required.

## Pinned upstream evidence

[OmniRoute #2937](https://github.com/cheaper-inference/OmniRoute/pull/2937), head `d25e32326d1cf9bee89653a33d3bb689e72a1944`, narrows its existing JSON-string cleanup to a tool named `Read` whose parsed value is an object. It leaves malformed JSON and non-object JSON strings intact and retains its existing object-argument cleanup. The enclosing merge `ec7233042c33e8a693b4ab72ba080372fe9db877` shows that cleanup applied to complete arguments in the deferred and ordinary done paths. The helper removes every top-level empty string or empty array, rather than checking a declared optional-field schema. A name alone does not establish Claude Code provenance or which fields are optional here.

## Local evidence and limitation

At DurinDoor base `2489958e30a2438bc3fe6b0d2a32350141b6409e`, `open-sse/translator/index.js` registers and uses the Responses-to-OpenAI converter as a general response pivot. `open-sse/utils/stream.js` supplies `clientTools` and provider metadata to the ordinary stream state, but a tool declaration or Claude-format request alone does not identify a Claude Code tool or prove that an empty field is optional. The search-enabled Responses-to-Claude adapter in `open-sse/translator/response/responses-to-claude.js` creates a separate `responsesBridge` state with only `toolCalls` and `model`; it does not forward those request declarations or a reliable Claude Code identity. Thus reliable identity and optional-field information do not reach both uses of the converter. The existing Read-specific sanitation in `open-sse/translator/response/openai-to-claude.js` is a separate downstream conversion and is not evidence of provenance at this boundary.

Locally, `openai-responses.js` emits the function header with empty arguments on `response.output_item.added`; it does not emit complete arguments carried by that event. It forwards function argument deltas as received, and emits a nonempty string from `response.output_item.done` only if no arguments were emitted for that call. A done-only item synthesizes the header first. The per-call emitted set prevents replaying done arguments after deltas or repeated done events; terminal completion does not replay function-call arguments. Object-valued done arguments are not cleaned or emitted by this path. No sanitizer is added, so generic `Read` and other tools retain the existing behavior, including unchanged string bytes at the done and delta boundaries.

A future port needs an existing trustworthy identity and field-level optionality at every relevant call site, plus focused offline added/done, delta and replay tests with a generic `Read` control. Neither inventing such provenance nor changing the bridge's added-event behavior is within this qualification.
