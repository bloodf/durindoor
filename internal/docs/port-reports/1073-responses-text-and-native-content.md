## Source-order repair

The snapshot recovery port above kept the recovered text of an item, but not its place in the stream. A Responses stream may deliver the delta of a later output item before the snapshot of an earlier one. The earlier item's recovered suffix was emitted when the snapshot arrived, which is after the later item's delta, so the client read `ACBD` where the source order is `ABCD`.

The repair is in `open-sse/translator/response/responsesTextSnapshots.js` and `open-sse/translator/response/openai-responses.js`:

- A tracked item carries its source position, the item id it was last seen under, and the text held back for it.
- A delta of a later item is held while an earlier item can still owe text. The hold ends when that earlier item finishes, so the recovered suffix of the earlier item is emitted before the later item's text.
- An item is finished when the upstream sends `response.output_item.done` for it, or when the stream reaches a terminal event. A `response.output_text.done` closes one content part and does not finish the item.
- Held text is released once, in source order, and never replayed. A snapshot that does not extend the tracked text of its item is not replayed; the streamed text is kept.
- The hold is bounded: `MAX_HELD_TEXT_CHARS` caps the held text. Past the cap the ordering guarantee is dropped and the held text is released in source order, so a malformed stream cannot grow the hold without bound.
- A terminal event, an error, and a cancel each release the held text before the final chunk, so no text is dropped.
- A single item streams incrementally: nothing is held when no earlier item can owe text.

Compatibility contract, unchanged by the repair: a rotated `item_id` on a known output position stays the same item, a new item that reuses an output position stays a different item, and tool and reasoning identity are untouched. The repair only orders text that is already recovered.
