## Method

1. `git show` of each row 91 commit (`3588f5ca`, `7a1b9d19`, `82ff9b48`, `cdafb29e`, `638e676c`) gave the exact diff, which is summarised below.
2. The imports and call sites in each diff were followed to the upstream subsystem they need. The first-add commit of each subsystem file was found with `git log --diff-filter=A 713bf17c -- <path>`, and fix commits with `git log --grep`.
3. Local owners were found with `git grep` over `open-sse/` and `src/`, and by reading the matching local files.
4. Prior dispositions were found by searching `internal/docs/port-reports/` for each upstream PR number.
5. Open-PR overlap: `gh pr list -R bloodf/durindoor --state open` returned 13 PRs, and `gh pr view <n> --json files` / `gh pr diff` were checked against every owner path below. The `origin/v5/*` and `origin/orq/tornl2/*` branches, issue #2034 (sign-in), issue #2305 (UI) and issue #2271 (route auth) were also checked.
6. Owner vetoes: `internal/docs`, `docs`, `AGENTS.md` and all 144 comments on #1073 were searched for "veto", "owner decision", "do not port", "exclude" and the subsystem names.

## Per-subsystem detail

### A. Provider breaker (`3588f5ca`, alias part)

- **Dependency order.** The dead-account part has no prerequisite (row 91 item 7). The alias part needs a provider-keyed failure state, because only such state can be keyed by alias rather than by canonical id. The local per-connection circuit is keyed by `connectionId`, so it cannot have this defect.
- **Recorded constraint.** The heartbeat report's disposition (#1485) says a provider-wide guard must not replace `connectionCircuitState.js`. A port of A is therefore additive: a provider-scope layer next to the connection circuit, never a rewrite of it. This is a recorded report disposition, not an owner veto. Row 91 already treats A as a parity gap, and this plan keeps both records.
- **Security and data boundary.** Process-local, in-memory state only. No credentials are read. An open provider breaker must not count local admission rejections, queue timeouts (`isQueueTimeout`) or cancellations, which matches the #1108 rule that cancellation releases without a failure ([connection-circuit-1108-draft.md](../connection-circuit-1108-draft.md)). Breaker status must not reach clients beyond the existing 503 or retry text.
- **Tests to port.** `account-fallback-alias-banned.test.ts` (alias reset clears dedupe; banned, expired and credits-exhausted filtered), plus the upstream breaker tests for network dedupe (#13887/#13899) when A1 lands. The local `tests/unit/connection-circuit-state.test.js` must stay green unchanged.
- **Docs.** `docs/features/error-rules-and-egress-cooldown.mdx` (provider-wide cooldown, alias handling).
- **Open-PR overlap.** Draft #2484 changes `open-sse/services/accountFallback.js` (`checkFallbackError`, around line 289) and `src/sse/services/auth/accountErrors.js`. It does not touch `filterAvailableAccounts` (line 819). It is a textual neighbour only; rebase after it merges.

### B. Session model history (`7a1b9d19`)

- **Dependency order.** B1 history store, then B2 context-cache protection (read and write the pin), then B3 universal handoff (handoff table, summary generation, injection), then B4 the #19110 scoping and #15459 config persistence for the handoff path. `7a1b9d19` only matters once B2 and B3 both exist, but its invariant (one row per successful target) applies from B1 onward.
- **Prior disposition kept.** #2653 deferred universal handoff "as a separate feature; no port". This plan does not reverse it: B3 is listed for sequencing only and needs that separate-feature decision. B1 and B2 do not depend on #2653.
- **Security and data boundary.** Session ids come from a client header or a fingerprint, so rows must be keyed per caller (`scopeHandoffSessionId`: `k:<fingerprint(apiKeyId)>:<sessionId>`, else `anon:`). Otherwise one key can pre-seed or read another key's pin. Upstream keys the context-cache row by `effectiveSessionId` and the handoff row by the scoped id, and the `7a1b9d19` skip fires only when the two strings are equal. A local port should use one scoped key for both writers. That is an open design choice for the PR, recorded here. New persisted table: it needs retention (upstream has a `used_at` cleanup index) and must be cleared by `clearSessionModelHistoryForCombo` when a combo's targets change. B3's summary generation is an extra model call per handoff, so it is cost-bearing and must stay opt-in and default off.
- **Local owners.** `open-sse/services/combo.js` (`handleComboChat`, successful-target settlement), a new `src/lib/db/repos/sessionModelHistoryRepo.js`, a new migration `038+` with a Postgres twin, `settings.comboStrategies[name]` for the toggle, and `src/lib/db/repos/combosRepo.js` for clearing on target change.
- **Tests to port.** `combo-session-model-history-once.test.ts` (all three cases), plus pin read and write and the per-key isolation from #19110.
- **Docs.** `docs/features/combos.mdx` (context-cache protection), `docs/operations/data-management.mdx` (new table and retention).
- **Open-PR overlap.** Drafts #2481 and #2486 both add migration `037-antigravity-rotation.js` (SQLite and Postgres) and edit `migrations/index.js`. B1's migration must take the next free number after they settle. Draft #2430 (v5 combos editor extraction) owns `dashboard/combos/**`, so any toggle UI waits for it; B1 and B2 can ship API- and settings-only. #2496 changes `src/sse/handlers/chat/combo.js` (auto pool scope), which is adjacent but separate.

### C. Codex plan gate (`82ff9b48`)

- **Dependency order.** C1 is the whole gate in one slice: `ddfb813a` (#17961) plus `82ff9b48` plus `f2e47a9d` (#20959). The gate is small (one 105-line module plus three call sites) and depends on nothing missing.

Fail-open when the plan is missing or `unknown` (upstream contract), and never send a paid-only model to a recorded Free/Go account, including explicit or pinned selection. ### D. Durable memory (`cdafb29e`)

- **Dependency order.** D1 store, settings and owner-scoped management API with non-stream extraction; then D2 retrieval and injection into prompts; then D3 streaming extraction; then D4 dashboard, MCP and CLI; then D5 optional backends (vector, embedding, rerank, claude-mem). - **Security and data boundary.** This is the most sensitive of the five. It persists user and model text per API key (`memoryOwnerId`), and D2 replays it into later prompts, so it is a stored prompt-injection surface. ### E. Claude extra-usage opt-in (`638e676c`)
