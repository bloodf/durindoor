## Current local behavior and evidence

The local Grok CLI speaks Responses. `GrokCliExecutor.transformRequest()` calls `normalizeResponsesInput()` on `input`, preserving array items, then sanitizes replayed reasoning and references. It does not currently rewrite `custom_tool_call` history or `additional_tools` items. `normalizeGrokCliTools()` flattens named tools to `type: "function"`; for a `type: "custom"` declaration this generic path does not construct the freeform `{ input: string }` parameter schema. See [grok-cli.js](../../../open-sse/executors/grok-cli.js) and [responsesApi.js](../../../open-sse/translator/formats/responsesApi.js).

The normal format-conversion path already defines a Responses custom-tool contract. In [openai-responses.js](../../../open-sse/translator/request/openai-responses.js), Responses custom declarations lower to Chat function tools with a required string `input`; custom calls and their outputs are represented as paired Responses custom items. The reverse Chat-to-Responses path retains custom declarations and emits `custom_tool_call` / `custom_tool_call_output` history. Response translation and buffered projection carry declared custom-tool identity back to the client, including `custom_tool_call_input` stream events and JSON output. Fixture evidence includes [port-6937-responses-toolcall-shape.test.js](../../../tests/translator/port-6937-responses-toolcall-shape.test.js), [v5-conformance-responses-json.test.js](../../../tests/translator/v5-conformance-responses-json.test.js), and [chat-responses-custom-tool-history-1419.test.js](../../../tests/translator/chat-responses-custom-tool-history-1419.test.js).

That translator behavior does not by itself fix Grok CLI's same-format Responses lane: when source and target are both Responses, `chatCore` takes native passthrough and does not run the translator's custom-tool conversion/restoration. The executor currently has a narrow namespace adaptation for this lane, evidenced by [grok-cli-namespace-tools.test.js](../../../tests/unit/grok-cli-namespace-tools.test.js), but no corresponding custom-tool round-trip fixture. The ordinary Grok CLI wire fixture [grok-cli-build-protocol.test.js](../../../tests/unit/grok-cli-build-protocol.test.js) uses a mocked proxy and demonstrates an available no-traffic test boundary.

`additional_tools` is separate. The Responses translator can include tools declared in such input items while translating to a different format. The Grok CLI passthrough has no equivalent hoist, and `chatCore`'s special removal of client-only envelope content is explicitly scoped to Codex passthrough. Adding Grok CLI hoisting, merge precedence, namespace/custom-child handling, or input-item removal would add client-side lite-mode behavior beyond the established top-level custom-tool contract.

## Disposition for PR #14738

**Accept narrowly as an ordinary offline regression fixture for the existing top-level Responses custom-tool contract; defer the `additional_tools` feature and other expansions.** The fixture should exercise Grok CLI's mocked executor boundary with one declared top-level `type: "custom"` tool. It should establish the freeform `{ input: string }` wire schema, preserve `call_id` and tool name across history and result restoration, and cover both streamed custom-input delta/done output and non-streaming JSON restoration. Keep ordinary function calls unchanged. Do not include `additional_tools`, namespace children, custom `tool_choice`, collision policy, tool caps, app changes, provider routing, or session behavior in this acceptance. This is fixture acceptance only; this report makes no product or test change.

No provider traffic was sent. No tests were run; the report-only change is checked with the requested file-content evidence below.
