# OmniRoute parity candidates: verification

Static review of the six candidates named in `omni-review-catalog.md` and
`omni-review-transport.md`, against this checkout and the cited/current
OmniRoute pull request diffs. No provider was contacted and no behavior was
executed. Upstream statements about live endpoints or provider responses below
are identified as upstream-reported evidence, not local observations.

## Findings

| Candidate | Classification | Recommendation |
|---|---|---|
| Claude effort suffix routing, #21347 | Missing feature with a concrete routing defect for advertised variants on authoritative synced catalogs | Port with a scoped test |
| TrustedRouter, #21364 | Missing provider feature | Port the provider if supported-provider breadth is desired; low-risk, bounded addition |
| Liquid System One, #21338 | Missing feature; catalog mislabels scope as out of scope | Consider as an explicit new native backend, with credential-origin and protocol tests |
| Z.AI live discovery, #21221 | Missing feature; not blocked by an owner-only test decision | Defer live discovery unless partial catalog semantics are designed; keep static fallback |
| Devin CLI readiness, #21365 | Proven auto-combo readiness gap when executable absent | Port advisory readiness filtering; do not treat host absence as credential health |
| Model availability evidence, #21303 | Missing substantial opt-in resilience feature; speculative as a user-impact defect locally | Defer pending design/owner decision on persistence and scope |

## Per-candidate trace

### Claude effort suffix routing — OmniRoute #21347

- **Local trace:** `open-sse/services/model.js:8-10` imports the provider-scoped thinking suffix parser, while `getModelInfoCore` at `:158-189` only parses provider/model identity and has no synced-catalog or effort-variant resolution. `src/sse/services/model.js:236-260` builds a routability checker from registry, combo, alias, and custom-model data; live model metadata is separately loaded and used by catalog materialization. There is no branch that maps a generated Claude `-{low|medium|high|max}` ID to a synced base row and carries effort to request dispatch. Consequently an advertised generated variant can resolve to a provider/model string but then fail the authoritative live-catalog routability check or reach the provider with a suffixed wire ID.
- **Upstream change:** PR #21347’s current diff changes `src/sse/services/model.ts`: it resolves the suffixed ID only when the provider/catalog says the Claude base exists, the suffix is in the provider’s allowed effort set, and the variant feature flag permits it; then it records the base model plus `resolvedThinkingEffort`. The PR adds regression coverage for an advertised GitHub variant, rejects undeclared effort IDs, and retains literal explicitly synced suffixed IDs. The catalog’s `a50680…` reference is one of two commits; the PR head also includes `5587a51`.
- **User-visible effect:** a Claude effort ID shown in `/v1/models` for a live-discovery provider can be submitted successfully and sent as the base wire model with the selected effort. Without this, the listed option can be unusable or sent under an unknown model name.
- **Overlap/constraints:** local suffix parsing is provider-scoped and may already support ordinary request thinking suffixes; do not broaden suffix acceptance or rewrite explicitly synced literal IDs. Preserve explicit request thinking fields over inferred suffix effort. This is not fixed merely by catalog metadata or thinking capability declarations.
- **Recommendation:** port the guarded resolver and tests. This is a behavior mismatch between generated public model IDs and authoritative live catalog identity, not a request to accept arbitrary `-high` names.

### TrustedRouter provider — OmniRoute #21364

- **Local trace:** `open-sse/providers/registry/index.js:1` imports the generated registry; a search of `open-sse/providers/registry/` and `src/` finds no `trustedrouter` entry or provider-specific configuration. Registry-backed provider lookup and connection model discovery are data driven, so a user cannot add this provider as a known API-key provider in the current built-in catalog.
- **Upstream change:** the cited SHA `91b540…` is only a one-line changelog commit. The current open draft PR has a three-commit diff, including a registry entry with chat and Responses endpoints, `/v1/key` validation, live `/v1/models` discovery and an embedding catalog; its documented endpoint root is `https://api.trustedrouter.com/v1`. This distinction matters: the cited pin alone does not contain the implementation.
- **User-visible effect:** users with a TrustedRouter key cannot select/configure a native TrustedRouter connection or discover its offered models through the built-in provider catalog. Current workarounds would require a compatible custom provider node and may not provide native validation or the provider’s curated metadata.
- **Overlap/constraints:** this is additive. Vendor-prefixed models need to remain under `trustedrouter/` to avoid shadowing direct vendor providers; use the PR’s registry behavior and existing compatible-provider patterns rather than assuming raw upstream model IDs are safe. Do not claim provider service availability from the PR’s stated live verification as a local test.
- **Recommendation:** port the provider registration and discovery if the product intends to support this service. Scope is bounded, but it is a missing provider rather than a broken existing route.

### Liquid System One — OmniRoute #21338

- **Local trace:** `src/app/api/v1/systemone/route.js:13-16` sends the endpoint to `handleSystemone`; `src/sse/handlers/systemone.js:96-100` resolves the requested provider/model, and `open-sse/handlers/systemoneCore.js:51-56` rejects any non-custom provider lacking a `systemoneConfig`. The `liquid` registry entry is chat-only (`open-sse/providers/registry/liquid.js:14-20`), with no System One config. Thus `liquid/d1` cannot use the native Liquid decisions endpoint locally. Local System One providers and endpoints are deliberately explicit in entries such as `open-sse/providers/registry/typesafe.js:20-28` and `laya.js:35-45`.
- **Upstream change and pin caveat:** the catalog’s `9bcaa778…` URL resolves to a revert of a different Liquid key-validation change, not the Liquid System One route. The current open #21338 PR has five commits and its diff adds a System One target resolver for `liquid/<model>`, mapping to `https://api.liquid.ai/decisions/v1/systemone`, strips the prefix for the wire model, and dispatches with the configured `liquid` connection key. The current diff also tests malformed IDs and preserves the separate `openrouter/liquid/...` route.
- **User-visible effect:** a Liquid connection cannot presently serve native System One decisions such as `liquid/d1` or `liquid/d1.2`; such calls fail as unsupported rather than reaching the decisions API.
- **Overlap/constraints:** this is a distinct native protocol and endpoint, not ordinary Liquid chat or the OpenRouter-hosted Liquid model. Upstream’s proposed route uses Liquid credentials and a request-body model; any port must maintain strict provider selection, prevent request-controlled host selection, validate model IDs, and make connection validation appropriate to decisions-only keys. The source catalog’s suggestion to send a tiny validation decision carries a provider call/cost and should be separately reviewed. Do not rely on the reverted validator patch as part of #21338.
- **Recommendation:** reclassify from “out of scope” to “missing feature; explicit product decision.” If implemented, port the native backend separately from chat catalog endpoint work, with security tests that prove the `liquid` key only goes to the fixed Liquid host.

### Z.AI live model discovery — OmniRoute #21221

- **Local trace:** `open-sse/providers/registry/zai.js:19-33` defines the Anthropic-format API-key transport and `:34-54` holds the static model list, including a local comment saying this catalog is the only one. The current `tests/unit/fleet-provider-zai-web-acceptance.test.js:69-80` asserts `fetchConnectionModels` returns the unsupported-listing response without making a request. It also checks raw `x-api-key` auth and the fixed `api.z.ai` message endpoint. The test’s actual compatibility/security contract is transport identity and credential destination; the no-discovery assertion is a product behavior choice, not an external approval gate.
- **Upstream change:** #21221 enables live `/api/paas/v4/models` discovery for `zai`. Its cited head `547e684…` is a follow-up fix for partial discovery: live list omission of `glm-4.7-flash` must not make that known-supported static row disappear; it marks the static row with the provider’s existing target format to preserve dispatch. The diff does not justify treating every live catalog as complete.
- **User-visible effect:** users currently see the curated static list, which can omit models newly added by Z.AI and can retain models no longer offered. Live discovery could improve freshness, while an authoritative but partial list can also hide valid static models or reject them at request time.
- **Overlap/constraints:** the cited acceptance test can be changed alongside implementation without an owner decision based solely on its existence. Preserve fixed host, raw `x-api-key`, `zai` versus `zai-web` identity separation, and fail-closed outbound URL handling. The current upstream follow-up itself demonstrates the compatibility risk of treating discovery as complete. This report makes no claim that the current vendor listing is complete or that any omitted ID works today.
- **Recommendation:** defer enabling authoritative live discovery until the source merge policy is explicit and covered (e.g. registry-dispatch union/partial-list fallback). If adopted, update the test contract to assert correct auth/origin and safe merge behavior, rather than preserving “never discover” as an invariant.

### Devin CLI readiness — OmniRoute #21365

- **Local trace:** `open-sse/executors/devin-acp-stdio.js:7-23` resolves the configured/local Devin executable but does not provide an availability probe. `open-sse/executors/devin-cli.js:225-230` surfaces spawn `ENOENT` only after dispatch. `src/app/api/providers/[id]/models/modelsConfig.js:479-481` exposes the local catalog independently of executable readiness. Auto-combo uses the runtime connection candidate construction in `open-sse/services/combo.js` / `src/sse/services/model.js`; no Devin binary readiness filter exists. The user-facing consequence is limited to auto-routing: a missing executable can be selected and then fail after dispatch. Direct explicit Devin requests should still return the actionable install/configuration error.
- **Upstream change:** #21365 adds an advisory, cached `isDevinBinAvailable()` probe beside the resolver and filters credentialed `devin-cli` connections from the auto-combo candidate list when unavailable. Its comment explicitly distinguishes host runtime readiness from account health, so no credential cooldown is recorded. PR is currently draft; the cited `e658152…` pin should be checked against its current three-commit diff before treating it as a final landed implementation.
- **User-visible effect:** auto combos avoid repeatedly selecting an unusable local CLI and can proceed to another eligible member; direct Devin dispatch remains available to report the missing executable.
- **Overlap/constraints:** `devin-cli-agentic` is a local ACP executor identity and its configured model catalog is not the same as the upstream provider ID. Verify aliases/IDs before porting the exact filter. Do not label a missing host executable as bad API credentials, cooldown the connection, or remove the model from direct use.
- **Recommendation:** port an advisory readiness filter only for the auto candidate path, keyed to the local executor identity. This addresses a concrete wasted dispatch and preserves direct diagnostic behavior.

### Model availability evidence — OmniRoute #21303

- **Local trace:** there is no persistent connection/model absence-evidence store in `open-sse/`, `src/`, or tests. `open-sse/services/accountFallback.js:207-219` makes selected OpenRouter 404s request-scoped because model/provider policy failures say nothing about account health; `:221-228` similarly avoids account-wide fallback for unknown Codex model IDs. `open-sse/handlers/chatCore.js:396-400` rejects only models explicitly marked with a static `routingUnavailableReason`. Existing handling is provider-specific and request-scoped; it does not learn that a particular connection revision and endpoint cannot serve a particular model.
- **Upstream change:** #21303’s current diff is a substantial opt-in facility with persistence/migration and routing integration. It accepts explicit 404 `model_not_found` evidence naming the exact wire model, requires two independent requests in 24 hours scoped to connection/revision/endpoint/model, expires after 30 days, clears on same-scope success, and excludes probes from evidence. It keeps catalog visibility and ordinary cooldowns separate. The catalog’s `7bfe2a…` is a pinned PR head, not a merged change.
- **User-visible effect:** if enabled and implemented, an auto/combo route could stop trying a model on a connection that repeatedly and explicitly says it does not serve that model, while trying another connection/model. No concrete current local failure was established by this static review; model-not-found handling differs by provider and some existing behavior intentionally avoids global lockouts.
- **Overlap/constraints:** persistent negative evidence can suppress legitimate traffic if stale or mis-scoped. Credential and endpoint revisions, exact wire model, endpoint kind, successful clearing, expiry, feature-flag default, probe handling, and fallback when all candidates are excluded are essential behavior—not incidental schema details. This is not redundant with current account fallback, but it is also not demonstrated as a proven defect.
- **Recommendation:** defer implementation pending an owner/design decision on those semantics and the migration. Treat as a new resilience feature, not a narrow bug fix; retain the current provider-specific protections against model 404s cooling an entire account.

## Source and confidence notes

- Local references identify static code paths only; no request was run and no live provider was contacted.
- Upstream PRs were read as GitHub diffs at review time. Some catalog “pinned” commits are incomplete or misleading for the implementation: #21364’s SHA is changelog-only; #21338’s cited SHA is a revert; #21347 and #21365 are open multi-commit PRs. The PR diffs cited above describe their current proposed changes, not merged behavior.
- “Proven defect” is reserved here for a code-path mismatch with observable intended behavior, such as generated Claude variants not resolving against live base models and Devin auto candidates reaching spawn without readiness filtering. Missing provider/backend support is classified as missing feature. Model-availability persistence is a plausible resilience feature, not proven local breakage.
