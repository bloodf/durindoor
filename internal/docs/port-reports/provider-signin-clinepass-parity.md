Production: select ClinePass and paste a key from app.cline.bot settings; its separate connection uses the `cline-pass/` model namespace. Discovery tries the public recommended-models feed, then authenticated models, with registry fallback. Chat uses the OpenAI-compatible endpoint and forces upstream streaming; the gateway can return non-streaming JSON. Usage reports percentage windows. Cline and ClinePass remain distinct provider identities.

The existing alternative account sign-in generates state and an extension authorization URL, accepts base64 embedded tokens, and falls back to a JSON code exchange. It is an authorization-code flow, not PKCE; the shared route owns flow state and callback ownership. Its practical ClinePass consumer support is uncertain: the local registry records an observed 401 for extension OAuth and defaults to API keys. No live account was used. Refresh uses the Cline JSON refresh endpoint for stored refresh tokens. Device flow is rejected by the existing provider dispatcher; no session or CLI import path is established here.

Staged only: `providerParity/clinepass/exchange.js` exports `exchangeClinepassCode`; `registration.json` specifies the central provider integration slot. It rejects unsupported modes, tokenless exchanges and sanitized failures while retaining the existing provider, route ownership and storage. It is not registered and does not change production behavior. Current production fallback exchange includes upstream error text in its exception and its provider decoder accepts an embedded JSON object without an access token. The shared completion handler rejects tokenless results before storage; the staged guard additionally protects direct provider callers. Existing route flow claims bind state, provider and the server-side proxy selection; a consumed flow rejects replay. Cline callbacks may omit upstream state, so callback handling must continue to use the existing bound-flow ownership checks during integration. The catalog fetch does not accept per-connection proxy options; request identity and proxy isolation remain separate integration concerns. These limitations are not evidence of live upstream behavior.

Closed-network evidence: `tests/unit/provider-signin-clinepass-parity.test.js` exercises the production provider, OAuth route and disposable connection storage, refresh and usage services, catalog and chat handler with mocked transports. It covers distinct account credentials and flow state, rejected state and replay, direct egress selection, code exchange, rejected refresh, unsupported device and import modes, catalog deadline aborts and streamed/non-streamed responses. Existing refresh and usage regression files cover additional quota cases. No test establishes live acceptance or per-account custom proxy dispatch.
