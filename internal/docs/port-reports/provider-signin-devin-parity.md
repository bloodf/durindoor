# Devin sign-in source comparison (#2034)

The comparison below covers supported paths and records the limits of the source evidence. Sources are MIT licensed:
[CLIProxyAPI dbe641f286a489ecb39e3c041c554371e6add864](https://github.com/router-for-me/CLIProxyAPI/tree/dbe641f286a489ecb39e3c041c554371e6add864),
[EasyCLIProxyAPI 29567ead8164a00724dfdc2087f02a23895636ee](https://github.com/router-for-me/EasyCLIProxyAPI/tree/29567ead8164a00724dfdc2087f02a23895636ee), and
[OmniRoute b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523](https://github.com/cheaper-inference/OmniRoute/tree/b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523).

CLIProxyAPI `internal/auth/devin/devin_auth.go`, `pkce.go`, `internal/cmd/devin_login.go` and `internal/api/handlers/management/auth_files_devin_oauth.go` implement browser PKCE and a session token exchange. Its auth service also supports a headless authorization URL with `cli_pkce_marker=1` when there is no redirect, and fetches `/v3/self`; DurinDoor's Desktop provider does not claim those paths. CLIProxyAPI `internal/runtime/executor/devin_executor.go`, `internal/runtime/executor/helps/devin_wire.go`, and `cmd/fetch_devin_models/main.go` implement its Connect request and catalog. EasyCLIProxyAPI `src/pages/EasyModePage.tsx` offers Devin OAuth and `src-tauri/src/management_api.rs` maps Cognition to Devin and delegates to the managed core; it does not establish a separate wire contract.

OmniRoute `src/lib/oauth/providers/devin-desktop.ts` registers two distinct entries: Desktop supports browser PKCE or import; CLI imports a token. `open-sse/executors/devin-desktop.ts` implements Desktop Connect and `open-sse/executors/devin-cli.ts` starts a local ACP subprocess. Agentic CLI has a separate executor. Neither the ACP path nor the cloud-agent `devin` provider should be treated as the Desktop Connect provider.

In DurinDoor production, select Devin Desktop and either import a session token or API key, or start browser sign-in and complete the fixed `127.0.0.1:59653/callback` flow. The provider sends S256 PKCE and exchanges the code for a prefixed session token. It stores no refresh token or expiry; a rejected session requires sign-in again. Its executor obtains a user JWT for requests, discovers models over Connect, and requires per-connection `enableSessionDispatch` to dispatch. Existing tests in `tests/unit/devin-desktop-provider.test.js` cover these paths with synthetic transport, including rejection and streams. Browser ownership and state are handled by the shared OAuth flow rather than a separate provider framework.

For Devin CLI, install and sign in to the local CLI or import a token in the CLI connection. The provider is import-only; its executor starts the local `devin acp --agent-type summarizer` process and passes the selected connection token as `WINDSURF_API_KEY`. Gateway proxy settings are rejected for this subprocess. `tests/unit/devin-cli-signin-parity.test.js` covers concurrent subprocess credentials and streamed responses. Agentic CLI is separately configured and uses its own executor and isolated home; the cloud-agent provider is separate again.

OmniRoute's CLI provider declares the same minimum 16-character import validation as Desktop, while the current DurinDoor CLI mapping accepts shorter strings. `src/lib/oauth/providerParity/devin/import.js` stages `mapDevinCliImport` to apply that validation and preserve the existing connection shape. `registration.json` identifies the single integration slot: the `devin-cli` `mapTokens` entry in `src/lib/oauth/providers.js`. Until that ordered shared wiring lands, production still accepts short nonempty CLI tokens; the staged helper is not registered. No device flow is supported for either provider, and no browser flow is enabled for the CLI entry. There is no independent CLI import service or device exchange path to port in the inspected sources.

The new closed-network test exercises the real provider objects and OAuth route with mocked outbound transport and storage: two independent PKCE challenges, verifier binding, state mismatch, same-owner supersession, expiry, replay prevention and unsupported-mode rejection. The existing Desktop and CLI tests cover discovery, rejected credentials, Connect streaming and usage, ACP streams and per-account identity. They do not prove byte-for-byte equivalence with every upstream request feature, live account behavior, or the upstream headless/profile paths. No real accounts or secrets were used.
