## Production and remaining gaps

DurinDoor has distinct `gitlab` and `gitlab-duo` connection identities. For either, register a GitLab OAuth application with the callback presented by DurinDoor, enter its instance and client ID, and complete the browser authorization. The existing route owns state and verifier handling; the provider exchanges the code with PKCE and fetches `/api/v4/user`. Duo can also use configured deployment client credentials. Alternatively, enter a personal access token and instance in the GitLab PAT form; the route verifies `/api/v4/user` and stores the selected identity. Neither provider exposes device sign-in here. No CLI or browser-session import contract was established.

Duo refresh uses the stored instance and client ID; `gitlab` has no corresponding specialized refresh lane. Duo sends code-suggestion requests to the configured instance and buffers the response before synthesizing SSE. No Duo-specific live model discovery was identified in the inspected production paths. These are existing production behaviors, not proof of complete upstream equivalence.

OmniRoute additionally exchanges the OAuth token at `/api/v4/code_suggestions/direct_access`, uses the returned gateway credentials, and has public completion fallback on direct-access rejection. Its executor has additional direct request and response handling. This checkout has no equivalent direct-access implementation; the direct-access flow is not staged here. Implementing it requires the ordered shared integration work, including secure gateway URL admission, connection-specific caching and transport identity. A standalone helper cannot make that behavior production-ready.

The current Duo executor includes upstream error body text in its returned error. Its refresh service also supplies the deployment client secret to a connection-selected instance without the instance match enforced by the exchange. Those production gaps remain open because the executor and shared integration files are outside this task's permitted changes. `src/lib/oauth/providerParity/gitlab/guards.js` stages `gitlabDeploymentSecret` and `gitlabRequestError`; `registration.json` identifies the exact refresh and executor integration slots. These helpers are not registered or active in production. Do not interpret the tests as a no-leak or complete account-isolation certification. No upstream wire contract is claimed for device, session, or CLI import.

The new closed-network tests exercise the real provider and executor with synthetic values and mocked fetch: device rejection, PAT verification and storage, sanitized exchange failure, concurrent PKCE exchange and refresh identity, pre-aborted requests, and buffered stream translation with a single submission. They do not exercise route ownership, direct gateway behavior, live discovery, proxy isolation, or every rejection path. Existing regression files are unchanged.
