# iFlow sign-in comparison (partial)

The dashboard authorization-code flow uses the existing iFlow OAuth configuration. A user signs in in the browser, completes the callback, and the server exchanges the code and verifies the profile before saving the key and OAuth tokens. The separate `src/lib/oauth/services/iflow.js` CLI service is currently unloadable: its `../config/index.js` import is absent. Its callback also does not check the generated state. It must not be described as a working production CLI flow. The dashboard has a separate cookie import: obtain a `BXAuth` cookie from an authenticated platform session and submit it in the iFlow cookie dialog. Its current handler looks up and refreshes a key, and stores the selected cookie and key. Its error responses can include upstream bodies; this remains a web integration issue.

The retained registry supplies a static model list; the executor sends OpenAI-shaped chat requests to the configured iFlow endpoint, adds a signed session header and requests usage on streams. OAuth refresh and local-only usage behavior are covered by `tests/unit/iflow-signin-parity.test.js`. Cookie identity persistence is covered by `tests/unit/v5-cookie-ingress-identity.test.js`.

The recursive GitHub trees for [CLIProxyAPI dbe641f](https://github.com/router-for-me/CLIProxyAPI/tree/dbe641f286a489ecb39e3c041c554371e6add864), [EasyCLIProxyAPI 29567ea](https://github.com/router-for-me/EasyCLIProxyAPI/tree/29567ead8164a00724dfdc2087f02a23895636ee), and [OmniRoute b15b2ee](https://github.com/cheaper-inference/OmniRoute/tree/b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523) contain no path with `iflow` in its name. The extracted CLIProxyAPI and EasyCLIProxyAPI source trees (excluding docs and test data) and OmniRoute `src/lib/oauth` and `open-sse` contain no case-insensitive `iflow` text. No iFlow provider implementation was found in these inspected source areas at the supplied pins; documentation and other OmniRoute directories were not exhaustively searched. No external wire contract is inferred from absent paths. The retained local files are the authority for the existing behavior described here. ## Staged web integration

`src/lib/oauth/providerParity/iflow/cookie.js` exports `importIflowCookie(cookie, { fetch, signal })`. It derives only one `BXAuth` value, performs the existing platform GET and one key-refresh POST, validates the returned name and key, and returns the existing connection shape. It suppresses upstream response and transport details and passes the abort signal to both requests. A failed POST is never retried because the provider may have accepted the rotation. Expired or rejected cookies fail at the lookup; obtain a fresh browser cookie and retry manually. The helper does not store a connection, check ownership, or itself prevent a later user-initiated import. The caller must authenticate the request and use the existing connection model.

The exact integration slots are listed in `src/lib/oauth/providerParity/iflow/registration.json`: replace the provider-specific lookup and rotation in `src/app/api/oauth/iflow/cookie/route.js`, pass `request.signal`, persist via `createProviderConnection`, and return a generic error and secret-free response. The helper is not registered, so the current production cookie route retains its existing behavior and error leakage. OAuth web wiring and the existing flow/state guards are unchanged. No device flow or dynamic model-discovery endpoint was found in the inspected local iFlow implementation; the registry is static. The CLI service has a missing import and is not a usable sign-in path in this checkout. No live account or browser was used.
