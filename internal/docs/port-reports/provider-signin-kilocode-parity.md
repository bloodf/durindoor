# Kilo Code sign-in comparison

Scope: MIT-licensed DurinDoor and the pinned MIT upstream projects. Source comparison uses CLIProxyAPI `dbe641f286a489ecb39e3c041c554371e6add864`, EasyCLIProxyAPI `29567ead8164a00724dfdc2087f02a23895636ee`, and OmniRoute `b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523`. The checked-out CLIProxyAPI and EasyCLIProxyAPI trees have no tracked paths or text references to Kilo Code, kilocode or kilo.ai. They do not establish a Kilo sign-in, refresh, import or inference contract. OmniRoute's applicable implementation is `src/lib/oauth/providers/kilocode.ts`, `src/lib/oauth/constants/oauth.ts`, and `open-sse/config/providers/registry/{kilocode,kilo-gateway}/index.ts`; its usage implementation is `open-sse/services/usage/kilocode.ts`.

## Production today

* **Kilo Code (`kilocode`)**: start device sign-in in the provider dashboard, open the supplied verification URL and approve it. `src/lib/oauth/providers.js` posts to `/api/device-auth/codes`, polls the returned code, and stores the approved bearer token and email using the existing connection flow. It optionally reads `/api/profile` for the first organization and passes that organization's ID on requests. OmniRoute's pinned provider implements the same device endpoints and status mapping, but does not perform this profile lookup. Neither provider supplies a refresh token or expiry; reauthorize after rejection. This device protocol does not use PKCE. The returned user code is also the device code, as in the source protocol; the verification URL and code should be treated as sensitive until the flow ends. The existing shared route binds each flow to a provider and owner intent, uses an opaque flow ID, and consumes successful claims once.
* **Kilo Gateway (`kilo-gateway`)**: configure the gateway through the provider dashboard, with an API key if needed. It uses `/api/gateway/chat/completions`, separately from Kilo Code's `/api/openrouter/chat/completions`, and does not send the Kilo Code organization header. Local catalog discovery uses `/api/gateway/models` for both registry entries; OmniRoute declares `/api/openrouter/models` for Kilo Code and `/api/gateway/models` for the gateway. Local Kilo Code has a static fallback catalog. The local gateway is configured with optional authentication. OmniRoute also describes anonymous Kilo Code access; that is not established as local production behavior.
* There is no Kilo-specific authorization-code exchange, session import, CLI credential import, or refresh contract in these pinned sources. No such mode is added here. OmniRoute additionally supports direct API keys on its `kilocode` entry; this report does not claim local dashboard registration of that mode.

The existing executor supplies bearer credentials and, for Kilo Code, the connection's organization ID. Existing generic translation and streaming paths are separate from the device provider. The shared route rejects expired or already claimed flows before polling; the provider fetch itself does not receive the route abort signal, so in-flight transport cancellation is not established. OmniRoute has personal balance and Kilo Pass usage code in `open-sse/services/usage/kilocode.ts`; a matching Kilo-specific local usage service was not found. This change does not establish full translation or usage parity. In particular, the production device-initiation failure currently includes an upstream response body in its exception. Treat that as an unresolved disclosure risk until the staged integration below is applied.

## Staged web wiring

`src/lib/oauth/providerParity/kilocode/errors.js` exports `kilocodeDeviceInitiationError(status)`. `registration.json` identifies the exact branch in `src/lib/oauth/providers.js` where the shared auth batch should use it. It returns a status-only error and retains the existing 429 message; it is not registered in production. Existing ownership, state and connection storage must remain in the shared handlers. No new gateway or storage is introduced.

The focused closed-network tests exercise the real provider, shared route, model discovery, executor and same-format stream translator with synthetic tokens and mocked fetch. They cover concurrent proxy/account identity, pending and rejected device statuses, expiry, duplicate submissions, optional profile failure, catalog credential isolation, and separation from gateway headers. They do not establish in-flight cancellation or usage parity. Existing regression files were not changed.
