# Kimchi sign-in investigation (#2034)

DurinDoor currently offers the Kimchi browser-token flow and API-key entry. For browser sign-in, select Kimchi, open the supplied sign-in URL, and complete the callback or paste the returned token/callback as directed. The provider validates the bearer token and optionally retrieves a profile; its mapped connection has no refresh token. An expired or rejected token requires sign-in again. API-key entry uses the existing provider connection UI. Model discovery sends the selected credential to the metadata endpoint and falls back to the static catalog when discovery yields no models. Requests use the OpenAI-format chat-completions endpoint and bearer authentication.

The shared authorization route binds state, flow ownership and proxy selection to the existing flow store; Kimchi's URL has no PKCE parameters. The separate KimchiService validates callback state and rejects 401/403, but its validation fails open on network errors and other statuses. The web provider instead rejects every non-OK validation response. These are distinct production behaviors. The CLI service checks state before errors, returns a fixed rejection message, accepts only one callback per attempt, and uses a five-minute deadline and /callback when optional configuration is absent. Its profile lookup uses the registry's userInfoUrl. No device grant, CLI credential import, or refresh grant is implemented by the Kimchi provider. Device requests are rejected before transport. The common generator creates PKCE material but does not send it for this browser-token flow.

The requested MIT source inventories were inspected at [CLIProxyAPI dbe641f](https://github.com/router-for-me/CLIProxyAPI/tree/dbe641f286a489ecb39e3c041c554371e6add864), [EasyCLIProxyAPI 29567ea](https://github.com/router-for-me/EasyCLIProxyAPI/tree/29567ead8164a00724dfdc2087f02a23895636ee), and [OmniRoute b15b2ee](https://github.com/cheaper-inference/OmniRoute/tree/b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523). Their recursive Git trees were not truncated and contain no Kimchi-named paths. This does not exclude generic compatible providers or source under unrelated names, and establishes no upstream wire contract.

The first-party MIT [Kimchi CLI browser-token implementation](https://github.com/getkimchi/kimchi/blob/b4e3105dc84daa6eb7e8e3834efc0fdb90d96770/src/cli-auth/index.ts) uses a loopback callback, state and a token. Its separate [OAuth implementation](https://github.com/getkimchi/kimchi/blob/b4e3105dc84daa6eb7e8e3834efc0fdb90d96770/src/cli-auth/oauth.ts) implements authorization code with PKCE and refresh. This newer variant is not implemented or staged here; its regional configuration, ownership, exchange, rotation and request handling need a separate complete integration before it can be offered. No parity claim is made for it. There is no staged registration in this change.

The focused closed-network tests exercise the actual web route, provider functions, CLI service, flow store, executor, translator and catalog service with synthetic tokens and mocked transports. They cover state mismatch, one-time claim and replay, independent credentials and proxy selections, callback deadlines, rejected tokens, catalog discovery, bearer headers and OpenAI-format streaming chunks. They do not establish live provider behavior, real proxy transport, refresh or the unimplemented SSO flow. No live accounts or provider endpoints were used.
