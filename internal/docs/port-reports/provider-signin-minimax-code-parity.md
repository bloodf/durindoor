# MiniMax Code sign-in and request parity (#2034)

## Production and operator steps

DurinDoor registers `minimax-code` as an OAuth device provider, separate from the `minimax` and `minimax-cn` API-key identities. Select MiniMax Code, choose `en` or `cn`, open the displayed verification URL, and approve the device code. The shared flow creates and retains the PKCE verifier, binds and claims the flow, stores the resulting access and refresh tokens on its connection, and consumes a completed flow. Importing a pasted token is unsupported. There is no local CLI profile import or write. See `docs/providers/minimax-code.mdx` for detailed setup.

The account issuers are `https://account.minimax.io` and `https://account.minimax.cn`; the public client is `mcode-public`, scope `agent.default`, audience `agent-backend`. The device form posts to `/oauth2/device/code` with an S256 challenge; the token endpoint `/oauth2/token` receives the device grant and verifier or the refresh grant and token. The account user agent is `minimax-code-cli`. The region travels with the private device code and is stored on the connection for refresh. Connection-specific proxy options accompany each request. Account errors returned by the provider adapter now use known protocol codes and do not expose upstream descriptions.

The catalog is static: `MiniMax-M3.1-Flash` and `MiniMax-M3`; no model-discovery endpoint was identified. The international gateway is `https://agent.minimax.io/mavis/api/v1/llm/v1/messages`; it receives Anthropic Messages with bearer authorization, `anthropic-version: 2023-06-01`, `User-Agent: MiniMaxAgent`, JSON content type and a stream-dependent accept header. A connection must explicitly set `providerSpecificData.enableSessionDispatch` to `true`; CN needs a trusted explicit MiniMax gateway URL. Existing closed-network tests cover model listing, OpenAI-to-Anthropic request and stream translation, usage, refresh after 401, and per-connection credentials. They do not establish live-account behavior.

## Staged web change

`src/lib/oauth/providerParity/minimax-code/web.js` exports `assertMinimaxCodeWebAction(action)`. Its registration manifest identifies the shared OAuth route as the integration slot: call it for MiniMax Code after resolving provider/action and before beginning a browser authorization or exchange, for both GET and POST. It rejects `authorize`, `exchange`, and `import-token` with `OAUTH_VALIDATION_FAILED`, while leaving device operations with the existing flow. The current shared route already rejects token import before network, but currently accepts `authorize` as a device-flow metadata response with a null authorization URL. The helper is not yet wired; the staged-only assertion is isolated in the parity test. Existing PKCE, ownership, flow storage and connection model remain the integration mechanism.

## Gateway replay and disclosure (production change in this unit)

`open-sse/executors/minimax-code.js` (the dedicated provider executor) and one provider-scoped branch in `src/sse/handlers/chat/singleModel/postProcess.js` now enforce:

- **Fixed public messages.** Every non-ok answer is built by the executor with a fixed message per failure class (400, 403, 404, 413, 429, 5xx, outcome unknown) and a fixed code. Gateway bodies are read only to classify (context-window detection, 200 error envelopes); their text is never echoed. `Retry-After` is forwarded only as delta-seconds or an IMF HTTP date. `parseError` hands the executor-authored code to the account layer.
- **Replay only when the gateway definitely did not do the work.** The in-executor retry (count `MINIMAX_CODE_GATEWAY_RETRIES`) covers an explicit 429 answer and a thrown transport error whose code (on the error or its `cause` chain) proves the request never reached the gateway: `ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, `ENETUNREACH`, `EHOSTUNREACH`, `UND_ERR_CONNECT_TIMEOUT`, `ERR_PROXY_CONNECTION_FAILED`. The retry reuses the same credentials, `proxyOptions` and caller signal; a caller abort during backoff rejects without another send. Exhausting a provably unsent retry answers 503 `gateway_unreachable`; the account layer may then try a sibling, because nothing was sent.
- **Possibly accepted work is never replayed.** A transport error without a proven-unsent code (`ECONNRESET`, `EPIPE`, `UND_ERR_SOCKET`, `ETIMEDOUT`, or no code), any gateway 5xx (500, 502, 503, 504, 529), a 200 envelope carrying an overloaded or other server error, the header deadline (502) and the whole-call timeout (500 `gateway_timeout`) are outcome-unknown. A bare 500/503/529 is not proof that no work or billing occurred, and no pinned source documents a no-work refusal for them (follow-up below). The executor answers `upstream_outcome_unknown` without retrying. For `minimax-code` only, `processAttemptResult` treats that code, `gateway_timeout`, or a `connect_timeout`/`network` transport failure as terminal before every retry path: it sets the existing internal `upstreamPartialOutput` marker so `runWithTransientBackendRetry` also stops, does not try a sibling account, and does not call `markAccountUnavailable`, because nothing proves the account failed. Other providers are unaffected; Codex credential-quota handling is untouched.
- **Usage stays unknown.** The client error carries no `usage`. The follow-up below records one unknown-cost receipt for the selected connection instead of no row.

Superseded by the follow-up: operator `requestPolicy` retry rules can no longer override the zero retry for 5xx, network or header-deadline outcomes. `MINIMAX_CODE_GATEWAY_RETRIES` still caps at 3.

Divergence from OmniRoute b15b2ee: its `minimaxCodeGateway.ts` retries dropped connections and 5xx alike and surfaces a sanitized upstream message. DurinDoor deliberately does neither.

### Obsolete assertions changed, with evidence

Run before the change against the new executor (`vitest run unit/minimax-code-budget.test.js unit/minimax-code-provider.test.js ...`): 5 failures, exactly these assertions, all encoding the behavior this order removes.

- `tests/unit/minimax-code-budget.test.js` "retries a dropped connection once": the mock throws a bare `TypeError("fetch failed")` (no proven-unsent code) and expected a second send. That is the replay after possibly accepted work. Replaced by "retries a connection refused before sending once" (new `refused` step with `cause.code = "ECONNREFUSED"`); the dropped case is asserted as single-send in the parity file.
- Same file, "retries a %i once, then surfaces the error with its own status" (429, 500, 503): `message` `toContain("synthetic N")` asserted the echo of upstream text. Now `not.toContain`; status, retry count and code assertions are unchanged.
- `tests/unit/minimax-code-provider.test.js` "maps quota responses to 429 with the retry hint": `toContain("plan quota reached")` asserted the echo of upstream text. Now `not.toContain`; the 429 status, `quota_exceeded` code and `Retry-After: 17` assertions are unchanged.

No other existing assertion changed. After the change: the four existing MiniMax Code files pass 58/58; adjacent suites touching `postProcess`, single-model stages, partial-output no-replay and the registration batch pass 188/188.

### Follow-up: accepted-work gaps closed (Refs #2034)

The public guide `docs/providers/minimax-code.mdx` now states the narrower rule. Details, evidence limits and focused runs are in `internal/docs/minimax-code-2034.md` ("Accepted-work follow-up"). In short: only 429 and proven-unsent DNS/connect failures are retried; MiniMax vetoes every other HTTP retry in `computeRetryDelay` and drops non-429 operator retry rules from its own request policy; `chatCore` writes one `saveRequestUsage` receipt per unknown outcome on the selected connection (`cost: null`, `costStatus: "unknown"`, `costSource: "minimax-unknown-outcome"`, `status: "error"`, `meta.outcome`/`meta.tokenStatus: "unknown"`; the zero token columns are frozen-schema placeholders, not measurements); the combo loop returns a MiniMax unknown outcome instead of trying the next model, and awaits MiniMax cancellation at its own deadline instead of racing past it.

## Evidence

`cd tests && node node_modules/vitest/vitest.mjs run unit/provider-signin-minimax-code-parity.test.js --maxWorkers=2`, in a private `HOME`/`DATA_DIR`/`TMPDIR` with a credential-free environment: 28 tests pass. The file covers the device grant, PKCE, flow ownership and single consumption, denial, expiry, token-import refusal, refresh isolation and the account deadline from the earlier candidate. It adds executor contracts (definite-refusal replay, single send for 502, 504 and dropped connections, provably unsent retry on the same token and proxy, cancellation during backoff, fixed messages and filtered `Retry-After`, concurrent account and proxy isolation). It also adds route-level `handleChat` regressions on a real SQLite connection store with two accounts. With the `postProcess.js` branch reverted, the four outcome-unknown route cases fail: the request is replayed on the sibling account. With it, they pass. The staged-only web-guard assertion remains in its own isolated block.
