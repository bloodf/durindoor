# Muse Code sign-in parity (#2034)

This is a closed-network assessment; no account, browser, or live credential was used. The new response validator is **staged and unregistered**. It does not change production behavior. Its registration manifest names the exports and integration slots. The existing OAuth route owns flow state, connection ownership and storage; the Muse device grant does not use PKCE.

## Production and user steps

- `muse-code` (`mc`): choose device sign-in, open the returned Meta verification link and enter the displayed code. The device token is retained as the renewable credential; a separate subscription key is minted for inference. Mint failure at login leaves the device token for a later remint. A rejected inference key can trigger remint; attestation denial is surfaced without another attempt. The subscription path uses the Muse client identity. Account entitlement and client attestation are not established by these fixtures.
- A separately issued Meta Model API key can be pasted into the `muse-code` API-key connection. It uses the same Responses endpoint, carries no Muse fingerprint, and cannot be reminted from a device token. Account-scoped `/v1/models` discovery exists; the local static catalog is separate.
- `meta-llama` (`meta`) is the distinct `api.llama.com` API-key provider. `muse-spark-web` is a separate web-session provider; neither is a Muse Code device credential. Do not import or reinterpret their credentials as Muse Code. No Muse Code CLI credential-file import or authorization-code/PKCE grant is established by these sources.

The local adapter currently accepts arbitrary verification URLs and returns upstream poll error descriptions. The staged helper validates Meta-origin links, bounds expiry, and replaces upstream diagnostics with fixed messages. Until integration, these protections do not apply in production. The staged transport supplies a deadline, redirect rejection and sanitized network errors; these also require integration. The shared `authorize` route currently accepts this device-only provider, so the staged action guard must be registered before unsupported modes are considered blocked. The focused tests exercise route-level provider binding, in-flight claims, replay and device-flow expiry. The existing adapter does not propagate an abort signal into its device requests; the staged transport accepts one when wired. The local model discovery does not merge OmniRoute's additional Muse metadata; session ownership allocation and quota handling also remain separate work.

## Evidence and limitations

`tests/unit/provider-signin-muse-code-parity.test.js` exercises the production provider entry points and mint service with synthetic credentials and mocked transports, including concurrent proxy and credential separation, remint, rejected mint, route claims and expiry, account-scoped discovery, and Responses streaming and usage. A single isolated block tests the staged validator. Existing `muse-code-oauth.test.js`, `muse-code-route.test.js`, `muse-code-signin-parity.test.js` and `meta-provider-id-collision.test.js` cover additional paths, including model and request identity. Polling transport abort and diagnostic sanitization are staged only. Production error descriptions can still contain upstream text; complete parity is not claimed.
