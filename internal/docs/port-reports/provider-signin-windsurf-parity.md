# Windsurf sign-in comparison (#2034)

The local `windsurf` provider accepts a manually supplied token through the dashboard import-token action. The connection has no refresh token or expiry by default. Users must obtain their own Windsurf token and paste it into the provider connection; this checkout does not implement a Windsurf OAuth authorization, device flow, session login, CLI credential import, token refresh, or account-specific model discovery. The existing executor sends gRPC-web chat requests and translates supported text responses to OpenAI JSON or SSE. Tools and media are rejected. Its model mapping is local, not an upstream discovery contract. These observations do not establish that a live service currently accepts the protocol.

The existing import route validates and stores the token using the ordinary connection model and hides credentials in its response. Authorization-code state, PKCE, polling and flow ownership are not applicable to this import flow. Requests carry each connection's token and proxy. The executor currently returns non-success upstream responses unchanged and can expose their bodies; gRPC error messages are also passed through. Therefore upstream-body secrecy is not established. Fixing that requires changing the shared executor, which is outside this unit's permitted paths. The production import route also does not verify the imported token; rejection occurs on use.
