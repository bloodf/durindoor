# Zed sign-in comparison (#2034)

MIT sources inspected: [CLIProxyAPI dbe641f](https://github.com/router-for-me/CLIProxyAPI/tree/dbe641f286a489ecb39e3c041c554371e6add864), [EasyCLIProxyAPI 29567ea](https://github.com/router-for-me/EasyCLIProxyAPI/tree/29567ead8164a00724dfdc2087f02a23895636ee), and [OmniRoute b15b2ee](https://github.com/cheaper-inference/OmniRoute/tree/b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523). The complete GitHub trees of the first two have no Zed provider path; no Zed hosted sign-in or request contract was established from them. This is a source-path finding, not a claim about every possible generic proxy configuration.

OmniRoute's [hosted provider](https://github.com/cheaper-inference/OmniRoute/blob/b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523/src/lib/oauth/providers/zed-hosted.ts), [auth helper](https://github.com/cheaper-inference/OmniRoute/blob/b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523/open-sse/shared/zedAuth.ts), [registry](https://github.com/cheaper-inference/OmniRoute/blob/b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523/open-sse/config/providers/registry/zed-hosted/index.ts), and [executor](https://github.com/cheaper-inference/OmniRoute/blob/b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523/open-sse/executors/zed-hosted.ts) define native RSA sign-in, account and LLM token exchange, catalog and completion streams. Its separate [zed provider](https://github.com/cheaper-inference/OmniRoute/blob/b15b2ee6ac0f57af254be4a3cc60ba8a6cc9a523/src/lib/oauth/providers/zed.ts) is an IDE keychain/manual import bridge for other providers, not hosted inference. Neither device authorization nor a hosted CLI credential import is established by these sources.

DurinDoor already registers `zed-hosted` in production OAuth and the gateway. Start its sign-in from the dashboard, authenticate in Zed, and use the loopback callback or paste its URL into the active flow. The flow stores an RSA private key in the existing verifier slot, not PKCE; the existing OAuth flow owns state and account binding. The returned long-lived account token has no refresh grant; an LLM token is obtained for an organization and renewed on expiry/rejection. Model discovery and completion require `providerSpecificData.enableSessionDispatch` to be the boolean true. The hidden `zed` identity represents IDE key import and must not be substituted for hosted credentials. Live acceptance was not tested.

Existing `zed-hosted-provider.test.js` exercises discovery, request/stream translation, expiry, rejection and separate account tokens with mocked transports. The new focused file exercises callback key ownership, profile identity, timed cache expiry and the opt-in guard. These are closed-network evidence, not proof of live service behavior.

Open gaps: the current cache key includes user, organization and token but not system/client or proxy identity, so same-credential connections with different client/proxy settings are not proven isolated. Upstream error bodies can propagate through existing helpers and executor error parsing; secret/body redaction is not established. Existing shared handler/executor files are outside this task's permitted edits. No helper is staged and no new web registration is required for the already registered hosted provider. The full requested parity and security coverage therefore remains incomplete.
