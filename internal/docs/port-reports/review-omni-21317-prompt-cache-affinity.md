# OmniRoute #21317 — prompt-cache session affinity

## Source snapshot

The PR adds an opaque SHA-256 `prompt_cache_key` for supported OpenAI/Codex wire requests when a trusted authenticated API-key ID and a validated client session are available. The digest includes principal, provider, connection, wire model and session. It preserves explicit client keys, gates on cache support and opt-out, and passes the principal through the credential-refresh stream retry. Session extraction checks listed headers, raw request body session/conversation fields, and bounded Claude metadata JSON. Its new focused test covers principal/session/connection/model boundaries, malformed/missing identity, unsupported/cache-opted-out requests, explicit-key precedence, and the retry principal path.

## DurinDoor comparison

Compared `origin/main` (`29490b783e83176d4d6a4162f76ee3dc79db66ea`) and frozen train tree `32a783d76d45d90bf0517015442f43fadd96106c` through Git objects. Both contain the same relevant implementation: `open-sse/handlers/chatCore.js` injects request-scoped `_cachePrincipalId`; `open-sse/executors/default.js` hashes provider, principal, connection, model and session into an opaque key; and caller keys retain precedence. The existing [#19803 report](open-prs-nov25-25-port-2.md) records this partial cache-key port and explicitly leaves the Codex key path and custom-node wire guard as separate open items. Those unchanged dispositions are not re-reviewed here.

**Verdict: missing/wrong behavior — low severity, limited to opt-in default-executor cache keys when no client session exists.** In `open-sse/executors/default.js`, `injectPromptCacheKey()` falls back to `resolveSessionId()` if translation did not set `_clientSessionId`. In `open-sse/utils/sessionManager.js`, `resolveSessionIdWithProvenance()` returns `deriveSessionId(connectionId)` with `requestScoped: true` when there is no client session, assistant anchor, or workspace ID. The caller does not check `_clientSessionIsGenerated`, so an opted-in request with no valid session still receives a repeatable connection-scoped `prompt_cache_key`, whereas #21317 returns the body unchanged without a valid client session. This can group unrelated sessionless conversations on the same route and reduce cache affinity correctness. The principal/connection/model scoping itself is already present from #19803.

Precise trace: with `providerSpecificData.enablePromptCacheKey === true`, no `_clientSessionId`, no session-bearing headers/body, and no workspace ID, `injectPromptCacheKey(provider, body, credentials, model)` calls `resolveSessionId()`; the resolver reaches `deriveSessionId(connectionId)`; `normalizePromptCacheKey()` hashes that derived value and writes `body.prompt_cache_key`. `captureSessionId()` records the generated provenance in `credentials._clientSessionIsGenerated`, but `injectPromptCacheKey()` does not consult that flag. Relevant code: [`default.js`](../../../open-sse/executors/default.js), [`sessionManager.js`](../../../open-sse/utils/sessionManager.js), and existing coverage [`portor-19803-prompt-cache-key-scope.test.js`](../../../tests/unit/portor-19803-prompt-cache-key-scope.test.js). No test was run; dependency installation and candidate execution were not needed for this static trace.
