The upstream defect is specific: when an undersized candidate causes the context compatibility filter to reorder the pool, its override-first tier can put a fitting override-backed target before a higher-scoring fitting target under Auto. The patch preserves Auto strategy order among confirmed-fitting targets except when the near-boundary override rejection protection applies; declared strategies retain override-first behavior. Its tests cover the filter and target-resolution pipeline.

DurinDoor's `origin/main` is `29490b783e83176d4d6a4162f76ee3dc79db66ea`; the frozen train object reviewed is `train/2` at `32a783d76d45d90bf0517015442f43fadd96106c`. The behavior-bearing files are identical between these refs. In both, `open-sse/services/combo.js:1560-1584` validates and applies optional `contextRequirements` eligibility before rotation, returning 503 if that configured filter empties the pool. This is a configured minimum-context filter, not a per-request compatibility filter, and it has no override-based tiering. `open-sse/services/combo.js:1586-1616` then rotates/scorers the eligible pool and only reorders for required capabilities; `scoreModelForTask` at lines 1001-1022 scores context pressure but does not remove or tier targets. `open-sse/services/combo/contextRequirements.js:144-163` confirms the eligibility filter preserves surviving input order.

Thus the PR's trigger—an undersized target causing override-first compatibility tiering to reorder otherwise fitting Auto targets—does not occur in the local route. A low-context model may receive a lower task score, and an explicitly configured minimum can exclude it before rotation, but neither produces the claimed override-first reorder. This is a routing architecture difference, not evidence that the candidate behavior is missing.
