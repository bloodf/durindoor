This is not a CLI Tools card. `ollama` and `ollama-local` are providers. When the client speaks Claude Messages, DurinDoor picks the Claude transport (`/v1/messages`) instead of `/api/chat`. Other client formats still use the Ollama `/api/chat` transport.

Point Claude Code, or any Anthropic client, at DurinDoor as in [Claude Code](../../../../docs/integrations/claude-code.mdx). Put `ANTHROPIC_BASE_URL` on this gateway, not on Ollama. Use a model id `ollama-local/<name>` or `ollama/<name>` from `GET /v1/models`.

You need an `ollama-local` or `ollama` connection, a DurinDoor API key, and a model that connection actually serves. Add the local host on **Providers** if it is not `http://localhost:11434`. See [Free and local](../../../../docs/providers/free-and-local.mdx).

## Native Claude transport

Both registry entries declare a `claude` transport and these quirks: `preserveNativeClaudeThinking`, `normalizeNativeClaudeTransport`, `dropClaudeCacheControl`, `claudeImagesRequireBase64`.

| Provider | Claude transport URL | Auth |
| --- | --- | --- |
| `ollama` (cloud) | `https://ollama.com/v1/messages` | `Authorization: Bearer` |
| `ollama-local` | `http://localhost:11434/v1/messages` | `Authorization: Bearer` |

Ollama authenticates with Bearer, not Anthropic's `x-api-key`. Local Ollama does not validate keys; DurinDoor still sends Bearer when a key is present.

`resolveRequestTransport` prefers a transport whose format matches the client `sourceFormat`. A Claude client therefore hits `/v1/messages` and skips the OpenAI hop. Matching source and target return the chunk unchanged, so text, `tool_use`, `thinking`, `redacted_thinking`, `image`, and `document` blocks keep their order.

`cache_control` is stripped because Ollama does not accept it.

Remote image URLs are fetched through the guarded image loader and rewritten as inline base64. Ollama's Messages endpoint does not fetch image URLs. Private, loopback, and link-local destinations are rejected.

## Streaming

The client-facing stream stays Claude SSE: `event:` plus `data:` frames. Claude passthrough does not append an OpenAI `data: [DONE]` sentinel. A stream that ends before `message_stop` throws `Claude passthrough stream ended before message_stop` instead of being stored as a successful truncated answer.

## Local host URL

`resolveOllamaLocalHost` reads `providerSpecificData.baseUrl`, or `http://localhost:11434`. It strips a trailing `/api/chat` and a trailing slash. The executor then uses that origin plus the runtime transport path, so a stored value of `/api/chat` or `/v1/messages` does not duplicate the suffix.

`scripts/auto-configure.mjs` and `/api/settings/auto-configure` do not create Ollama connections. They probe Headroom, PxPipe, and Firecrawl only. There is no `/api/cli-tools/ollama-settings` route.

<Callout type="warn">
Do not point Claude Code at `http://localhost:11434`. Point it at DurinDoor (`http://localhost:20128/v1`) and select an `ollama-local/...` or `ollama/...` model. DurinDoor is the one that calls Ollama's `/v1/messages`.
</Callout>

## Legacy `9router` labels

This transport has no CLI provider section named `9router`. Incoming CLI configs for other tools still use that label. The server accepts it, plus `X-Msh-Platform: 9router`. Data still lives under `~/.9router/` unless you set `DATA_DIR`.

## Check it works

```bash
curl http://localhost:20128/v1/messages \
  -H "Authorization: Bearer YOUR_DURINDOOR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "ollama-local/llama3.2",
    "max_tokens": 64,
    "messages": [{"role": "user", "content": "Say hello."}]
  }'
```

Replace `llama3.2` with a name that connection lists. If curl succeeds and Claude Code fails, the process is still using an upstream Anthropic key or is not reading `~/.claude/settings.json`. Confirm `ANTHROPIC_AUTH_TOKEN` is the DurinDoor key.

| Symptom | Check |
| --- | --- |
| 401 from Ollama cloud | Cloud wants Bearer, not `x-api-key` |
| Duplicate path in upstream URL | Stored host should be an origin; the runtime transport adds `/v1/messages` |
| Stream recorded as success with no stop | Truncation before `message_stop` is a failure on this path |

### Current behavior and implementation boundaries

Ollama registry transports choose native Messages for Claude input. The native path removes cache_control, fetches remote images through guards and requires message_stop to complete streams. Existing ollama cloud connections can use it, but hidden cloud metadata does not permit adding a fresh connection.
