## Unresolved evidence

These names appear session-like in the 69-ID inventory, but the static registry/auth marker does not by itself establish an authorized user-supplied cookie/session contract or an active account sign-in flow. They are not counted as confirmed parity candidates until provider-specific setup, auth parsing and executable dispatch agree: `deepseek-web`, `doubao-web`, `gemini-web`, and `cursor-api`. For each, the outstanding evidence is whether accepted credential is user-supplied session, provider-issued OAuth/device token, ordinary API key, or a delegated local client token; then trace that exact credential through composed auth and executor dispatch on both projects. `poe` is not evidence for `poe-web`: its own upstream identity is API-key auth and the separate web route is outside the 69-ID exact-ID set.

The MiniMax Code row demonstrates why device login is checked independently from registry `authType`: that field is `none`, while the composed OAuth device flow writes a local profile consumed by its executor. Device login is treated as a credential-acquisition path, not inferred from `authType: oauth`. Confirmed OAuth rows above were checked against provider OAuth source and composed runtime; where provider-specific OAuth/device UI/handler evidence is not explicit in the listed sources, this report makes no claim that the user-facing login is identical. “Equivalent” therefore qualifies runnable account/session contract only.
