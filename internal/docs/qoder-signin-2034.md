# Qoder contract comparison for #2034

Comparison pins: CLIProxyAPI `6faa8d20b2673404cff70a2f2d9537ae0d0e684d`, EasyCLIProxyAPI `e4223d5eefa22a3301ca7e2a28d05897432b07f9`, and OmniRoute `e3c1531afd07d5e06f7ffab658584a7ae2e3627e`. These are source comparisons, not live provider verification.

- CLIProxyAPI's [executor registration](https://github.com/router-for-me/CLIProxyAPI/blob/6faa8d20b2673404cff70a2f2d9537ae0d0e684d/sdk/cliproxy/service_executors.go), [auth manager](https://github.com/router-for-me/CLIProxyAPI/blob/6faa8d20b2673404cff70a2f2d9537ae0d0e684d/internal/cmd/auth_manager.go) and [model definitions](https://github.com/router-for-me/CLIProxyAPI/blob/6faa8d20b2673404cff70a2f2d9537ae0d0e684d/internal/registry/model_definitions.go) do not establish a native Qoder contract; the pinned source tree has no Qoder-named files. Generic compatible-provider configuration is not evidence of native OAuth, refresh, region or streaming support.
- EasyCLIProxyAPI's [management API](https://github.com/router-for-me/EasyCLIProxyAPI/blob/e4223d5eefa22a3301ca7e2a28d05897432b07f9/src-tauri/src/management_api.rs) delegates OAuth start, status and callback to its core. Its [guided setup](https://github.com/router-for-me/EasyCLIProxyAPI/blob/e4223d5eefa22a3301ca7e2a28d05897432b07f9/src/pages/EasyModePage.tsx) does not establish a native Qoder login; its pinned tree has no Qoder-named files. The desktop pin does not determine the installed core revision or plugin capabilities.
- OmniRoute's [Qoder OAuth provider](https://github.com/cheaper-inference/OmniRoute/blob/e3c1531afd07d5e06f7ffab658584a7ae2e3627e/src/lib/oauth/providers/qoder.ts) uses an experimental, configured authorization-code flow and user-info lookup. Its [refresh implementation](https://github.com/cheaper-inference/OmniRoute/blob/e3c1531afd07d5e06f7ffab658584a7ae2e3627e/open-sse/services/tokenRefresh/providers/qoder.ts) posts a refresh grant only when configured. Its [registry](https://github.com/cheaper-inference/OmniRoute/blob/e3c1531afd07d5e06f7ffab658584a7ae2e3627e/open-sse/config/providers/registry/qoder/index.ts) supplies static models; its [executor](https://github.com/cheaper-inference/OmniRoute/blob/e3c1531afd07d5e06f7ffab658584a7ae2e3627e/open-sse/executors/qoder.ts) routes PATs through a local CLI and other credentials to a compatible HTTP endpoint, including streaming and envelope handling. The [usage service](https://github.com/cheaper-inference/OmniRoute/blob/e3c1531afd07d5e06f7ffab658584a7ae2e3627e/open-sse/services/usage/qoder.ts) is a separate billing/usage contract. These do not demonstrate interchangeable device credentials, regional accounts or identical billing.

DurinDoor uses regional device login in `src/lib/oauth/providers.js` and `src/lib/oauth/services/qoder.js`, regional signed catalog requests in `open-sse/services/catalogs/qoderModels.js`, and signed streaming requests in `open-sse/executors/qoder.js`. Its device-token refresh is intentionally a no-op; re-login is required when it expires. PAT exchange and usage handling remain separate. No OmniRoute flow was ported.

The mock regression exercises concurrent regional login and refresh through normal entry points. It also reproduces a local isolation defect: the catalog previously keyed by user ID before access token, allowing different credentials with the same regional user ID to share model configuration. Catalog entries now include the access credential in the hashed key. Existing Qoder tests cover regional discovery, usage, request and stream handling. No live calls were made; actual provider support, account-specific billing, browser authorization, refresh behavior and streaming compatibility remain unverified against a live service. The static comparison does not establish parity for OmniRoute's distinct OAuth and CLI paths.
