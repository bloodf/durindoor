# ZCode V4 compatibility for #1252

The pinned first-party V4 app-server does not expose an enforceable text-only session through its documented stdio interface. Gateway dispatch is blocked. This qualification follows the [closed-provider review](./provider-parity-closed-omniroute.md). It concerns the distinct local ZCode process and does not change the Z.ai or GLM account and API-key providers.

## First-party ZCode at `fec975905a2abd4c07e35c40d51fa097a2258ec9`

- **Registration and transport.** The CLI routes `app-server` to the protocol runner with stdin and stdout. The protocol specifies one JSON message per LF-delimited frame, V4 commands through `v4/command`, and a separate subscription to `conversation/<sessionId>` for snapshots and deltas. A command ACK records admission, while the projection reports the result. [CLI dispatch](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/apps/zcode-cli/packages/cli/src/run.ts) · [Protocol](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/docs/zcode-protocol.md)
- **Session schema.** V4 `createSession` accepts model and mode configuration and accepts MCP server definitions separately. Neither its payload nor its nested config declares `toolAllowlist` or `toolDenylist`. The Zod objects strip unfamiliar keys, so an accepted command would not prove that either restriction took effect. [Command schema](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/packages/shared/src/zcode-protocol-v4/command.ts) · [Session config schema](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/packages/shared/src/zcode-protocol-v4/create-session-config.ts)
- **Effective runtime path.** The V4 handler calls `host.createSessionRecord`. The bridge calls `createSessionRecordForV4` with workspace, MCP and workflow options, with no allowlist or denylist. The shared runtime setup assigns `runtimeConfig.toolAllowlist` and derives `runtimeConfig.toolDisallowlist` from its own parameters, but V4 cannot supply the session restrictions at that point. The CLI parses `--disallowed-tools`, but the app-server dispatch does not pass the extracted list to the protocol runner. An empty MCP list cannot establish that built-in tools are disabled. Plan mode still permits some MCP and session-control capabilities, and the permission guide explicitly distinguishes it from OS isolation. [V4 handler](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/apps/zcode-cli/packages/bootstrap/src/zcode-protocol-v4/commands/handlers/session-mgmt.ts) · [Bridge](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/apps/zcode-cli/packages/bootstrap/src/zcode-protocol/v4-bridge.ts) · [Runtime setup](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/apps/zcode-cli/packages/bootstrap/src/zcode-protocol/server-operations.ts) · [Permissions](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/apps/zcode-cli/docs/usage/05-permissions.md)
- **Model discovery.** The protocol guide describes the Host's provider registry and workspace catalog. At this revision, the actual V4 workspace-config projection contains mode options and slash commands. Its implementation assigns model discovery to the Host's ModelSelectionView. The conversation snapshot reports session configuration and usage, and V4 declares a `stop` command. These fields do not supply a standalone model list or prove tool restrictions. [Workspace projection](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/apps/zcode-cli/packages/bootstrap/src/zcode-protocol/v4-workspace-config.ts) · [Snapshot schema](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/packages/shared/src/zcode-protocol-v4/snapshot.ts) · [Stop schema](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/packages/shared/src/zcode-protocol-v4/command.ts)
- **Fixtures.** The CLI unit suite covers dispatch with injected dependencies. The bootstrap suite tests V4 commands, including stop, and tests allowlist/denylist forwarding separately via legacy `session/create`. The legacy tests provide no evidence that V4 enforces the same policy. [CLI tests](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/apps/zcode-cli/packages/cli/tests/cli.unit.test.ts) · [V4 command tests](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/apps/zcode-cli/packages/bootstrap/tests/v4-native-commands.test.ts) · [Legacy restriction tests](https://github.com/zai-org/ZCode/blob/fec975905a2abd4c07e35c40d51fa097a2258ec9/apps/zcode-cli/packages/bootstrap/tests/zcode-protocol.test.ts)

## OmniRoute integration reference at `77470f3644d4b9cfe1f1ff6b31d8bcbee41bf16`

OmniRoute registers `zcode` with alias `zc`, no gateway authentication header, a dedicated executor and the local stdio URI. Its catalog filters a shared GLM model list. That static list is OmniRoute metadata and does not establish which models an operator's V4 session can use. Its executable fixture uses a binary header and value encoding, incompatible with first-party V4 NDJSON. No logic was ported. [Registry](https://github.com/cheaper-inference/OmniRoute/blob/77470f3644d4b9cfe1f1ff6b31d8bcbee41bf16/open-sse/config/providers/registry/zcode/index.ts) · [Executor](https://github.com/cheaper-inference/OmniRoute/blob/77470f3644d4b9cfe1f1ff6b31d8bcbee41bf16/open-sse/executors/zcode.ts) · [Fixture](https://github.com/cheaper-inference/OmniRoute/blob/77470f3644d4b9cfe1f1ff6b31d8bcbee41bf16/tests/fixtures/fake-zcode-app-server.mjs)

Revisit #1252 when a documented V4 session control can be traced through validation and dispatch to enforcement for built-in and dynamically registered tools. Then an injected NDJSON process can cover that contract and gateway behavior without starting a real profile.
